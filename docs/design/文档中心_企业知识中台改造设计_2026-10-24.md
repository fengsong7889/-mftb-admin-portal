# 文档中心 → 企业知识中台（Doc Knowledge v3）改造设计

> 版本：2026-10-24
> 定位：设计稿，不含代码改动。落地前需确认第二十一节决策项。
> 现状基线：`docs/Doc_Native_Progress_2026-10-23.md`（阶段二 A 已完成，全量测试通过）。

---

## 一、一页结论

1. **不重建，演进现有底座**。`doc_node`（稳定身份）+ `doc_revision`（不可变修订）+ 空间位集 + 文档 ACL + 确认/交接/审计/幂等，已经覆盖“文档治理”最难的部分；本次只补“多形态内容、分类体系、密级授权、阅读服务、档案生命周期、接口文档”六块。
2. **用图书馆的 FRBR 四层模型统一内容形态**：作品（`doc_node`）— 表达（`doc_revision`）— 载体（`doc_asset`）— 单件（`doc_book_copy` / 数字授权）。PDF、Office、Markdown、外链、OpenAPI 都只是“载体/表达”的差异，不是五套系统。
3. **三套坐标各司其职，禁止混用**：
   - **空间** = 组织归属与权限上限（唯一权限边界）。
   - **分类** = 知识导航（树形，一个文档一个主分类）。
   - **标签** = 多维检索（受控词表，多对多）。
   - **内容形态** = 渲染器选择，不承载任何权限。
4. **权限从“只认个人”升级为“主体 + 密级 + 有效期”**：`USER / DEPT / ROLE / ALL` 四类主体，`PUBLIC / INTERNAL / SENSITIVE / RESTRICTED` 四级密级，ACL 只能收窄不能放大空间权限。
5. **档案管理只借思想，不照搬全流程**：全宗—系列—案卷—件映射为“空间—一级分类—二级分类/文档—修订/附件”，保留保管期限、密级、冻结、鉴定、双人审批销毁、销毁清册。
6. **接口文档做成“结构化资产”而不是 PDF 附件**：OpenAPI 导入 → 操作清单 → 版本差异 → 破坏性变更确认 → 废弃标记 → 负责人。
7. **首期只做 P0 内容地基**（约 4–6 人周）：分类树、标签、文件对象存储、PDF 预览、统一搜索索引、部门/角色 ACL、密级。图书借阅、RAG、实体馆藏放到后续阶段，避免一次铺开。

## 二、现状盘点与差距

### 2.1 已有能力（可直接复用）

| 能力 | 现状 | 复用方式 |
|------|------|---------|
| 稳定身份 | `doc_node` 同时承载腾讯外链与原生文档 | 继续作为统一目录记录，不换主键 |
| 不可变修订 | `doc_revision` 追加式、`content_hash`、`revision_no` | 所有内容形态共用版本链 |
| 全文检索 | `FULLTEXT(title,summary,markdown) WITH PARSER ngram` | 升级为独立搜索索引表 |
| 权限 | 菜单准入 → 空间位集（1/3/5/7/15）→ 文档 ACL（1/3）→ 版本可见性 | 增加主体类型与密级，不推翻 |
| 治理流程 | 确认、交接、执行状态机、回收站、审计 | 制度签收、到期复核、离职接管复用 |
| 幂等 | `Idempotency-Key` + 请求哈希 + 回执 | 文件上传、批量导入、接口同步复用 |
| 机器接入 | `docint_` 令牌、6 个 MCP 工具、机器审批永远 403 | 增加“机器密级上限”，默认 INTERNAL |
| 导出 | Markdown + JSON 清单（不含正文/凭据/ACL/审计） | 增加文件包与归档移交包 |

### 2.2 按场景看缺口

| 场景 | 现状可做到 | 关键缺口 |
|------|-----------|---------|
| 公司规章制度 | Markdown 正文、版本、确认 | 生效/失效日期、适用范围、全员签收、到期复核、部门/角色可见 |
| 学习书籍（PDF） | `doc_type=4` 仅是元数据，正文靠外链 | 文件存储、PDF 阅读器、书目元数据、书籍分类、阅读进度/笔记/收藏 |
| 研发产品/技术文档 | Markdown、版本、确认、交接 | 附件、模板、关联 RDM 需求/代码仓库、评审多级化 |
| 系统接口文档 | 无专门模型 | OpenAPI 解析、操作清单、版本 diff、破坏性变更门禁、负责人 |
| 人事制度/晋升/绩效 | 仅个人 ACL | 部门/角色授权、密级、有效期、下载审批与水印、访问审计 |
| 搜索发现 | 单表 ngram + 少量筛选 | 分类/标签/形态/负责人分面、PDF/Office 文本提取、权限内过滤、相关推荐 |
| 生命周期 | 有效/归档/废弃 | 草稿→评审→生效→失效→归档→待销毁→销毁、保管期限、冻结、销毁清册 |
| 阅读服务 | 仅 `doc_view_log` 留痕 | 阅读进度、书签、划线批注、收藏、我的书架 |

### 2.3 现有模型的三个结构性约束

1. `doc_node.category` 是自由字符串、`tags` 是逗号串，无法做树形导航和受控词表。
2. `doc_document_acl` 只支持个人、只有 1/3 两个权限位，且 `CHECK` 约束固定，无法表达部门/角色/有效期。
3. 正文只支持 Markdown 且上限 2 MiB；现有附件方案（RDM 的 Base64 入 MEDIUMTEXT、单文件 5 MB）**不能用于 PDF 书籍**。

> 结论：必须新增表与字段，但**不改旧表语义、不删旧列、不换主键**，用兼容层逐步迁移。

## 三、参考模型与映射

### 3.1 图书馆：FRBR 四层

IFLA 的 FRBR 把书目世界分为“作品—表达—载体—单件”。它正好解决“一份制度有多个版本、一本书有 PDF/EPUB/纸质三种载体”的问题：

| FRBR | 本系统 | 说明 |
|------|--------|------|
| Work 作品 | `doc_node` | 稳定身份、标题、分类、负责人；跨版本不变 |
| Expression 表达 | `doc_revision` | 某一版内容（语言、修订号、生效状态） |
| Manifestation 载体 | `doc_asset` | PDF / Office / Markdown / OpenAPI 文件 / 外链 |
| Item 单件 | `doc_book_copy` 或数字借阅授权 | 实体馆藏条码，或某人的限时阅读权 |

**收益**：图书、制度、技术文档共用一套目录与版本；不会出现“书籍表、制度表、接口表”三套重复权限与审计。

### 3.2 档案管理：多级著录 + 生命周期

参考 ISAD(G) 的多级著录思想与国内档案“全宗—系列—案卷—件”实践：

| 档案概念 | 本系统映射 |
|---------|-----------|
| 全宗 | 空间（`doc_space.space_kind = ARCHIVE`） |
| 系列 | 一级分类（`doc_category.level = 1`） |
| 案卷 | 二级分类或文档（按业务选择） |
| 件 | 修订 / 附件（`doc_revision` / `doc_asset`） |
| 保管期限 | `doc_archive_meta.retention_years` |
| 密级 | `confidentiality`（1–4 级） |
| 鉴定 | 到期复核任务 + 销毁申请 |
| 销毁 | 双人审批、销毁清册、保留元数据墓碑 |
| 冻结 | `legal_hold=1`，阻止归档与销毁 |

**借什么**：保管期限、密级、鉴定销毁、清册、冻结。
**不借什么**：不做独立的“档案编研/借阅/移交”全流程，避免变成第二个 OA。

### 3.3 DMS（Confluence/语雀/飞书知识库）

借鉴四点：
- 空间/知识库是权限边界，分类只是导航；
- 模板中心降低写作成本；
- 版本对比 + 变更摘要；
- 权限继承 + 单篇收窄，默认继承、例外显式。

### 3.4 接口文档

参考 OpenAPI 3.1 与 API 管理平台实践：
- `operationId` / `method + path` 作为操作稳定键；
- 规范文件不可变，每次导入生成新修订；
- 语义 diff 分为新增、删除、破坏性、弃用、文档变更；
- 破坏性变更必须由负责人确认后才能生效；
- 废弃操作保留至少一个版本周期，前端显示弃用横幅与替代操作。

## 四、目标与边界

### 4.1 目标

1. 五类场景（制度、书籍、研发、接口、人事）都能在同一目录下被“找到、读懂、授权、追溯”。
2. 新增内容形态不需要新增一套权限、审计、版本系统。
3. 敏感文档做到“默认不可见、可见可追溯、下载可管控”。
4. 搜索在权限范围内做分面检索，不泄露标题与摘要。
5. 档案可归档、可鉴定、可销毁，且销毁后仍保留可审计的元数据。

### 4.2 明确不做（本期）

| 不做 | 原因 | 替代 |
|------|------|------|
| 在线 Office 协同编辑 | 与腾讯文档重复，成本极高 | 继续外链腾讯文档；本系统只做目录/版本/权限 |
| 公网匿名分享链接 | 数据泄露风险不可控 | 仅登录用户 + 短期签名下载 |
| 扫描版 PDF OCR | 依赖重、准确率不可控 | P2 评估；先支持文本型 PDF |
| 实体图书借阅（首期） | 需要条码、馆藏、逾期罚金等线下流程 | 先做数字阅读；实体馆藏作为 P2 可选项 |
| 通用 BPM 工作流引擎 | 现有确认/交接已够用 | 复杂审批接 OA，不在文档中心重造 |
| 文档内实时评论/协同 | 首期价值低于成本 | P2 评估批注，不做实时 |

## 五、总体信息架构

### 5.1 分层

```
┌────────────────────────────────────────────────────────────┐
│ 发现层   门户 / 搜索 / 推荐 / 学习路径 / 我的知识            │
├────────────────────────────────────────────────────────────┤
│ 阅读层   Markdown 阅读器 / PDF 阅读器 / 接口文档视图 / 书架  │
├────────────────────────────────────────────────────────────┤
│ 治理层   确认 / 签收 / 交接 / ACL / 密级 / 审计 / 归档销毁   │
├────────────────────────────────────────────────────────────┤
│ 内容层   doc_node（目录）→ doc_revision（表达）→ doc_asset  │
├────────────────────────────────────────────────────────────┤
│ 权限层   菜单 → 空间位集 → 文档 ACL → 密级 → 下载策略        │
└────────────────────────────────────────────────────────────┘
```

### 5.2 菜单与路由建议

保留现有 6 个菜单，新增 4 个专题视图；**不要为每种文档类型各开一个后台**。

| 菜单 | 路由 | 定位 | 来源 |
|------|------|------|------|
| 知识门户 | `/knowledge` | 推荐、必读、最近更新、分类入口 | 新增 |
| 文档库 | `/doc-center` | 空间 × 分类 × 标签 × 形态的统一浏览 | 现有升级 |
| 图书角 | `/doc-books` | 书目卡片、书籍分类、继续阅读 | 新增 |
| 接口中心 | `/doc-apis` | 按系统浏览 OpenAPI、操作、变更 | 新增 |
| 档案室 | `/doc-archives` | 保管期限、待鉴定、销毁清册 | 新增 |
| 学习路径 | `/doc-learning` | 策展清单、新人包 | 现有 |
| 我的知识 | `/doc-me` | 收藏、笔记、阅读历史、待签收 | 新增 |
| 方案管理 | `/doc-plans` | 原生方案（现有） | 现有 |
| 统计 | `/doc-stats` | 阅读、覆盖、存储、健康度 | 现有升级 |
| 治理与集成 | `/doc-governance` | 分类/标签/模板/密级/凭据/索引 | 现有升级 |

> 图书角、接口中心、档案室都是**同一张目录表上的专题视图**，不是独立存储。这样权限、审计、搜索只实现一次。

### 5.3 三条不可违反的规则

1. **权限只认空间 + 文档 ACL + 密级**；分类、标签、内容形态一律不参与授权判断。
2. **一个文档只有一个主分类**；标签可以有多个。分类用于导航，标签用于检索。
3. **内容形态只决定渲染器**；同一份制度既可以是 Markdown，也可以是 PDF，权限与版本语义完全一致。

## 六、统一内容模型

### 6.1 内容形态矩阵

在 `doc_native_document` 增加 `content_kind`（旧 `doc_node.doc_type` 保留给历史列表/统计做兼容快照）：

| `content_kind` | 名称 | 正文载体 | 编辑器 | 阅读器 | 检索文本来源 |
|---|---|---|---|---|---|
| 1 | MARKDOWN | `doc_revision.markdown` | 原生 Markdown 编辑器 | Markdown 渲染（不执行 HTML） | 正文直接入索引 |
| 2 | PDF | `doc_revision_asset(role=1)` | 上传 | 浏览器原生 PDF / PDF.js | PDF 文本提取 |
| 3 | OFFICE | 原件 + 转换后的预览 PDF | 上传 | 预览 PDF | 转换后文本提取 |
| 4 | EXTERNAL_LINK | `doc_native_document.source_url` | 登记链接 | 新窗口/内嵌 iframe | 仅标题/摘要 |
| 5 | OPENAPI | `doc_api_spec.raw_spec` + 附件 | 导入 OpenAPI | 接口文档视图 | 操作摘要/路径/描述 |
| 6 | IMAGE_GALLERY（可选） | 多张图片资产 | 上传 | 图集 | 标题/说明 |

**图书不是一种 `content_kind`**：一本书通常是 `content_kind=2`（PDF）加一行 `doc_book_meta`（ISBN、作者、出版社、封面、书籍分类）。这样“书”与“PDF 制度”共享阅读器与权限。

### 6.2 旧字段兼容

| 旧字段 | 新行为 |
|-------|--------|
| `doc_node.doc_type`（1–5） | 保留；新文档写入兼容值（Markdown→1、PDF→4、外链→5），仅用于旧列表与统计 |
| `doc_node.category` | 保留为分类名快照；新写入同时写 `category_id`，旧字段由服务层回填 |
| `doc_node.tags` | 保留为逗号串快照；新写入同时写 `doc_node_tag`，读取以标签表为准 |
| `doc_node.tencent_url` | 新原生文档写空串；外链文档写目标 URL |
| `doc_native_document.lifecycle` | 保留；由 `doc_node.status` 派生同步，旧接口继续可读 |

> 双写只维持两个发布周期；之后旧字段转为只读快照，不再作为事实源。

## 七、分类与标签

### 7.1 分类树 `doc_category`

```sql
CREATE TABLE doc_category (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  space_id    BIGINT NOT NULL,
  parent_id   BIGINT NOT NULL DEFAULT 0,
  code        VARCHAR(64) NOT NULL,
  name        VARCHAR(100) NOT NULL,
  path        VARCHAR(500) NOT NULL COMMENT '如 /1/5/9/，用于子树查询',
  level       TINYINT NOT NULL DEFAULT 1,
  sort_order  INT NOT NULL DEFAULT 0,
  doc_count   INT NOT NULL DEFAULT 0 COMMENT '异步汇总，仅展示',
  status      TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_doc_category_code (space_id, code),
  KEY idx_doc_category_parent (space_id, parent_id, sort_order),
  CONSTRAINT fk_doc_category_space FOREIGN KEY (space_id) REFERENCES doc_space(id),
  CONSTRAINT ck_doc_category_level CHECK (level BETWEEN 1 AND 4)
);
```

规则：
- 分类属于空间，最多 4 级；跨空间不共享分类树。
- 支持新增、重命名、移动、合并、停用；**停用不删除**，历史文档仍可显示。
- 移动分类时同步更新子树 `path`，单事务完成。
- `doc_count` 异步汇总，允许短暂不准；列表页不依赖它做权限判断。

### 7.2 标签 `doc_tag` / `doc_node_tag`

```sql
CREATE TABLE doc_tag (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  space_id   BIGINT NULL COMMENT 'NULL=全局标签',
  name       VARCHAR(64) NOT NULL,
  color      VARCHAR(16) NULL,
  status     TINYINT NOT NULL DEFAULT 1,
  created_by BIGINT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_doc_tag_name (space_id, name)
);

CREATE TABLE doc_node_tag (
  node_id BIGINT NOT NULL,
  tag_id  BIGINT NOT NULL,
  PRIMARY KEY (node_id, tag_id),
  KEY idx_doc_node_tag_tag (tag_id, node_id),
  CONSTRAINT fk_doc_node_tag_node FOREIGN KEY (node_id) REFERENCES doc_node(id),
  CONSTRAINT fk_doc_node_tag_tag FOREIGN KEY (tag_id) REFERENCES doc_tag(id)
);
```

规则：
- 空间可启用“仅允许受控标签”，禁止自由输入；治理页维护词表、合并同义词。
- 单文档标签上限 20 个；标签名称空间内唯一。
- 标签不承载权限，不作为密级替代。

### 7.3 迁移

1. 按 `(space_id, category)` 去重生成一级分类，`code` 用稳定哈希或序号。
2. 解析 `doc_node.tags` 逗号串，生成标签与关联；无法解析的保留原文到 `doc_node.tags`，不阻断。
3. 回填 `doc_native_document.category_id`；未匹配的归入“未分类”。
4. 提供只读校验脚本：分类覆盖数、标签关联数、未分类数、重复名。

## 八、文件与对象存储

### 8.1 为什么不能用现有 Base64 方案

现有 RDM 附件是“服务端不落盘 → Base64 Data URL 存 MEDIUMTEXT”，上限 5 MB。PDF 书籍通常 10–100 MB，Base64 膨胀 33%，会拖垮行记录、备份与查询。**文档中心禁止把二进制写入 MySQL**。

### 8.2 存储抽象

```java
public interface DocObjectStorage {
    StoredObject put(String key, InputStream in, long size, String contentType);
    String presignGet(String key, Duration ttl);
    String presignPut(String key, Duration ttl, String contentType);
    void delete(String key);
    ObjectStat stat(String key);
}
```

| 环境 | 实现 | 说明 |
|------|------|------|
| 本地开发 | `LocalDocObjectStorage` | 目录可配置，默认 `backend/.local/doc-assets`，已在 gitignore |
| 测试/生产 | `S3DocObjectStorage` | S3 兼容：MinIO / 阿里云 OSS / 腾讯 COS / AWS S3 |
| 降级 | 只读模式 | 存储不可用时禁止上传与新预览，已有元数据仍可读 |

配置项（放 `backend/.env.local`，不入库）：`DOC_STORAGE_PROVIDER`、`DOC_STORAGE_ENDPOINT`、`DOC_STORAGE_BUCKET`、`DOC_STORAGE_ACCESS_KEY`、`DOC_STORAGE_SECRET_KEY`、`DOC_STORAGE_REGION`。

### 8.3 上传流程（直传优先）

```
客户端 → POST /assets/presign {fileName,size,mime,sha256}
服务端 → 校验白名单/大小/空间配额 → 创建 doc_asset(status=1 待确认) → 返回预签名 URL
客户端 → PUT 直传对象存储
客户端 → POST /assets/{id}/complete
服务端 → HEAD 校验大小/ETag → 读取文件头 magic bytes → 可选病毒扫描 → status=2 可用
客户端 → 创建/保存修订时绑定 assetId
```

小文件（< 10 MB）允许服务端中转上传；大文件必须直传，避免占满应用内存。

### 8.4 限制与安全

| 项 | 建议值 | 说明 |
|----|--------|------|
| PDF / Office 单文件 | 50 MB（可配） | 超限拒绝 |
| 图片 | 10 MB | 封面/插图 |
| Markdown 正文 | 2 MiB（维持现状） | 与资产限额分离 |
| 扩展名白名单 | pdf/doc/docx/xls/xlsx/ppt/pptx/txt/md/csv/png/jpg/webp | 其他拒绝 |
| magic bytes | 必检 | 防伪造 Content-Type |
| 压缩包 | 首期不允许 | 防 zip bomb；后续单独沙箱解压 |
| 病毒扫描 | ClamAV 可选 | 不可用时标记 `scan_result=UNSCANNED`，由策略决定是否放行 |
| 对象桶 | 私有，禁止公共读 | 下载必须走签名 URL |
| 签名 URL | 5 分钟 | 一次性、绑定用户与文件 |
| 下载响应头 | `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff` | 防内联执行 |
| 缓存 | `Cache-Control: private, no-store` | 禁止 CDN 缓存私密文档 |
| 审计 | 每次下载写 `doc_download_log` | 含用户、IP、UA、文件、用途 |

## 九、权限、密级与合规

### 9.1 五层判定（在现有四层上增加密级）

```
菜单准入
  → 空间位集（READ=1 / EDIT=2 / CONFIRM=4 / MANAGE=8）
    → 文档 ACL（USER / DEPT / ROLE / ALL，可带有效期）
      → 密级（PUBLIC / INTERNAL / SENSITIVE / RESTRICTED）
        → 下载策略（允许 / 需审批 / 禁止）
```

- 空间是**权限上限**：文档 ACL 只能收窄或等价，不能把一个“无空间读权限”的人放进来。
- 密级是**硬门槛**：用户密级不足时，即使 ACL 命中也不可见。
- 菜单准入只决定能否进入页面，不替代资源校验。

### 9.2 文档 ACL 主体

```sql
CREATE TABLE doc_acl_entry (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  node_id      BIGINT NOT NULL,
  subject_type VARCHAR(16) NOT NULL COMMENT 'USER/DEPT/ROLE/ALL',
  subject_id   VARCHAR(64) NOT NULL COMMENT 'sys_user.id / sys_department.id / sys_role.id / 0',
  permissions  INT NOT NULL DEFAULT 1 COMMENT '1读 3读写',
  expires_at   DATETIME NULL,
  created_by   BIGINT NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_doc_acl_entry (node_id, subject_type, subject_id),
  KEY idx_doc_acl_lookup (subject_type, subject_id, node_id),
  CONSTRAINT fk_doc_acl_entry_node FOREIGN KEY (node_id) REFERENCES doc_native_document(node_id),
  CONSTRAINT ck_doc_acl_entry_perm CHECK (permissions IN (1,3))
);
```

- `ALL` 只允许用于 `PUBLIC/INTERNAL`，禁止用于 `SENSITIVE/RESTRICTED`。
- 过期行在判定时忽略，定时任务只做清理提示，不物理删除。
- 旧 `doc_document_acl` 保留，读取时与新表取并集；新写入只写新表，旧表逐步只读。

### 9.3 密级与用户授权

| 密级 | 值 | 含义 | 可见条件 | 下载 |
|------|---|------|---------|------|
| PUBLIC | 1 | 公开 | 菜单准入 + 空间读 | 按文档策略；默认允许 |
| INTERNAL | 2 | 内部 | 空间读 | 按文档策略；默认允许 |
| SENSITIVE | 3 | 敏感 | 空间读 + ACL 命中（部门/角色/个人）+ 用户密级 ≥3 | 需审批 + 水印 |
| RESTRICTED | 4 | 机密 | 空间读 + 个人 ACL + 用户密级 ≥4 | 需审批 + 水印 + 禁止导出 |

```sql
CREATE TABLE doc_user_clearance (
  user_id     BIGINT PRIMARY KEY,
  max_level   TINYINT NOT NULL DEFAULT 2,
  granted_by  BIGINT NOT NULL,
  granted_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  expires_at  DATETIME NULL,
  CONSTRAINT fk_doc_clearance_user FOREIGN KEY (user_id) REFERENCES sys_user(id),
  CONSTRAINT ck_doc_clearance_level CHECK (max_level BETWEEN 1 AND 4)
);
```

- 未登记用户默认 `INTERNAL(2)`，不是 `PUBLIC`。
- 密级授权必须由空间 MANAGE 或系统管理员授予，写审计。
- 人事绩效、薪酬、晋升材料建议默认 `RESTRICTED`，并绑定部门/角色 + 个人例外。

### 9.4 制度签收的“适用范围”

“谁能读”与“谁必须签收”是两件事：

```sql
CREATE TABLE doc_ack_target (
  node_id     BIGINT NOT NULL,
  revision_id BIGINT NOT NULL,
  subject_type VARCHAR(16) NOT NULL COMMENT 'DEPT/ROLE/ALL',
  subject_id  VARCHAR(64) NOT NULL,
  due_at      DATE NULL,
  PRIMARY KEY (node_id, revision_id, subject_type, subject_id)
);

CREATE TABLE doc_ack_receipt (
  node_id     BIGINT NOT NULL,
  revision_id BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  acknowledged_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  source_ip   VARCHAR(64) NULL,
  user_agent  VARCHAR(255) NULL,
  PRIMARY KEY (node_id, revision_id, user_id)
);
```

- 签收只对“当前生效修订”有效；换版后需要重新签收。
- 覆盖统计按部门/角色汇总，避免逐个点名造成隐私压力。
- 到期未签收进入提醒队列，接现有钉钉通知能力。

### 9.5 下载、水印与导出

- 文档级 `download_policy`：1 允许、2 需审批、3 禁止。
- `SENSITIVE` 默认 2，`RESTRICTED` 默认 2 且禁止 JSON/Markdown 导出。
- 水印内容：姓名 + 工号 + 时间 + “禁止外传”；`RESTRICTED` 服务端叠加，`SENSITIVE` 客户端覆盖。
- 导出（Markdown/JSON 清单/归档包）与下载同权限；批量导出需 MANAGE + 二次确认。
- 所有下载、导出、ACL 变更、密级变更、销毁写审计；`SENSITIVE/RESTRICTED` 的阅读也写审计。

### 9.6 机器身份（MCP / AI）

- `doc_integration_grant` 增加 `max_confidentiality`，默认 2；签发时不得超过签发人密级。
- 机器令牌**永远不能**审批、签收、导出、销毁、改 ACL。
- 机器检索结果必须在服务端按密级与 ACL 过滤；禁止把过滤交给适配器。
- 机器令牌只允许访问被授权空间；跨空间与 `RESTRICTED` 一律 403。

## 十、生命周期、制度与档案

### 10.1 统一状态机

在 `doc_node.status` 上扩展（旧值 1–4 不变）：

| 值 | 状态 | 说明 |
|---|------|------|
| 1 | 草稿 | 仅作者/协作者可见 |
| 2 | 评审中 | 待确认，正文冻结 |
| 3 | 已生效 | 当前有效版本，可被阅读/签收 |
| 4 | 已归档 | 只读保留，默认不在列表主视图 |
| 5 | 已失效 | 被新版本替代，保留可查 |
| 6 | 待销毁 | 鉴定通过，等待审批执行 |
| 7 | 已销毁 | 内容已清除，仅保留元数据墓碑 |

```
草稿(1) → 评审中(2) → 已生效(3) → 已失效(5)
                              ↘ 已归档(4) → 待销毁(6) → 已销毁(7)
```

- `legal_hold=1` 为叠加标记，阻止进入 6/7。
- 未来生效：`effective_from` 可晚于确认通过时间，定时任务在到期日切换状态；切换前仍显示“待生效”。
- 旧 `doc_native_document.lifecycle` 由状态派生：1–3 → 1 有效，4 → 2 归档，6/7 → 3 废弃。

### 10.2 制度专项字段

在 `doc_native_document` 增加：

| 字段 | 说明 |
|------|------|
| `effective_from` / `effective_to` | 生效/失效日期 |
| `review_cycle_months` | 复核周期（如 12 个月） |
| `superseded_by_node_id` | 被哪个新文档替代 |
| `download_policy` | 1 允许 / 2 需审批 / 3 禁止 |
| `confidentiality` | 1–4 级 |
| `category_id` | 主分类 |
| `content_kind` | 内容形态 |

销毁规则：

4. 销毁不可逆，接口要求二次确认 + 输入文档编号。

### 10.5 删除、归档、销毁的区别

| 动作 | 可逆 | 内容 | 元数据 | 适用 |
|------|------|------|--------|------|
| 回收站删除 | 是 | 保留 | 保留 | 误删、草稿 |
| 归档 | 是（可恢复） | 保留 | 保留 | 历史版本、离职资料 |
| 销毁 | 否 | 清除 | 墓碑 | 到期且无保留价值 |

1. 上传 OpenAPI 3.0/3.1 JSON/YAML；Swagger 2 先转换。
2. 解析为操作清单；`method + path` 为稳定键，`operationId` 为展示键。
3. 规范化请求/响应 schema（排序键、去除描述），计算 `schema_hash`。
4. 与上一版对比：
   - 新增操作 → 1；
   - 删除操作 → 2，且标记破坏性；
   - 请求必填增加、类型收窄、枚举减少、响应字段删除 → 3 破坏性；
   - `deprecated: true` → 4；
   - 仅描述变更 → 5。
5. 存在破坏性变更时，文档状态不得直接进入“已生效”，需负责人确认（写入 `doc_api_change.acknowledged_by`）。
6. 每次导入生成新的 `doc_revision`（不可变），`raw_spec` 作为附件/正文存储。

### 12.3 展示

- 左侧：按 tag 分组的操作树；顶部按系统、版本、废弃状态筛选。
- 右侧：方法 + 路径、摘要、参数表、请求体 schema 树、响应示例、错误码、负责人、变更历史。
- 提供“复制 cURL”“查看 diff”“查看上一版”。
- 首期不做在线试调（避免把生产令牌带进浏览器）；P3 可接沙箱环境。

### 12.4 安全

- 示例中的 `Authorization`、`Cookie`、`token`、`secret` 自动脱敏。
- 不允许在描述中粘贴真实密钥；导入时扫描并阻断高危模式。
- 接口文档默认 `INTERNAL`；涉及内部地址、未公开接口的设为 `SENSITIVE`。

## 十三、搜索与发现

### 13.1 独立搜索索引

不直接在 `doc_revision` 上做多表 join，新增反规范化索引表：

```sql
CREATE TABLE doc_search_index (
  node_id        BIGINT PRIMARY KEY,
  space_id       BIGINT NOT NULL,
  category_id    BIGINT NULL,
  title          VARCHAR(200) NOT NULL,
  summary        VARCHAR(1000) NOT NULL DEFAULT '',
  body_text      MEDIUMTEXT NOT NULL,
  tags           VARCHAR(500) NOT NULL DEFAULT '',
  owner_user_id  BIGINT NULL,
  content_kind   TINYINT NOT NULL DEFAULT 1,
  confidentiality TINYINT NOT NULL DEFAULT 2,
  status         TINYINT NOT NULL DEFAULT 1,
  effective_from DATE NULL,
  index_state    TINYINT NOT NULL DEFAULT 1 COMMENT '1待索引 2就绪 3失败',
  updated_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FULLTEXT KEY ft_doc_search (title, summary, body_text, tags) WITH PARSER ngram,
  KEY idx_doc_search_facet (space_id, category_id, content_kind, status),
  KEY idx_doc_search_owner (owner_user_id)
);
```

维护时机：
- 创建/保存修订：同步 upsert 标题、摘要、Markdown 正文、标签；
- PDF/Office 文本提取完成：更新 `body_text` 与 `index_state`；
- 删除/恢复/归档/销毁：同步状态；
- 提供管理端“重建索引”命令，按空间分批执行。

### 13.2 检索与分面

- 关键词：`MATCH ... AGAINST`（ngram），标题命中加权。
- 分面：空间、分类（含子树）、标签、内容形态、负责人、年份、状态、密级。
- 排序：相关度、最近更新、生效日期、阅读量。
- 权限过滤必须在 SQL 中完成，**禁止先分页后过滤**，否则会泄露总数与标题。
- 对外只返回用户有权阅读的字段；无权限文档不返回“存在但无权”的提示。

### 13.3 相关推荐

- 同分类 + 同标签的前 N 篇；
- 同一学习路径的下一篇；
- 同一 RDM 需求/系统关联的文档；
- 阅读过本文档的人还读过（按 `doc_view_log` 聚合，需脱敏）。

### 13.4 RAG（P3）

复用现有 `ai_knowledge_doc` / `ai_knowledge_chunk`，但必须解决权限：
- 分块表增加 `source_ref`（= `node_id`）与 `system_code`；
- 检索时 join `doc_search_index` / `doc_native_document` / `doc_acl_entry`，按当前用户过滤；
- 无权限的分块不得进入上下文，也不得出现在引用列表；
- 引用回链到固定修订 URL；
- `RESTRICTED` 默认不进入 RAG，除非管理员显式开启且用户密级足够。

## 十九、安全边界与校验点

| 层 | 校验点 |
|----|--------|
| 前端 | 仅做 UX 校验与按钮显隐；不作为安全边界 |
| 网关/过滤器 | JWT 与 `docint_` 分流；集成令牌只允许白名单方法/路径；请求体大小限制 |
| 服务层 | 每次读写重新判定菜单、空间、ACL、密级；不信任前端传的 `spaceId/nodeId/userId` |
| SQL | 全部参数化；列表权限过滤在 SQL 内完成；禁止拼接表名/列名 |
| 文件 | 扩展名 + magic bytes + 大小 + 压缩包拒绝 + 对象桶私有 + 签名 URL 短时 |
| 下载 | 权限 + 策略 + 审计 + 水印；`RESTRICTED` 禁止导出 |
| 搜索 | 过滤后再分页；不返回无权文档的标题/摘要/总数 |
| 机器身份 | 密级上限、空间上限、不可审批/导出/销毁/改 ACL |
| 审计 | 追加式；ACL/密级/下载/导出/销毁/归档必记；敏感阅读也记 |
| 日志 | 不打印令牌、密码、连接串、正文；错误不返回堆栈与 SQL |
| 缓存 | 私密内容 `no-store`；不走公共 CDN |

## 二十、测试计划

### 20.1 单元测试

- 分类树：移动、合并、停用、子树路径更新、循环引用拒绝。

- ACL 绕过：直接访问下载/预览/导出端点。
- 过期 ACL 仍可读。
- 机器令牌访问 `SENSITIVE/RESTRICTED`、审批、导出、销毁。
- 搜索泄露：无权文档的标题、摘要、总数。
- 文件伪造：改扩展名、改 Content-Type、PDF 内嵌 JS、超大文件、zip bomb。
- 路径穿越：对象 key、下载文件名。
- 导出泄露：JSON 清单是否含正文/ACL/凭据。

### 20.4 前端测试

- 路由与菜单一致性（`check:menu`）。
- 权限驱动渲染：无权限不显示按钮。
- 阅读器：PDF 预览、进度保存、笔记锚点。
- 接口文档：操作树、diff 展示、废弃标记。
- i18n：繁中/英文键完整。
- 统计卡位置（`check:stat-order`）、确认弹窗（`check:confirm-modal`）。

### 20.5 性能与容量

- 1 万文档、10 万修订下的列表/搜索 P95。
- 50 MB PDF 上传/下载/预览。
- 并发 100 用户搜索与阅读。
- 索引重建按空间分批，不锁表。

### 20.6 门禁

- 后端：`mvn -o test` 全量；真实库集成单独注入 `DB_URL`。
- 前端：`npm run verify`。
- 迁移：独立空库重放 + 存量库重复启动。
- 安全：`npm run secret-scan`。

## 二十一、回滚方案

| 层 | 方案 |
|----|------|
| 代码 | 按阶段独立提交；新模块用特性开关（`doc.knowledge.enabled`、`doc.asset.enabled`、`doc.api.enabled`、`doc.archive.enabled`）控制入口 |
| 数据库 | 只做 additive 迁移；不删列、不改旧列语义、不删表；回滚只停用新入口 |
| 接口 | `/api/doc/v2/*` 保持可用；v3 故障时前端回退 v2 列表/详情 |
| 存储 | 对象保留；只停用上传/预览；已有文件仍可通过旧链接读取（若存在） |
| 搜索 | 索引异常时关闭 v3 搜索，回退数据库条件查询 |
| 菜单 | 通过版本化迁移停用新菜单并处理授权，保留菜单 ID；不手工删远程菜单 |
| 权限 | 若 ACL 出现越权缺陷，v3 读接口整体 fail-closed，保留 v2 只读；修复后再开放 |
| 审计 | 回滚不删除审计与销毁清册 |

## 二十二、风险与取舍

| 风险 | 影响 | 应对 |
|------|------|------|
| 范围过大 | 长期无法上线 | 严格按 P0→P3；P0 不包含借阅、RAG、OCR |
| 对象存储未就绪 | PDF/Office 无法上线 | 本地磁盘实现先跑通；生产前必须接 S3 兼容 |
| PDF.js 依赖评审不通过 | 笔记锚点体验受限 | P0 浏览器原生预览；笔记先支持页码级 |
| 历史分类/标签质量差 | 导航混乱 | 迁移后提供治理页批量合并/改派；允许“未分类” |
| ACL 组合复杂 | 性能与越权风险 | 统一 `DocAccessResolver`；缓存用户主体集合；全量矩阵测试 |
| 搜索索引延迟 | 新文档搜不到 | 同步 upsert + `index_state` 提示；管理端可重建 |
| 敏感文档泄露 | 合规事故 | 默认 INTERNAL、密级硬门槛、下载审批/水印、审计、机器令牌上限 |
| 模型过度设计 | 维护成本高 | 图书/接口/档案共用目录与版本；不为每类文档建独立表 |

## 二十三、场景走查

### 23.1 公司规章制度

HR 在“制度库”空间新建文档 → 选择分类“人事制度/考勤” → 设置密级 INTERNAL、生效日期、复核周期 12 个月、签收范围“全员” → 上传 Markdown/PDF → 提交确认 → 管理员确认生效 → 员工在“待签收”看到 → 阅读并签收 → 到期前 30 天生成复核任务 → 换版后旧版进入“已失效” → 满 10 年归档 → 鉴定后双人审批销毁，保留清册。

### 23.2 学习书籍

管理员在“图书角”新建书目 → 填写 ISBN/作者/出版社/书籍分类 → 上传 PDF、封面 → `access_mode=1` 自由阅读 → 员工按分类浏览 → 打开阅读器 → 进度自动保存 → 划线做笔记 → 收藏 → 在“我的知识/继续阅读”接着读。

### 23.3 研发产品/技术文档

产品经理在“研发文档”空间新建 Markdown → 关联 RDM 需求单 → 选择分类“产品/需求”、标签“支付/结算” → 提交评审 → 研发负责人确认 → 生效 → 交接给新负责人 → 旧版本保留 → 相关推荐显示同需求的其他文档。

### 23.4 系统接口文档

后端负责人上传 OpenAPI 3.1 → 系统选择 `rdm` → 解析出 42 个操作 → 与上一版 diff 发现 2 个删除、1 个必填新增 → 标记为破坏性 → 负责人确认 → 新版本生效 → 前端在“接口中心”按 tag 浏览、复制 cURL、查看 diff → 废弃操作显示替代路径与下线时间。

### 23.5 人事绩效

HR 上传“2026 年度晋升评审办法” → 密级 RESTRICTED → ACL 绑定“人力资源部”角色 + 各业务负责人个人 → 有效期 90 天 → 下载策略“需审批” → 负责人申请下载 → 审批通过 → 服务端加水印 PDF → 下载审计记录 → 到期后 ACL 自动失效，文档自动归档。

## 二十四、待确认决策

1. **对象存储**：生产是否已有 S3 兼容存储（MinIO/OSS/COS）？推荐直接接 S3 兼容；若暂时没有，P0 用本地磁盘，但上线前必须切换。
2. **图书范围**：首期只做数字阅读（推荐），还是同时做实体馆藏借阅（条码/馆位/逾期）？
3. **接口文档来源**：首期手工上传 OpenAPI（推荐，快），还是直接做 Git 自动同步（需要仓库权限与 webhook）？
4. **人事敏感文档授权**：是否确认引入“部门/角色 + 密级 + 有效期”（推荐必须），还是继续只用个人 ACL？
5. **依赖评审**：是否允许新增 PDFBox（后端文本提取）与 PDF.js（前端笔记锚点）？若不允许，P0 用浏览器原生 PDF + 标题/摘要检索。
6. **RAG 时点**：是否同意放到 P3，并先完成权限同步与引用回链，再接 AI 助手？
