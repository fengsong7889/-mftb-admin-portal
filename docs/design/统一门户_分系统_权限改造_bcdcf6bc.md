# 统一门户与分系统权限改造方案

## 一、结论：方向主流，但不需要一步到位拆成微服务

你的三个设想对应企业系统中常见的架构：**统一身份认证 + 应用门户 + 应用准入授权 + 应用内部权限**。

用户体验是：

```text
员工登录一次
    ↓
企业应用门户：只显示有权进入的系统
    ├─ 广告系统 → 有权限的菜单 → 有权限的操作
    ├─ HR 系统 → 有权限的菜单 → 有权限的操作
    ├─ 权限中心 → 系统授权、菜单授权、角色管理
    ├─ OA 系统 → 申请、待办、流程
    └─ 财务、物资、AI 等系统
```

这是成熟企业软件中的常见模式，但不能据此认定所有大厂都采用同一种内部实现：
- [Microsoft Entra My Apps](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/myapps-overview) 提供应用门户，按用户/组分配应用，集中呈现用户可访问的应用。
- [阿里云 CloudSSO 用户门户](https://www.alibabacloud.com/help/en/cloudsso/user-guide/log-on-to-the-cloudsso-user-portal-and-access-alibaba-cloud-resources) 体现了“统一登录后选择有权限的目标账户及权限配置”的类似模式；它面向云账户，并非直接等同于 HR/OA 应用门户。

通常的实现分工：身份中心回答“你是谁”，权限中心回答“你能进入什么系统、做什么”，业务系统最终校验接口和业务数据权限。门户本身只是入口，不是唯一安全边界。

### 推荐选择

| 路线 | 能力 | 代价 | 本项目选择 |
|---|---|---|---|
| 统一门户、逻辑分系统 | 独立入口、菜单、权限和工作台，共享部署 | 中等，现有业务复用较多 | 首期采用 |
| 多个独立前端、共享后端 | 各前端独立发布，后端仍统一 | 中高，需要共享组件、登录及部署治理 | 有独立发布需要时再做 |
| 独立前后端与数据边界 | 独立扩容、故障隔离、独立团队发布 | 高，还涉及跨系统调用、事务、数据一致性 | 不纳入首期 |

**首期实现的是同一应用内共享登录态，不是跨独立应用的标准 SSO。** 它可以完整实现你提出的用户体验，但不能承诺进程级故障隔离、独立发布或数据库物理隔离。微前端、微服务和 SSO 是不同维度，不要求同时引入。

1. 现有路由、菜单、接口与系统的完整映射。

## 三、首期范围与系统划分

已确认的前提：现有企业内部使用；先做统一门户和分系统工作台；不做多租户，不拆服务器，不拆数据库。

按业务域归组，而不是把每个一级菜单机械地变成一个系统。首批目录如下；员工只看到自己被授权的部分：

| 系统编码 | 系统名称 | 首期归属 |
|---|---|---|
| `ads` | 广告与推广系统 | 广告销售、推广配置、算法、坑位、赠送、推广报表、团购运营 |
| `hr` | HR 系统 | 员工档案、组织架构、职位、人事信息 |
| `iam` | 权限中心 | 角色、角色绑定、系统准入、功能授权、数据授权、菜单配置、登录审计、账号安全管理 |
| `oa` | OA 系统 | 我的申请、流程中心、审批流程配置、采购申请、个人资产/领用等员工自助入口 |
| `eam` | 物资管理系统 | 资产台账及流转、采购订单、入库、耗材管理、库存及报表 |
| `finance` | 财务系统 | 余额、充值、扣款、转账、账务明细、对账、现有财务审批 |
| `merchant` | 商户运营系统 | 商户集团、门店、门店数据配置、地图规划 |
| `search` | 搜索运营系统 | 搜索词库、引导、策略、效果校验、搜索报表 |
| `ai` | AI 管理系统 | 模型、配额、授权、MCP、使用统计、会话审计 |
| `platform` | 平台配置系统 | 通知配置、多语言、通用规则、版本记录及平台辅助工具 |

边界决定：
- 身份、组织信息保留一份主数据，不为各系统复制员工表。
- HR 维护人事资料；角色绑定、权限分配、管理员身份和账号安全操作归权限中心。HR 的人事编辑权不等于授权权。
- OA 负责申请/流程体验，业务执行仍由原业务服务负责。首期不合并现有财务审批引擎与 OA 引擎。
- 耗材领用中的个人自助归 OA；管理员发放与库存管理归 EAM。同一组件可复用，但服务端动作权限必须区分。
- 原 `Home` 保留为门户内的“个人工作台”；AI 对话继续受已有 AI 使用授权和配额约束，不能由“可以进入个人工作台”推导出 AI 管理权限。
- 已有原型页面明确标记为原型，受所在系统权限约束；未接后端的功能不因本次改造自动变成正式能力。

## 四、用户体验与路由方案

### 4.1 登录与门户
- 普通登录成功默认进入 `#/portal`，即使只有一个系统也先显示门户，保持入口一致。
- 门户展示系统名称、图标、说明，支持搜索；无权限系统默认不显示，首期不做权限申请工作流。
- 没有任何系统授权时显示“暂未分配系统权限”，不视为登录失败。
- `#/` 兼容重定向到 `#/portal`；原首页迁移为 `#/workbench`，作为已登录个人工作台入口。
- 门户与个人工作台使用公共布局，不显示跨所有业务域的侧边栏。

### 4.2 系统内部
- 新增 `#/s/:systemCode` 作为通用系统工作台：显示系统名称及有权限的菜单快捷入口，首期不新增业务报表。
- 进入系统后只显示该系统的授权菜单；顶部固定提供“返回门户”和“切换系统”。
- 只有系统准入、没有菜单授权时，可进入系统工作台，但显示“尚未分配功能权限”。不能默认开放全部菜单。
- 系统不存在显示 404，无准入显示 403，服务不可用显示不可用状态，不渲染旧缓存中的业务内容。

### 4.3 兼容现有路径
- 首期保留 `/employee-management`、`/ad-sales` 等原业务路径与 API 路径，不批量改为 `/s/hr/...`，避免改动大量页面内跳转及通知链接。
- 根据匹配到的业务路由和对应菜单归属确定当前系统；不能仅靠 localStorage 中的“最后选择系统”。
- 刷新、浏览器前进后退、收藏及通知直达都经过系统、菜单和动作校验。
- 登录前保存本站内部目标路由；登录后校验通过再恢复，否则返回门户。不接受任意外部回跳 URL。
- 动态路径使用路由模式匹配，覆盖 `/:id`、新增、编辑、详情、打印等子页面；未知业务路由返回 404，不默认放行。
- 标签页、最近访问按 `用户ID + 系统编码` 隔离；收藏增加系统归属并重新校验。切换账号、撤权、登出时清理对应缓存。

## 五、权限模型：在现有 RBAC 上增加系统准入

### 5.1 四个不同层次

```text
身份认证：是否为有效会话
    ↓
系统准入：是否获准进入 ads / hr / oa 等
    ↓
菜单与动作：能否查看、创建、编辑、删除、导出、审批
    ↓
数据与业务规则：能操作哪些商户、部门、本人记录或流程任务
```

普通业务请求的判断为：

```text
允许 = 会话有效
    AND 系统启用
    AND 拥有系统准入
    AND 菜单启用且拥有该动作
    AND 满足该业务的数据范围与状态约束
```

系统准入不能替代菜单权限；菜单权限不能替代数据范围。已有商户数据范围、本人记录和流程参与人校验继续保留，不宣称当前所有模块已经具备统一行级权限。

### 5.2 授权规则
- 延续现有“角色授权 ∪ 所属部门授权”的合并规则，首期不增加用户级直授和复杂 deny 规则。
- 系统准入单独保存；角色可跨系统授权，不强行拆分现有角色或修改被审批流程引用的角色编码。
- 权限中心先选择系统，再配置该系统菜单及动作；保存仅影响选中的系统，不得覆盖角色在其他系统的授权。
- 移除某一来源的系统授权后，若另一角色或部门仍授权，用户仍有准入；授权页展示最终权限来源，避免把“移除一条来源”误认为“完全撤权”。
- 系统准入完全撤销后，即使保留菜单授权记录，也不能使用；重新授权前明确展示将恢复的已有功能权限。
- 迁移时保持既有动作集合。历史空动作按当前后端的 `view` 语义显式化；新授权不再以空数组暗示查看，空选择表示未授权。
- 对“仅编辑、缺少查看”等历史配置做冲突清单，不在迁移时无提示扩大动作权限。
- 平台超级管理员统一由服务端判定，前后端共用结果。普通系统角色不能通过自助绑定或修改角色编码成为超管。
- 内置权限中心不能被普通配置操作停用；超级管理员身份变更保留专门限制和审计，避免把管理入口锁死。

### 5.3 员工自助
现有全员自助能力迁移到一个明确的“基础员工”角色，赋予 OA 准入及必要自助动作；已有正常员工进行一次性初始化，新员工创建时绑定。该角色不包含全员资产台账、全量库存或 HR 档案权限；本人/任务参与人范围由后端校验，不接受客户端传入任意用户ID决定范围。

## 六、数据结构与接口

### 6.1 数据结构
在现有库中增量扩展，不复制业务数据：

| 对象 | 用途与约束 |
|---|---|
| 新增 `sys_system` | 系统编码、名称/英文名、说明、图标、排序、状态；编码唯一且不可随意修改，首期仅支持内置系统 |
| `sys_menu.system_code` | 菜单归属；有效业务菜单必须有归属，同一菜单树分支不能跨系统；个人工作台等公共入口采用显式白名单 |
| 新增 `sys_role_system` | 角色与系统准入关联，唯一键 `(role_id, system_code)` |
| 新增 `sys_department_system` | 部门与系统准入关联，唯一键 `(dept_id, system_code)` |
| 新增 `sys_permission_revision` | 单行权限版本号；授权、角色/部门/菜单状态、归属及用户绑定变更时，在同一事务内递增 |

现有 `sys_role_menu`、`sys_department_menu` 和角色绑定继续使用。保留叶子菜单ID与 `menuKey`，减少历史授权失效；混合系统的目录节点按归属重组，不通过复制叶子菜单生成多个安全身份。

系统目录配置仅管理已实现系统的展示和启停；新增一条记录不等于自动生成一个业务系统。菜单归属变更由明确的迁移/管理操作完成，不允许普通请求任意改写。

### 6.2 接口契约
新增接口统一使用项目 `Result<T>` 包装及明确 DTO：

| 接口 | 职责 |
|---|---|
| `GET /api/portal/context` | 返回当前用户可进入的系统、有效权限版本、平台超管标记；只返回授权且启用的系统 |
| `GET /api/systems/{code}/navigation` | 校验准入后返回该系统授权菜单、可用动作及同一快照版本；不返回其他系统树 |
| `GET /api/systems`、`PUT /api/systems/{code}` | 权限中心管理系统目录，只允许已注册字段调整 |
| `GET/PUT /api/roles/{id}/systems/{code}/authorization` | 读取/原子保存单角色、单系统准入和菜单动作，不影响其他系统 |
| `GET/PUT /api/departments/{id}/systems/{code}/authorization` | 部门维度同上 |

补充约束：
- 授权管理接口受权限中心对应动作控制；读取授权配置也不是“任意已登录可读”。
- 保存携带版本号，过期编辑返回冲突并要求刷新，防止多人操作互相覆盖。
- `/auth/login`、`/auth/info` 的有效权限改用同一后端解析器；不让导航、登录响应和接口校验各自计算不同结果。
- 运行态导航与管理员配置树分离。现有 `/api/menus/tree` 在兼容期返回当前用户过滤后的树；完整管理树采用受保护的管理接口。
- 旧全量授权写接口在切换后停止接收旧格式写入，提示刷新客户端；不能把某系统提交的局部集合当作全局全量覆盖。

## 七、关键代码改造

### 7.1 前端
主要修改：
- `src/App.tsx`：公共门户布局、系统布局、系统入口、旧路径兼容，保留 HashRouter 与现有部署 base。
- `src/contexts/AuthContext.tsx`：服务端确认后建立有效访问状态；接入统一权限快照与跨标签页退出通知。
- `src/contexts/MenuContext.tsx`：按用户和系统加载导航，取消过期请求，避免快速切换时旧系统响应覆盖新系统。
- `src/components/Sidebar.tsx`、`HeaderBar.tsx`、`MenuTabs.tsx`：系统名称、切换器、系统内菜单与分系统历史。
- `src/components/MenuPermissionGuard.tsx`、`src/constants/menuDataSource.ts`、`src/pages/Permission/types.ts`：收敛路由/菜单映射，补全页面动作及动态路径校验。
- `src/pages/Permission/`：系统维度授权与来源展示；系统目录管理及账号安全入口。
- `src/pages/Home/index.tsx`：个人工作台内的收藏、快捷入口按系统和菜单授权过滤。
- 新增门户页面、通用系统工作台及系统导航状态模块；业务页面优先复用。

权限决策不再降级读取旧 localStorage 角色配置；后端返回空菜单必须保持空数组，不能解释为“加载失败，补挂全部离线菜单”。原型功能需显式登记和授权。启动校验未完成时显示加载态，不先显示受保护页面。

新页面遵循现有品牌色、全局样式和表单规范；系统配置及授权编辑采用独立页面，提交先校验再按规范确认，支持现有多语言。

### 7.2 后端
- 扩展 `PermissionServiceImpl` 与 `PermissionAspect`：从服务端菜单/资源归属确定系统准入，再校验动作。
- 新增统一有效权限解析服务，输出系统集合、菜单动作、超管标记和版本号；供认证、导航与鉴权共同调用。
- 为没有菜单注解的接口分类：业务接口、显式员工自助、已认证公共能力、现有公开接口。未分类的新业务接口默认拒绝，并由自动化测试阻止漏登记。
- 不信任客户端 `systemCode`、URL 参数或请求头作为权限证明；有权进入广告系统不能据此调用 HR 管理接口。
- 补齐服务端安全审计：系统/菜单/动作、对象、操作者、授权前后差异及拒绝原因，不记录明文 Token。

### 7.3 跨系统共享能力
必须区分“管理完整数据”和“为其他业务提供必要选择项”：
- 员工、部门、职位、门店、购买公司等选择器提供最小字段 DTO；只返回业务所需的ID、名称等字段。
- 共享选择器按已登记的调用业务权限授权，可以支持多个合法业务权限的任一组合，但每个组合都包含其系统准入；不能简单设为登录即返回全量资料。
- HR 的薪酬、证件、联系方式及账号安全信息不进入通用选择器。
- 涉及归属/数据范围的选择器继续过滤可选择对象。
- OA 任务摘要和审批操作依据 OA 权限、参与人及流程状态授权；跳转查看原业务系统完整详情仍须目标系统权限。首期不授予审批人整个业务系统的管理员权限。
- 复用原有服务调用和事务，不为了界面分系统把 JVM 内调用改成 HTTP。

### 7.4 HR 与权限中心边界
当前员工新增/编辑路径同时处理 `role`、`functionRoleIds`。改造时：
- HR 普通档案接口不再接受管理员身份或角色绑定变更；非法字段变更由后端拒绝，不能只隐藏输入框。
- 角色绑定、密码重置、强制下线等安全操作通过权限中心动作授权。
- 员工离职/停用仍可触发账号禁用和统一会话失效，但不能借人事操作提升权限；登录启用与人事在职状态分别表达。
- 对超级管理员账号的重置、绑定、停用及删除增加专项保护；普通授权管理员不能通过高权限角色的编辑/绑定绕过限制。

## 八、权限变更与统一退出

### 8.1 权限撤销
- 权限变更与版本递增同事务提交；后端授权请求读取数据库当前版本，缓存只在版本一致时复用。
- 首期采用数据库版本号，不新增 Redis。该方式也覆盖多个后端实例，避免仅清空单实例内存缓存。
- 撤权提交后，新发起的请求必须拒绝；已执行中的请求不承诺被追溯撤销。
- 前端进入系统、窗口聚焦及可见页面每 30 秒刷新权限快照；收到 403 时立即重新校验并清理失效菜单、标签和详情数据。
- 前端刷新频率只决定展示更新速度，不是后端允许继续访问的宽限期。401 进入登录流程，403 不应把仍有其他系统权限的用户整体登出。

### 8.2 统一退出
当前登出接口主要记录日志，首期补齐服务端会话撤销：
- 登出按“用户 + 当前 Token 匹配”原子撤销活跃会话，旧会话的迟到登出不得注销后续新会话。
- 活跃 Token 为空也视为会话无效，不能仅清空字段后仍接受未过期 JWT。
- 各系统切换共享同一会话，不重复调用登录，也不重新生成 Token，避免触发现有单设备互踢。
- 同源标签页通过 `storage` 事件或 `BroadcastChannel` 同步登出和账号切换；前端清理权限与页面缓存，后端独立保证失效。
- 登出接口失败时仍清理本地状态并明确提示；不把本地清理成功描述为服务端已确认撤销。

现有公开扫码/签署入口维持专属鉴权规则，单独回归，不因后台分系统新增通用匿名白名单。

## 九、迁移、发布与回退

### 阶段 A：归属与兼容清单
- 整理全部已启用菜单、业务路由、子路由、控制器接口的归属，登记共享接口和公共入口。
- 明确原型/正式功能、菜单归属冲突、缺少动作及未覆盖接口；未分类项不允许进入严格切换。
- 建立路由和接口覆盖测试，将清单作为后续新增系统的门禁。

### 阶段 B：基础能力与授权迁移
- 新增表、字段、系统目录及统一权限解析器；保留业务接口及旧前端必要读取兼容。
- 从现有角色/部门菜单授权推导对应系统准入，**只做一次性迁移**；不能每次启动重新推导，否则会把后来撤销的系统权限重新授予。
- 初始化基础员工自助角色；保留现有叶子菜单ID、动作及业务数据。
- 迁移前后对比“用户—系统—菜单—动作”结果，任何额外授权或缺失授权均列明原因并验证。
- 全部迁移登记 `backend/src/main/resources/db/migrations/catalog.json`，使用递增版本键、依赖顺序、`applyOnce(key, task, verify)`、关键表契约及后置校验；`backend/sql/` 使用实施时最大序号加一。
- 同步调整历史菜单种子逻辑，确保重启不覆盖新的系统归属或恢复已撤销授权。

### 阶段 C：门户与试点
- 实现门户、系统布局、切换器、分系统导航及权限中心授权页。
- 按账号灰度启用新入口，以“权限中心 + HR”验证管理边界，再以“OA + EAM”验证员工自助与跨域流程。
- 同期完成完整退出、权限版本更新和必要共享接口，不能把界面上线视为权限改造完成。

### 阶段 D：全量接入与严格启用
- 推广至广告、财务、商户、搜索、AI、平台配置。
- 后端安全能力先部署，前端后部署；所有实例版本及迁移就绪后统一切换严格模式。
- 强制使用新授权写接口；旧客户端授权写请求提示升级，避免误覆盖其他系统权限。
- 观察系统进入失败率、403、共享接口错误和迁移审计；最后移除不再使用的兼容逻辑。

### 回退原则
- 数据库只增量扩展，不删除原业务表和历史授权。
- 入口灰度开关只控制导航体验，不能关闭后端系统鉴权。
- 切换前准备能理解系统权限的兼容回退版本；严格上线后不能直接回退到忽略系统权限的旧后端。
- 上线前备份授权数据并演练恢复；迁移失败不接流量，沿用现有 readiness 与契约校验机制。

## 十、验收标准

### 权限与安全
1. 无系统权限：门户无入口，直达旧路径或调用业务 API 均被拒绝。
2. 仅有系统准入：只可进入空工作台，不能获取菜单业务数据。
3. 只读角色：可查看，新增/修改/删除/导出按具体动作拒绝；不能靠前端改状态绕过。
4. 同时拥有两个系统：分别展示菜单，任一系统局部授权保存不影响另一系统。
5. 多角色及部门授权合并准确；完全撤权后，其他标签页、旧链接和旧权限缓存均不能使新请求通过。
6. 普通 HR 编辑者不能修改管理员身份、角色绑定或越权重置高权限账号。
7. 不具备 HR 管理权的 OA/EAM 用户可使用必要选择器，但拿不到 HR 敏感字段。
8. 员工自助只能查看/操作本人或参与任务；同系统内更换对象ID也不能越权。
9. 系统停用、角色停用、部门变更和账号停用在各后端实例一致生效。
10. 退出后旧 Token 不可使用；旧会话退出不影响后续新会话；正常切换系统不会互踢。

### 路由与体验
- 覆盖无权限、空菜单、加载中、服务不可用、动态详情、旧收藏、通知直达、回跳、刷新及前进后退。
- 快速切换系统时，迟到响应不能覆盖当前系统导航。
- 标签页和收藏不跨账号泄漏；公共扫码/签署与 AI 使用授权继续正确工作。
- 菜单配置成功返回空数组时不补挂缓存菜单；原型路由不能成为绕过系统授权的入口。

### 自动化与工程门禁
- 前端：`npm run typecheck`、`npm run lint`、`npm run test:run`、`npm run check:menu`、`npm run build:strict`、`npm run secret-scan`。
- 后端：`mvn -f backend/pom.xml compile -q`、`mvn -f backend/pom.xml test -B`；补充系统权限、共享接口、会话撤销、迁移幂等及接口分类覆盖测试。
- 新增表和归属迁移需验证重复启动、部分迁移失败、多实例权限失效及权限差异对照。

## 十一、成本预估与后续演进

静态代码层面的粗估，待归属清单完成后校准：

| 工作 | 预计工作量 |
|---|---|
| 菜单/路由/API 归属及兼容盘点 | 3–5 人日 |
| 系统模型、授权、会话和迁移 | 7–10 人日 |
| 门户、导航、授权页面及历史入口兼容 | 6–9 人日 |
| 全模块接入、共享边界、测试与灰度修正 | 9–16 人日 |
| 合计 | 约 25–40 人日 |

假设 1 名前端、1 名后端并有测试支持，存在联调依赖，建议按 **4–6 周**安排，不是确定工期。以上不包含现有原型功能补全、业务重写、多租户、独立部署或全面重建数据权限。

### 未来真正独立部署时
只有出现独立团队发布、独立扩容、故障隔离或外部系统接入需求，再启动下一阶段：
1. 选定一个边界清楚的系统做独立部署试点，沿用当前系统编码及权限资源标识。
2. 接入企业已有 IdP 或成熟身份产品，通过 **OpenID Connect Authorization Code + PKCE** 实现 SSO；已有企业 SAML 体系通过兼容接入。
3. 每个应用注册独立客户端，校验 issuer、audience、有效期和签名；身份用稳定用户ID映射，不把用户名作为跨系统唯一身份。
4. 优先采用应用后端/BFF 管理会话与 HttpOnly Cookie；身份中心已有会话时通过跳转自动完成登录，各应用不再次要求输入密码。
5. 不通过 URL 传递长期 Token，不依赖跨域 localStorage，不把一个 JWT 无差别发给全部服务；CORS 也不等于 SSO。
6. 明确集中注销、应用会话撤销、密钥轮换、MFA、审计和故障策略。
7. 前端可独立应用直接跳转；只有确实需要统一页面组合及多团队独立发布时再引入微前端。后端及数据库按业务所有权继续渐进拆分。

**最终建议：先完成“看起来是多个系统、权限上也是多个系统”，再按真实组织和发布需求决定哪些系统需要物理独立。**
