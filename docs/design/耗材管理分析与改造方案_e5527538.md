# 耗材管理全面分析与改造方案

## 一、结论与已确认规则

当前模块具备「建档—手工入库—领用扣库存—流水—预警」的基础框架，但还不能准确回答“公司购买了多少钱、消耗了多少钱、剩余多少钱、各部门和员工分别消耗多少钱”。问题不只是缺两个字段，还涉及数据契约、成本来源、业务单据及统计口径。

按最后一次确认，采用以下规则，覆盖此前的“共用档案”选择：
- 一份耗材档案只选一个所属品牌、一个购买公司，均为必填单选，不允许共用或多选。
- 同款耗材由不同品牌或公司购买时分别建档、分别核算，不跨公司调剂库存。
- 所属品牌指「閃蜂／mFood」；现有耗材品牌指生产厂商品牌，两者独立保留。
- 成本采用移动加权平均；实际发放出库确认消耗，未使用退料冲减消耗，不另设员工日常使用登记。

核验边界：已检查前端页面、API、后端服务、库存SQL、菜单初始化和采购关联，并完成一次独立代码审查。本地浏览器显示后端不可用、仅有离线菜单，因此没有完成真实数据库及页面联调验证；未改代码、未提交业务数据、未启动或重启服务。

### 2.1 需要优先处理的现状问题

1. **分类／厂商品牌的数据源没有完全统一。** 基础选项已转向统一分类库、品牌库，耗材档案服务仍调用旧表 Mapper；统一迁移还涉及旧表删除和分类ID重映射。完成相应迁移的数据库上，非空分类／品牌档案存在保存、读取失败风险。修复应统一访问现有基础库并核对存量ID，不能靠重新建旧表掩盖问题。证据：[档案取值逻辑](file:///Users/yangjingjing/Desktop/SARY/backend/src/main/java/com/mftb/admin/service/impl/EamConsumableServiceImpl.java#L363-L418)、[统一库迁移](file:///Users/yangjingjing/Desktop/SARY/backend/src/main/java/com/mftb/admin/config/EamSchemaMigrationInitializer.java#L589-L645)。
2. **领用人的值类型不一致。** 员工选项值是工号，耗材后端需要用户数值ID；前端还以姓名包含匹配默认人，并把工号转成数字。应使用耗材专用人员选项，返回明确用户ID，展示姓名＋工号。证据：[领用人员初始化](file:///Users/yangjingjing/Desktop/SARY/src/pages/Consumable/Claim/ClaimForm.tsx#L44-L78)、[员工选项](file:///Users/yangjingjing/Desktop/SARY/src/api/employee.ts#L91-L97)。
3. **代领授权和选项权限不完整。** 自助提交可指定其他用户ID，但未落实管理员／物资人员代领限制；自助表单又依赖员工管理、仓库管理列表权限。应提供业务专用选项，不通过扩大管理权限解决。
4. **“成本”目前实际是参考价。** 入库可录入单价，但领用成本取档案参考价，库存总值也按当前参考价计算；修改参考价会改变展示的库存价值。现有数据不能直接作为实际成本账。证据：[入库处理](file:///Users/yangjingjing/Desktop/SARY/backend/src/main/java/com/mftb/admin/service/impl/EamConsumableServiceImpl.java#L203-L224)、[库存价值计算](file:///Users/yangjingjing/Desktop/SARY/backend/src/main/java/com/mftb/admin/service/impl/EamConsumableServiceImpl.java#L314-L347)、[领用成本快照](file:///Users/yangjingjing/Desktop/SARY/backend/src/main/java/com/mftb/admin/service/impl/EamConsumableClaimServiceImpl.java#L145-L176)。
5. **库存业务口径不一致。** 领用选项显示所有仓库合计可用量，实际却扣所选仓库；仓库可不选并回落到编号0。安全库存在库存列表按单仓判断，在预警／看板按全部仓库判断；补货列表与表单的建议数量也不一致。库存“最后更新人／时间”实际来自档案，不是出入库。
6. **约束和纠错不足。** 同一耗材拆多行可绕过单次限领合计；有库存或历史后仍能修改单位；部分空值清除没有显式更新策略；普通保存接口的状态、关联ID、价格等校验不足。新入库／新领用没有请求幂等，不能只依赖按钮防重复。
7. **查询和导出尚有占位行为。** 五个业务列表的导出仅提示成功，未生成文件；“我的领用”没有传递搜索关键字；独立流水页传 `txnDate`，接口定义使用起止时间；库存行流水仅加载最近200条，不能当作完整历史。证据：[档案导出](file:///Users/yangjingjing/Desktop/SARY/src/pages/Consumable/Item/ItemList.tsx#L114-L117)、[我的领用查询](file:///Users/yangjingjing/Desktop/SARY/src/pages/Consumable/Claim/ClaimList.tsx#L39-L62)、[流水日期参数](file:///Users/yangjingjing/Desktop/SARY/src/pages/Consumable/Stock/StockTxnList.tsx#L29-L73)、[流水截断](file:///Users/yangjingjing/Desktop/SARY/src/pages/Consumable/Stock/StockTxnDetail.tsx#L40-L51)。

可保留：数量型库存与资产逐件台账分离、事务内库存与流水同步、库存条件SQL、历史领用单状态锁、已有流水和领用明细快照、独立表单页面、二次确认及已有列配置机制。首次并发入库的流水连续性仍需真实MySQL验证，不能仅凭静态代码宣布通过。

## 四、目标数据流与实际业务场景

### 4.1 建档及归属

- 档案新增 `companyBrand`、`purchaseCompanyId`，两者必填单选；后端验证真实存在、启用及操作权限。
- 一旦产生任何库存业务，品牌、公司、基本单位不可直接修改；其他公司需要另建档案。
- 由于档案已固定唯一归属，现有库存唯一键 `(item_id, location_id)`可以保留；不再实施“共用SKU＋多公司库存”的复杂模型。
- 历史单据保存归属快照，不能依赖档案当前名称或员工当前部门反算历史。
- 有历史引用的档案采用停用／归档，不允许通过删除破坏查询；无业务历史才允许删除。

### 4.2 入库与采购联动

```text
耗材档案
  → 采购申请／采购执行（实际成交价、购买公司）
  → 验收合格或让步接收
  → 耗材入库单
  → 增加数量及库存成本金额
  → 入库流水和公司采购统计
```

- 共用现有「采购与供应」入口；采购明细增加资产／耗材类型判别、耗材档案ID，旧数据默认资产，原资产逐件建账行为保持不变。
- 耗材订单限定一个品牌、一个购买公司；首期不允许资产与耗材混单，也不允许跨公司耗材混单。
- 验收耗材不生成FA资产编号；只对实际接收数量入库，退货／换货待验数量不计可用库存。
- 实际成本取已确认成交金额，不取预算和参考价；价格未确认时阻止成本记账。部分到货按本次接收数量计算，不提前记整张订单金额。
- 入库明确分为采购、期初、其他来源；期初和盘盈不得计入本期采购金额。手工采购入库需实际金额、供应商及凭据，和订单验收共用记账服务。
- 请求幂等键与来源验收明细唯一约束同时保证“同一业务不重复入账”；采购接口重试和人工入口不能重复消费同一验收来源。

### 4.3 领用与发放

- 不新增OA审批。员工自助提交进入“待发放”并占用库存；仓管确认实物发放后扣减数量、结转成本，进入“已发放”。授权物资人员现场代领可一次确认完成创建和发放。
- 待发放可取消／拒绝，释放占用；不自动超时释放，待发放清单显示等待时长供管理处理。首期整单发放，不引入分批发放。
- 一张领用单只包含一个品牌、一个购买公司；后端逐行校验档案归属，不能由客户端覆盖。
- 先按耗材合并计算整单限领量，再按仓库校验可用量；缺货不得跨公司库存兜底。
- 数量、成本、单据状态、流水在同一事务完成；所有库存行按固定顺序加锁，并提供请求幂等。
- 历史 pending／approved 单保留原审批和撤销能力，并通过同一成本出库服务处理；新旧流程明确标识，不伪造历史审批。
- 个人领用记实际受益员工；部门公共领用记公共费用和经办人，不把公共耗材全部算成经办人的个人消耗。

### 4.4 异常闭环

- 未使用退料：关联原领用明细，限制累计退料量不超过已发放量，按原出库成本退回原档案／仓库，冲减原员工或部门消耗；不计作新采购。
- 误操作：未记账单可撤销；已记账不直接编辑或删除，以关联冲销／纠正记录处理。
- 盘盈盘亏：库存页面进入独立调整表单，要求原因及权限；差异计入库存调整，不伪装成员工领用。盘盈有库存时按当前均价，无成本基数时必须确认金额。
- 仓库调拨：仅同一档案、同一公司，源仓按当前成本转出，目标仓按转入金额更新均价；全事务、双向流水，不计采购或消耗。
- 采购退货：关联采购／入库来源；未入库拒收不扣库存，已入库退货仅允许可退可用量；退款采购金额和退库账面成本分别记录，价差单列，不倒改员工历史成本。

## 五、公司、部门、员工的金额核算

### 5.1 明确三个不同的金额

| 指标 | 口径 |
|---|---|
| 公司采购金额 | 已确认实际采购成交金额；同时分列已验收入库金额、未入库金额和采购退货冲减，不把下单等同于到货 |
| 公司消耗金额 | 已实际发放的成本金额－关联未使用退料金额；可下钻部门、员工和耗材 |
| 剩余库存金额 | 当前库存的账面成本，不是数量乘最新参考价 |

“采购花费”本期指已确认采购成本，不冒充银行实际付款。现金实付、应付款、发票和付款核销属于财务范围，本次不新建付款系统；界面不使用“已付款”误导。沿用当前系统单一本位币，跨币种换算不在本期。

### 5.2 移动加权平均

按“耗材档案＋仓库”独立计价，公司和品牌由档案固定归属：

```text
入库后平均成本 =（原库存金额＋本次入库成本金额）÷（原库存数量＋本次入库数量）
发放成本金额 = 发放数量 × 发放时平均成本
```

- 后端使用BigDecimal：平均单价保留6位，记账金额保留2位；一次领完剩余库存时结转全部剩余金额，避免尾差。
- 库存、领用明细、流水保存实际金额；前端不以JS浮点乘法重新生成账面金额。
- 参考单价只辅助采购估算，后续修改不得影响已有库存或历史消耗。
- 发放、退料、调整均保存数量／金额前后值、业务来源、操作人和记账时间。统计以记账时间归期，业务日期单列，不能通过回填日期重排历史均价。

示例：同公司同仓先购100包×2元，再购100包×4元，采购入库共600元、均价3元。员工甲领30包记90元，员工乙领50包记150元，库存剩120包、360元。甲退10包冲回30元，则净消耗210元、库存390元，合计仍为600元。

### 5.3 统计视图

- 公司汇总：期初库存金额、确认采购金额、已入库采购净额、未入库金额、净领用消耗、库存调整／退货价差、期末库存金额。
- 部门汇总：个人消耗合计、部门公共消耗、部门净消耗；按历史部门快照归属，调岗不移动历史费用。
- 员工汇总：姓名＋工号、领用数量、退料数量、净消耗金额，关联原单据；统计实际领用人，不是代办人。
- 耗材明细：品牌、购买公司、分类、厂商品牌、耗材／规格／单位、仓库、入库、领用、退料、结余及对应金额。
- 所有视图支持期间、品牌、购买公司筛选；部门为树筛选，父级汇总去重；员工、耗材支持搜索下拉。
- 不把包、支、盒等不同单位直接累加为“总消耗数量”。跨耗材总览优先显示金额、单据数和品类数；数量按耗材＋单位展示。
- 公共消耗单列，保证“员工个人消耗合计＋部门公共消耗＝部门消耗”；未分配部门的历史数据单列，不隐藏。
- 后端统一分页、统计及导出过滤条件；导出全部匹配记录，不限当前页、不受200条截断。列表与导出均应用相同数据权限，成本金额设置独立查看权限。

## 七、验收标准

1. 同款耗材在不同品牌／公司分别建档，相同名称不串库存、不串成本；有历史后归属和单位修改被拒绝。
2. 分类三级及更深层级正确回显；父分类／父部门筛选包含后代且无重复统计。员工ID正确，姓名同名、调岗、离职及停用字典不破坏历史。
3. 两次不同价入库、多次领用、部分退料、同公司调拨、盘盈盘亏及采购退货的数量和金额可对账；上述600元示例作为固定用例。
4. 自助提交不计消耗，确认发放才结转；取消释放占用；公共部门费用不误算为经办人个人消耗。
5. 并发首次入库、多人争抢库存、重复请求、重复验收回调和事务异常测试通过；库存不为负、流水前后连续、不重复记账。
6. 公司库存金额满足“期初＋入库金额－出库金额＝期末”；采购、消耗、退料、调拨及差异分列，不能重复计入。
7. 普通员工、仓管、财务／统计角色分别验证可见范围和操作权限；不能利用直接调用API越权代领、发放或查看无权成本。
8. 超过200条流水仍可完整分页；期间筛选、我的领用搜索、导出与报表汇总一致。
9. 原资产采购验收、分类／品牌基础库和历史耗材领用单回归通过。
10. 确认实施后执行前端 `npm run typecheck`、`npm run lint`、相关测试及 `npm run check:menu`；后端执行编译和单元测试，并在隔离MySQL环境验证真实SQL／锁／事务。服务恢复后再完成六个现有菜单和新增页面的浏览器联调验收。

本期不包含：财务实际付款核销、多币种汇兑、跨公司库存转移、批次效期／先进先出、包装单位换算、员工实际使用二次登记及独立移动端扫码。这些不影响本方案定义的办公耗材采购、发放消耗和费用归属闭环。
