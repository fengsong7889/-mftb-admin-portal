> 状态：定版（2026-11-18，阶段一 UI 已交付并确认推进，阶段二全栈实施中）
> 归属真值：`docs/system-portal/inventory.md` §1/§2（新增第 19 个业务系统 cpm）
> 前端：`src/pages/Cpm/`（主站壳）+ `frontend/packages/contracts/` 菜单登记

> 表结构真值：`backend/modules/legacy/src/main/resources/336_cpm_core.sql`（12 张 biz_cpm_*）

## 1. 需求与竞品结论

**核心场景**：以天为单位记录工作任务（已完成/进行中/待办）→ 自动汇总周/月/季报 → 跨周期长期事项多次更新进度 → 通用岗位模板 → AI 辅助整理（粘贴/录音转写）→ 上级评价与成果认定闭环。

**竞品对标**（钉钉日志 / 飞书汇报 / Tita / Worktile·PingCode / 企业微信）：

| 维度 | 行业做法 | 本系统取舍 |
|---|---|---|
| 记录 | 钉钉=模板表单填报（重）；飞书=文档化 | 一句话快捷录入 + 默认值吃掉选择成本；模板只配「词表+提示语」不配字段结构 |
| 汇总 | 自动抓取任务系统生成初稿（40min→10min） | 确定性聚合优先（数字永不经模型），AI 只做清洗/摘要 |
| 反馈 | 钉钉已读/评论/点赞；Tita=CFR 沟通-反馈-认可 | 评论(Feedback)+点赞(轻量)+成果认定(Recognition) 三层，认定进个人成果档案 |
| 绩效 | Tita 与考核一体化；Worktile 明确「工时≠绩效」 | 分层：本系统=过程层事实与反馈；HR 绩效考核持有结果层；sync_to_perf 预留二期打通 |
| 提醒 | 截止催办+未交统计标配 | 催办只提醒本人、同日去重、过期不 nag；无跨人排名视图（反内卷红线） |

**关键理念**（飞书「向下写周报」）：汇报先对本人有价值（个人工作资产沉淀 + 可追溯的成长证据），才可持续；为上级而写的汇报必然走向敷衍。

## 2. 部署位置决策（为什么是独立系统）

- 不并入 OA：OA 语义=审批流+员工自助单据，工作记录无审批语义；叶子归属规则（一棵树同属一系统）会锁死未来 OKR/绩效扩展。
- 不并入 RDM：RDM 是产研专属，运营/行政/财务无准入，违背「全岗位通用」；RDM 進度日報是管理者视角项目快照，与本系统（员工个人事实）职责互斥、保留不动。
- 不并入会议：仅复用其 AI 治理链路（场景开关/额度/急停/计量/Prompt 三层分离），业务不内聚。
- 先例：meeting 从 OA 独立（SystemCode.java 同论证）；全员可达用 `CpmAccessGrantInitializer`（会议/RDM 同法：授到所有启用角色+有效部门，只铺使用侧两张，只补空不扩权，每次启动重放自愈）。

```

├─ 使用侧（全员基线，view/edit/ai_cpm，服务层硬约束本人）

├─ 治理侧（显式授权）
│  ├─ cpm-team     團隊匯報：阅读范围=本人+主管推导+显式授权；CFR 评论/点赞/成果认定；统计卡
```

## 4. 数据模型（12 表要点）

- `biz_cpm_item`：条目事实原子；UNIQUE(user_id,source_type,source_ref) 软删感知唯一键防重复导入；work_hours 仅分布统计；version 乐观锁。
- `biz_cpm_item_update`：进度流水只追加；期末状态/轨迹唯一收敛源（改历史=重叙绩效，接口层无更新/删除入口）。
- `biz_cpm_report`：UNIQUE(user_id,period_type,period_start) 每人每期一份；发布=条件 UPDATE 翻正+快照冻结；ai_summary 披露位。
- `biz_cpm_report_read`/`comment`/`reaction`：送达统计、Feedback（一层回复）、点赞（唯一键=取消而非刷数）。
- `biz_cpm_recognition`：from≠to 由 CHECK 硬拒、同人同目标唯一；to_user_id 服务端按目标归属推导；period_tag 季度口径；sync_to_perf 预留。
- `biz_cpm_view_grant`：dept_manager 推导线（每周一重建，先删后插同事务）与 explicit 人工线分轨。
- `biz_cpm_template`/`biz_cpm_rule`：词表白名单唯一真源；规则全局单行（config_slot='default'，RDM 先例）。
- `biz_cpm_ai_extraction`：requestKey 幂等台账、payload 7 天限期清除、processing>2min 置 expired。
- `biz_cpm_push_record`：(event_type,user_id,period_start) claim 抢占幂等；dry-run 全部 skipped 留痕。

迁移键：`cpm:schema:v1.0` / `cpm:menu:v1.0` / `cpm:template-seed:v1.0` / `cpm:rule-seed:v1.0` / `cpm:access-grant:v1.0` / `ai:cpm-scene-v1.0`；初始化器 @Order 26/29/32 序（早于 PermissionAnnotationValidator@30、晚于门户底座@15）。

## 5. 核心流程（与实现一一对应）

1. **每日记录 ≤30 秒**：快捷录入回车即存（条目+首条流水同事务）；延续建议一键带入（今日已有流水则幂等跳过）；模板切换只影响词表与提示语。
2. **跨周期进度**：任意日更新进度→只追加流水；日视图=活跃投影；周报按 itemId 去重、状态取期末、轨迹保留（30%→70%）。
3. **汇报生成**：进入即呈现 `GET /reports/preview` 确定性初稿；发布重算快照再冻结（所见=所发）；事务提交后异步送达。
4. **CFR 闭环**：发布→钉钉卡片(摘要+站内链接，正文登录鉴权)→上级打开登记已读→评论/点赞→成果认定（类型+说明，认定人/被认定人服务端判定）→被认定人收通知+进个人成果档案→期末 sync_to_perf（二期 HR 取证）。
5. **AI 提取**：预检与执行同源 → requestKey 幂等 → 三层 Prompt（固定约束/可信上下文/编号原文）→ 白名单校验（分类必须命中模板词表、progress 0-100、≤30 条、sourceRefs 必须指回原文）→ 候选预览 → confirm 才落条目（source=ai）。
6. **催办**：截止日提醒窗口内扫未发布成员，push_record claim 同日去重；过期 6 小时停止 nag；只发本人。
7. **关联导入**：`GET /api/cpm/sources/rdm` 走 `contracts/rdm` 端口 `RdmWorkItemSource`（实现在 RDM 域，复用需求列表「某人视角」口径：提出/产品经理/研发负责人/验收人/未完成任务负责人五类关系 OR 命中），端口无实现时 fail-closed 返回空清单，绝不降级成 CPM 直查 `rdm_*` 表；`GET /api/cpm/sources/meeting-actions` 取未完成 ACTION，首负责人列与 `biz_meeting_minutes_item_owner` 协办线并集去重（只查缓存列会把协办人漏成"与我无关"）。前端「關聯導入」挑选器一键建条目：`imported` 只作界面提示，重复导入仍由条目唯一键 `UNIQUE(user_id,source_type,source_ref)` 单一裁决；状态/角色词表不外抄（RDM 状态渲染用 `RDM_STATUS_LABEL`，服务端只回原始码）。

## 6. 通用性 vs 易用性

结构通用（标题/状态/进度/说明四要素全岗位一致）+ 词表可换（product/dev/qa/ops/general + 自定义）；AI 按当前模板词表归类兜底；默认值吃掉选择成本；**刻意不做**：自定义字段引擎、OKR（target_id 预留）、360 评估（HR 域）。

## 7. 安全与反内卷红线

- 身份一律 JWT 服务端注入；条目/汇报读写硬约束登录人；IDOR 拒绝；认定 to_user 服务端推导 + CHECK(from≠to)。
- 分类词表=白名单校验+AI 提示词同源（脏键即注入面，templateKey/分类键限 slug 字符集）。
- AI：场景默认拒绝、急停 fail-closed、payload 限期清除、响应 no-store、AI 摘要披露；ASR 凭据只走环境变量（CPM_ASR_BASE_URL/API_KEY/MODEL），未配置录音入口置灰（fail-closed）、音频不落盘。
- 推送：dry-run 默认开（cpm.notify.dry-run=true）、幂等 claim、卡片不携带正文。
- 不提供跨员工提交率/工时排名页；统计仅治理侧聚合口径且跟随筛选。

## 9. 端到端走查发现并已修复（真实链路才暴露的那类缺陷）

| 缺陷 | 为什么单测/门禁拦不住 | 修复与回归钉 |
|---|---|---|
| 条目/汇报/规则/模板 INSERT 报 `Column 'created_by' cannot be null`（界面表现为"数据库操作异常"），快捷录入与保存在真实环境全线失败 | 实体写了 `@TableField(fill = INSERT)`，但全局 `MetaObjectHandler` 只填时间不填人；MP 于是把 `created_by` 以 NULL 拼进 INSERT，而列是 `NOT NULL DEFAULT ''`——单测用 mock Mapper 永远不会触库 | 6 张带审计列的表全部显式写 `createdBy/updatedBy`（登录人姓名快照）；`CpmWriteRulesTest.itemInsertStampsAuditColumns` 用 ArgumentCaptor 钉住"落库前必须自带审计列" |
| 定时催办扫描每次都抛 `登錄狀態失效` 后静默失败，规则页却显示正常 | 调度线程没有 SecurityContext；`CpmRuleService.read()` 里 `guard.currentUser()` 是给人用的门禁，被调度复用后无人察觉（异常只进日志，不进界面） | 拆出 `readForScheduler()`（不判登录态，权限门禁留在 Controller），`CpmScheduler` 改用；`CpmWriteRulesTest.ruleReadHasSchedulerSafePath` 钉住"HTTP 路径要登录、调度路径不得要" |
| AI 提取失败时界面显示 `整理失敗：upstream_http_error` 原始码（真实原因：模型供应商账号欠费） | cpm 自己另写了一份 `resolveUpstreamErrorCode`，把纪要已有的分类（欠费/密钥失效/模型不存在/限流/内容安全/配额耗尽）全压成 `UPSTREAM_HTTP → upstream_http_error`；mock 单测只测白名单校验，不碰真实上游错误体 | 分类上收为唯一实现 `service/agent/AiUpstreamErrorCodes`，纪要与 cpm 都委派过去；前端错误文案改走 `cpm.aiError.*` 取词（不再维护第二份字面量表，认不出的码回落通用文案而不泄露原始码）；`AiUpstreamErrorCodesTest` 钉住六类常见失败 + 状态码保留 + 不回显上游原文 |

> 结论同 `docs/HOME_REQUEST_STORM_2026-10.md` 的判读口径：对「不应该发生」型断言必须做真实链路验证；
> mock 层测试能证明逻辑分支，不能证明列约束与线程上下文。

## 10. 回滚与运维开关（§十四 落地口径）

| 开关 | 生效方式 | 关掉后的可见结果 |
|---|---|---|
| `cpm.enabled`（`CPM_ENABLED`，默认 true） | 启动期把 5 个 cpm 菜单 `status=0`，同时 `CpmAccessGuard.currentUser()` 拒绝全部 `/api/cpm/**` 读写 | 侧边栏与门户入口消失、接口整体拒绝；其它系统不受影响，无需回滚代码。刻意不做"只读降级"：留一条读口子就等于留一条写前探测面 |
| `ai_scene_config.cpm_report`（默认关） | 场景面板即时生效，无需重启 | AI 助手按钮置灰并给出原因码，粘贴/录音链路一起停；确定性聚合与汇报不受牵连 |
| `CPM_NOTIFY_DRY_RUN`（默认 true） | 即时 | 投递只登记 `skipped` 留痕，不真发钉钉 |
| `cpm.rdm-sync-enabled`（`CPM_RDM_SYNC_ENABLED`，默认 false） | 重启生效（`@Value` 注入） | 回写一句都不写 RDM，条目侧保存照常；徽标显示「系統未開啟回寫」并说明原因，开关留在条目行供运维打开后立刻可用 |
| 汇报规则 `enabled` | 规则页保存即生效 | 停催办与推送；页面生成不受影响 |

数据库回滚：12 张表只增不改既有表；停用=关菜单与系统准入（数据保留）；极端情况删版本键重放或 DROP `biz_cpm_*`（无外部依赖）。

工时（`work_hours`）行内录入：仅在模板 `workHoursEnabled=true` 时于「更新進度」弹层出现 0.5/1/2/4/8h chips，
随进度一次提交；服务端夹 0~200 且 `user_id` 进 WHERE，**不进任何评价口径**（对齐 Worktile「工时=投入分布统计」）。

## 11. 阶段三：时间维度 · 公文式阅读面 · 版本修订 · RDM 回写（2026-11-19）

阶段二把链路打通了，但有四件事没做到：时间只是条目上一个数字、汇报查看面是标签+列表而不是可读文件、发布是终态无法补录、导出只能复制 Markdown。

### 11.1 投入时段落在独立表，而不是给条目加三列

| 决策 | 理由 |
|---|---|
| 新增 `biz_cpm_time_entry`（一次投入一段，同日可多段） | 条目是跨周期事项（延续带入 = 同一条目多天写流水）。在条目上加 `start/end/duration` 只能记一次投入，第二次保存会覆盖第一次——等于把「区间事实」存成「最新快照」 |
| 时刻用 `TIME` + `crosses_midnight`，不用 `DATETIME` | 日期真值已经是 `work_date`，再塞进时间戳就有两处日期可以互相矛盾（跨夜时段尤其明显） |
| `duration_minutes` 服务端算出后**固化落库** | 允许显式覆盖（中途离开、只记得时长），但不允许查询时二次计算——否则同一行在不同查询里给出不同工时 |
| **不建** `UNIQUE(item_id, work_date)` | 与 `rdm_work_log`「同人同日唯一、当日累加」是两种语义：那边要当日合计，这边要保留每一段区间事实 |
| 单日单条目上限 20 段 | 防「一秒一段」把工时刷成噪音，不是防正常记录 |

工时口径两条铁律：**日均分母 = 有投入的天数**（`activeDays`，不是周期自然天数，否则请假一周的人被读成"日均很低"）；**精确时段与手工估算分列后再相加**（有精确时段就不回退手工值，否则同一次投入记两遍）。

聚合口径单点：分类/按日/Top N 全部由 `CpmSnapshotBuilder` 从**同一批已取回的明细行**算出，Mapper 里刻意不放 `SUM` 方法——两处 `WHERE` 迟早漂开，漂开的后果是"明细加起来 ≠ 总数"，而这种数字对不上从来不会被当成缺陷去查。

### 11.2 状态扩六值，不另立 `completion_status`

`todo/doing/done/blocked/cancelled/deferred`。第二套状态字段必然长出「進行中 + 已完成」这种自相矛盾的组合（RDM 曾为此修过「進行中 + 100%」的矛盾任务）。已取消不计入完成率分母（取消不是没做完，而是不再该做），延期仍计入（改期不等于取消，事还在）。CHECK 放宽沿用纪要域 `meeting:schema:v1.2` 的做法：DROP → 由常量单一真源拼约束 → verify **实查 `CHECK_CLAUSE`**。

> 该处踩到真实缺陷：MySQL 回传的 `CHECK_CLAUSE` 把引号转义成 `\'blocked\'`，直接 `contains("'blocked'")` 永远为假——DDL 已成功却被判"未放宽"、版本键不记录、每次启动重放。修法是 `.replace("\\", "")` 后再比对，且表名必须从 `TABLE_CONSTRAINTS` 关联取（`CHECK_CONSTRAINTS` 没有 `TABLE_NAME` 列）并要求 `ENFORCED='YES'`。

### 11.3 汇报阅读面：一份文件，不是三个面板

`CpmReportDocument` 复刻纪要正文卡的公文版式（居中宋体抬头 + 双线 rule + 身份行 + 连续编号章节 + metadata 网格），日报/我的周月报/上级查看页**共用同一组件**——理由与 `SnapshotView` 一致：两套渲染必然在某个字段上分叉，而汇报分叉的后果是「上级看到的和本人发出的不是同一件事」。样式全部走主题令牌（纪要原版那三处裸色不照抄），条形图 CSS 自绘而不用图表库：`canvas` 在 `html-to-image` 的克隆节点里会渲染成空白块。

### 11.4 版本与修订：发布不再是终态，但历史不可改

`biz_cpm_report_revision`（镜像 `biz_meeting_minutes_revision`）：每次发布冻结一版，修订产生 V(n+1)，V1 永远还在，通知绑定 `revision_id`。

- 幂等键由**内容哈希**派生：同内容 + 同说明 = 同键 = 重放，不会因连点长出 V3。
- 版本表**没有 `deleted` 列**：软删一个版本等于毁掉取证链；"当前生效哪一版"由 `biz_cpm_report.published_revision_id` 单点指向。
- 阶段二遗留的 published 记录**不追认 V1**，界面老实标「歷史發送快照（無版本記錄）」。
- 读历史版本不登记已读回执（回执说的是"收到了这一期"，翻旧账不算）。
- 导出的是冻结快照而非实时聚合，`export.docx?revisionNo=` 必须带版本。

### 11.5 RDM 进度回写：委派而不是自己 UPDATE

RDM 的进度真值在 `rdm_work_task.progress`；`rdm_requirement.progress` 被 RDM 日报明确判为"可能长期停留 0，用它算迭代进度会与执行侧甘特图矛盾"。而 `RdmDeliveryServiceImpl.updateTaskProgress` 挂着六道护栏（可见性 + 操作人 + `expectedProgress` 乐观锁 + action 白名单 + PRD 100% 只能走提交评审 + done/block 必填说明）、写审计流水、触发交付项阶段重算。CPM 自己 UPDATE `rdm_*` 等于绕过全部护栏。

因此回写下沉到 task 级，通过 `contracts/rdm` 新端口 `RdmTaskProgressSink` 委派 RDM 写入口。映射表写死：

| CPM 事件 | RDM action | 不满足时 |
|---|---|---|
| progress 1..99 | `progress` | 被 RDM 拒绝则原样回显 |
| doing 且 progress 0 | `start` | — |
| blocked → doing | `unblock` | — |
| done（100） | `done` | 缺交付说明 → `rejected`，**不降级成 99%** |
| blocked | `block` | 缺原因 → `rejected` |
| cancelled / deferred | 不回写 | `rejected`：RDM 无对应语义 |
| PRD 任务 ≥100 | 不回写 | `rejected`：只能走提交评审 |

**工时不回写**（`rdm_work_log` 同日累加，两边都写就翻倍）。总闸 `cpm.rdm-sync-enabled` 默认 false；端口缺席 fail-closed；回写失败 CPM 仍保存成功，但结果必须回显在徽标上。"重新對齊"只以 RDM 当前值刷新本地基准，**不推送本地值**（否则等于把乐观锁关掉）。

### 11.6 导出口径：docx 走服务端，PDF 走浏览器

`poi-ooxml` 5.4.1（Apache-2.0；排除 iText=AGPL，本专有仓不可用；不引 `poi-scratchpad`；只输出不自建解析外部 OOXML；`log4j-api` 经 `log4j-to-slf4j` 桥接，无 `log4j-core`）。PDF/长图沿用纪要已验证的浏览器端链路，共享层 `documentExport.ts` 由纪要与 cpm 共用同一份分页算法（复制一份等于让下一个改分页的人只改对一处）。走 blob 而不是 `window.open`：授权头只有 request 拦截器会加。

### 11.7 阶段三走查与 L2 发现并修复的缺陷

| 缺陷 | 为什么拦不住 | 修复与回归钉 |
|---|---|---|
| 并发记时 / 并发修订报 `DeadlockLoserDataAccessException` | 单测全用 mock Mapper，不触库；只有两个真事务并发才暴露 | 时段写入与版本写入都改成**先锁父行**（`SELECT … FOR UPDATE`），把锁顺序固定成「父 → 子」：`biz_cpm_time_entry.item_id` 外键会让 INSERT 给父行加 S 锁，随后的缓存 UPDATE 要升级成 X 锁，两个并发者在 S 上互等 |
| 同一说明的并发修订长出 V3/V4（幂等失效） | 加了父行锁仍不够：REPEATABLE READ 下事务读视图在**加锁之前**的第一次一致性读就固定了，排队等到对方提交后用自己的旧快照查 `request_key`，看不见 → 再插一版 | 版本侧 `findByRequestKeyForUpdate` / `maxRevisionNoForUpdate` 走当前读；`CpmConcurrencyIntegrationTest.concurrentRepublishProducesSingleNewRevision` 钉住「只能再加一版」 |
| 回写总闸关掉时徽标停在「未回寫／尚無回寫記錄」 | 服务端把原因只写在 `syncAfterProgress` 的返回值里，既没入库也没进界面；用户无法区分"还没触发""被 RDM 拒绝""运维根本没打开"，只会反复更新进度 | 界面拉 `GET /cpm/rdm-sync/status` 并显示「系統未開啟回寫」+ 原因；`Cpm.stage1.test.tsx` 新增总闸关闭用例 |
| 集成测试 `removeFixture` 清理失败，遗留版本行让下一轮版本号从 2 涨到 4、5 | `report ↔ revision` 两条外键**互相指向**成环，任何"先删哪张"的固定顺序都会撞 `Cannot delete or update a parent row`；清理静默失败后污染 `max(revision_no)`，看起来像业务缺陷 | 先把 `published_revision_id` 置空断环，再按「推送记录 → 版本行 → 汇报」删；同时修掉 `jdbc.update(sql, args, args)` 这个把 `Object[]` 当单个绑定值传进去的写法（MySQL 报 `Truncated incorrect DOUBLE value: '\xAC\xED…'`） |
| Word 导出 Content-Type 是 `application/octet-stream` | 附件模式下浏览器照样落盘，测试点不出问题 | 改回 .docx 标准 MIME：任何按 Content-Type 分派的中间层（企业网关、邮件附件预览）都不该把交付件当未知二进制 |
| `minutesExport.safeFileName` 上提共享层后兜底名从 `meeting_minutes` 变成 `document` | 纯 re-export 看不出行为变了；只有既有测试 `safeFileName('///')` 判红才暴露 | 纪要侧保留专属默认值的薄封装（算法仍共用），`MinutesExportButton.test.tsx` 继续绿 |

> `cpm` 域硬编码行数从基线 360 降到 **306**（阶段一的临时硬编码全部 t() 化，并顺带把 `CPM_STATUS_LABELS` / `CPM_PERIOD_LABELS` / `RECOGNITION_KIND_LABELS` / `CPM_SOURCE_LABELS` 改成 getter——模块级 `i18n.t()` 会在 import 时冻结语言，切语言后组件重渲染仍拿不到新词）。
