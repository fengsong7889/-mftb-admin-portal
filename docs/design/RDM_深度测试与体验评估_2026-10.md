# MFTB 产研交付系统（RDM）深度测试与体验评估方案

> **适用范围与更正（2026-10-23 复核，基线 29ed675d）**
>
> 本报告保留原始执行记录，但以下结论不能按字面当作“全链路验收通过”：
>
> 1. 结论中的“通过”混合了浏览器实测、接口实测、单测与代码核查。凡只有配置/代码证据的条目（如流转规则存在、四眼原则写在服务里），只能证明结构存在，不能证明本轮执行成功；详见 `docs/qa/rdm-2026-10/execution.md`。
> 2. 34 条流转规则的“无零入度/零出度”只说明配置图没有孤立节点，不等于从初态可达、可到终态，也不覆盖角色与业务前置条件，不能据此判定无死胡同。
> 3. 旧整需求流程（V1/V2）与 V3 分批交付必须分开：V3 受理后由交付项、测试批次、发布批次推进；旧放行服务仍保留管理员自批例外，V3 发布裁决禁止自批。
> 4. 单条需求存在 5 项阻断的放行预览，不能证明其中某一项单独生效；阻断项需独立控制变量验证。
> 5. 需求列表 120 条分页正常，不能替代 1000 条边界；历史会话的全生命周期记录也不能替代当前版本复验。
> 6. 页签切换导致未保存 PRD 丢失是真实风险；“前端按 pathname 重挂载”只能解释原因，不能作为不修的理由。本轮已补本机暂存与页签离开提醒，服务端乐观锁已完成，浏览器前进/后退仍未完成。
> 7. `scope=all` 仅排除 draft/intake_pending/intake_rejected；`executionOnly=true` 才额外排除 pool。`/api/ready` 不是就绪端点，应以 `/api/health/ready` 为准。
> 8. 周报顶部“已上線”按 `actual_release_date` 统计本期，部门“已交付”原先按当前状态快照统计存量，属于时间口径不一致，不是需求/交付项粒度差异；本轮已统一为本期上线。
> 9. 需求接口单次分页上限为 200，前端传 size=500 不能实现“一次加载 500 条”。
> 10. `src/i18n/**` 属于验证规则中的 L2 触发层，修改双语后不能声称仅需 L1。
>
> **2026-10-23 后续修复（本轮）**：服务端 PRD 乐观锁（`rdm_prd.row_version` + 保存时比对/自增）已落地并端到端验证；项目看板列可下钻到需求清单（`BoardColumn.statuses` 与列计数同源，四列实测 105/9/2/2 全部一致）；看板支持「再載入」到 200 条上限；研发工作台的「迭代排期/查看交付中需求/團隊負載」按钮改为按目标菜单权限显示。多角色矩阵已用三个 `QA-` 前缀账号实测（侧栏无越权、越权接口 403、admin 全量任务 36 条而受限角色 0 条）。新发现 `/api/menus/tree` 对任意登录用户返回全量菜单（信息暴露、非越权访问），列为本轮遗留决策。readiness 长期 DOWN 已澄清为启动期中间态（Started 日志先于 callRunners 打印，末尾校验器实测在 Started 后数分钟才跑完），非结构漂移。

| 事项 | 实测 | 说明 |
|---|---|---|

## 维度 1：流程场景与合理性验证

### 1.1 正向主流程（实测可达路径）

> 状态取值来自 `rdm_transition` 配置表（34 条流转规则），非文档推演。

`draft` →（提交）→ `intake_pending` →（准入通过）→ `pool` →（分配/认领）→ `assigned` → `evaluating` →（受理）→ `accepted` → `prd_designing` → `reviewing` →（评审通过）→ `review_passed` → `scheduled` → `designing`/`developing` →（开发完成）→ `testing` →（测试通过）→ `uat_pending` →（放行+上线）→ `released` →（验收）→ `verified` → `closed`

| # | 测试场景 | 测试步骤 | 预期结果 | 实测 |
|---|---|---|---|---|
| 1.1.1 | 免审批直入池 | 提交 `needApproval=0` 的需求 | 跳过 `intake_pending` 直接 `pool`，并发需求编号 | 通过（`draft→pool` 规则存在） |
| 1.1.2 | 需审批走 OA | 提交命中准入策略的需求 | 生成 `XQSP` 准入单，审批通过后入池 | 通过（工作台待办 `intake` 分组有计数） |
| 1.1.3 | 分配产品经理 | 需求池勾选 → 批量分配 | 进入 `assigned`，PM 收到待办 | 通过（`pool→assigned`） |
| 1.1.4 | 产品受理 | PM 点「受理」 | `evaluating→accepted`，可写 PRD | 通过 |
| 1.1.5 | PRD 评审 | 编写 PRD → 发起评审 → 通过 | `reviewing→review_passed`，PRD 冻结快照 | 通过（放行闸门读取冻结快照） |
| 1.1.6 | 排期与开发 | 排期 → 拆任务 → 填工时 | `scheduled→developing`，任务完成率进入统计 | 通过 |
| 1.1.7 | 测试与提测批次 | 发起提测 → 接收 → 录入结果 | 批次通过后 `isTestPassed(item)=true` | 通过（无有效批次恒 false） |
| 1.1.8 | 发布放行 | 放行检查 → 申请 → 裁决 → 上线 | 阻断项=0 才可申请；裁决人≠申请人 | 通过（实测见 1.3.1） |
| 1.1.9 | 验收归档 | 业务验收 → 评分 → 归档 | `released→verified→closed` | 通过 |

### 1.2 状态机完整性（死胡同验证）

对 34 条流转规则做图论检查（出边/入边）：

| 检查项 | 结果 |
|---|---|
| 无出边的状态 | **0 个**（每个状态都能继续走或退回） |
| 无入边的状态（不可达） | **0 个** |
| 终态是否真的终态 | `closed` 仍可 `reopen → developing`；`verified` 可 `closed` |
| 退回路径是否齐全 | `reviewing→prd_designing`（评审退回）、`testing→developing`（测试打回）、`uat_pending→developing`（验收不通过）、`rejected→intake_pending`（受理驳回重走审批） |

**结论：业务流转闭环，不存在"进去了出不来"的死胡同状态。** 唯一需要产品确认的是 `closed→developing` 的重新打开没有次数限制与审计标签（见 §8）。

### 1.3 异常分支场景（≥5 个，含实测）

| # | 异常场景 | 测试步骤 | 预期结果 | 实测证据 |
|---|---|---|---|---|
| 1.3.1 | **测试阶段有严重 Bug 是否允许上线** | 取 `testing` 状态需求发起放行检查 | 必须阻断；`TEST_PASSED` 检查项失败，且存在 Major/Critical 未关闭问题时 `isTestPassed=false` | ✅ 需求 15（`testing`）放行检查：`releasable=false`、`blockingCount=5`，其中 `TEST_PASSED` 原因「測試中」；`RdmTestBatchService.isTestPassed` 明确「无有效批次 → 恒 false」，并额外统计 Critical/Major 未关闭问题 |
| 1.3.2 | PRD 评审不通过如何退回 | 评审节点选择「驳回」 | 回到 `prd_designing`，保留评审意见，不丢失已写内容 | ✅ 规则 `reviewing→prd_designing` 存在；前端动作由 `allowedActions` 下发，无动作时不渲染按钮 |
| 1.3.3 | 开发阶段需求变更 | 提变更单 | 生成变更记录；未裁决变更**阻断放行** | ✅ 放行检查项 `NO_OPEN_CHANGE`；实测该需求此项 `passed=true`（无未裁决变更） |
| 1.3.4 | 验收不通过 | 业务验收选择「不通过」 | 回到 `developing` 返工，已发放行单作废 | ✅ 规则 `uat_pending→developing`；`RdmReleaseServiceImpl` 注释与实现均声明「返工后放行单作废」 |
| 1.3.5 | 抢单并发 | 两人同时认领同一需求 | 仅一人成功，另一人得到明确失败提示，不出现双受理人 | ✅ 认领走服务端条件更新（`claim`），前端二次确认；`RdmAccessGuard` 收敛受理权 |
| 1.3.6 | 自己给自己放行 | 发起人尝试裁决自己的放行单 | 拒绝 | ✅ `RdmReleaseGateService`：「四眼原則：發布裁決人不能是申請人本人（系統管理員亦不得自批）」 |
| 1.3.7 | 放行后证据变化 | 裁决后再改测试/验收/构建映射，执行发布 | 拒绝并提示重新申请 | ✅ 「證據已變化（範圍/測試/驗收/缺陷/構建映射任一變動）」；证据哈希不一致即失效 |
| 1.3.8 | 放行单过期 | 裁决超过有效期的批次执行发布 | 拒绝 | ✅ 「放行裁決已於 X 過期」 |
| 1.3.9 | 重复发起放行 | 已有待裁决放行单时再次申请 | 拒绝并提示先处理 | ✅ 「已有待裁決的放行單，請先處理」 |
| 1.3.10 | 空数据/无相关批次 | 测试角色进入工作台 | 显示自定义空态，不报错、不空白 | ⚠️ 见 §5.2（已修 2 处默认「無此資料」） |

### 1.4 流程合理性观察（数据侧）

- 全量 120 条需求中 **`evaluating` 占 101 条（84%）**，最早一条自 2026-10-06 起滞留 17 天。
  → 流程配置没问题，但**受理环节缺少"超时自动升级/批量受理"的实际执行**，SLA 只在配置页存在，工作台看不到「受理超时」的独立信号。
- 看板渠道口径：`待分配/受理` 列 105 条，而 `scope=pool` 只有 1 条 —— 列口径把 `assigned/evaluating` 都算进了「受理」，与左侧视图栏「待分配」不是同一口径（见 §8 建议）。

### 2.2 按钮布局与语义

| 检查项 | 规范要求 | 实测 | 结论 |
|---|---|---|---|
| 主次分明 | 查询/新增=主色实心；重置/取消=描边灰；导出=绿描边；导入=蓝描边 | 需求清单「查詢 + 提需求」、测试工作台「查詢 + 發起提測」并列两个主色按钮 | ⚠️ 同一操作区出现两个主色按钮，视觉无法判断主操作；属规范允许的「查询+新增」组合，但建议新增按钮统一带 `+` 图标区分（当前部分有、部分无） |

### 2.3 已修复的按钮/操作缺陷

1. **项目总览失败态「查詢/重置」失联**：改为强制刷新令牌，条件未变也重取。
2. **项目总览「重試」只重列表**：与查询共用同一令牌，统计卡同步重取。
3. **工作台「刷新」整页闪白**：拆分首屏 `loading` 与刷新 `refreshing`，刷新只让按钮转圈。

## 维度 3：UI 设计规范验证

### 3.1 规范摘录（AGENTS.md / `.qoder/rules/frontend-ui-design-spec.md`，强制）

> 以下为与本模块直接相关的强制条款原文摘录（编号沿用规范章节）。

**A. 设计令牌**
- 主品牌色 `#E8720C`（主按钮/选中态/菜单高亮/链接/Tab 激活）；hover `#F59432`；成功/导出 `#52C41A`；信息/导入 `#1890FF`；警告/参数 `#FA8C16`；高级 `#722ED1`；危险 `#FF4D4F`；边框 `#D9D9D9/#f0f0f0/#e8eaed`；文本 `#262626/#595959/#8C8C8C`。
- 卡片：表单/详情页圆角 8–12px，阴影 `0 2px 8px rgba(0,0,0,0.04~0.06)`；页面内边距 `20px 24px`；卡片间距 16px；按钮间距 8px。
- 字号：页面标题 18/700；模块标题 15/600；表单标签 13–14；说明 12/400。

**B.1 按钮语义**：查询/新增=主色实心；重置/取消=灰描边（hover 变橙）；导出=绿描边 `.btn-export`；导入=蓝描边 `.btn-import`；删除/驳回=`danger`；表格内=链接橙色；操作列分隔符 `.action-split`。

**B.3 Modal 二次确认**：所有"提交申请"类必须 `Modal.confirm` + `className: 'custom-confirm-modal'` + `.confirm-icon-wrapper`；顺序必须是「校验 → 弹框 → API」。

**B.7 统计卡片**：图标 20px → 数值 22/700 → 标签 12/#8C8C8C；圆角 12、padding 16；hover `translateY(-4px)` + 阴影；计数动画 1200ms；**布局 `repeat(4, 1fr)`**。

**B.9 操作列**：禁止图标；`Space split`+`|`；`type="link"` `size="small"`；顺序 详情→编辑→其他→删除。

**C. 表单页**：橙色渐变顶条（3px，`headerGradientShift`）+ 圆角 12 白卡片 + 橙色实心返回钮 + `#1890ff` 标题；模块用白色 div 卡片（禁 antd Card 彩色标题头）；`Form layout="vertical"`；底部 `.form-footer`（取消 + 保存/提交）；**头部右侧禁止放保存按钮**。

**D. 详情页**：必须 `DetailPageHeader` 组件；内容卡片 `.detail-card`；底部「最后更新人/时间」收尾；禁顶部操作按钮。

**E.1/E.2/E.8 列表页**：搜索区 4 列 grid（`.search-section`）→ **统计卡片（必须在搜索区下方）** → 操作区（`.action-section`，左导出/批量、右新增/列配置）→ 表格。

## 6. 产品易用性吐槽与优化建议（真实角色视角）

### 6.1 PM / 产品经理

1. **「受理」环节是隐形黑洞**：101 条需求卡在 `evaluating`，工作台没有任何「受理超时」信号，只有看板上一个 105 的大数字。建议：工作台加「受理超时」红卡，或需求池按「停留天数」默认倒序。
2. **看板列名与视图栏不是一套口径**：列头「待分配/受理 105」与左侧「待分配 1」并存，用户会怀疑数据错了。建议列名改成「待分配 + 受理中」，或点列时带上状态集合筛选。
3. **流水线卡片承诺了做不到的事**：原文案「點列可進入對應視角處理」，点了只是打开无筛选列表。已先把文案改成「點擊進入需求清單查看明細」；正确做法是支持 `statuses` 多值下钻。
4. **个性化配置勾选后条目会重排序**：取消某项后该项沉到末尾，连续操作容易误关其它区块。建议配置面板顺序固定，只切换显隐。

### 6.2 研发工程师

1. **任务与需求两套入口**：「新增任務」在研发交付页，「排期甘特」在需求详情，任务进度又能在甘特里直改。建议在需求详情固定一个「研发执行」区块，把任务/甘特/工时收在一处。
2. **工时填报入口不显眼**：放行闸门会卡「實際工時已填報」，但列表页没有任何「待填工时」提示，往往到放行时才发现。建议在任务列表加「未填工时」筛选/角标。
3. **测试工作台首屏看不到状态**（已修列序）：窄屏笔记本上是高频痛点。

### 6.3 测试工程师

1. **「我的測試批次」只在工作台**，测试工作台本页没有同口径分区，两个页面各看一半。建议测试工作台顶部直接复用该面板。
2. **批次号被截断且无 tooltip**：120px 列宽 + 无 `ellipsis/title`，批次号看不全也复制不了。建议加复制按钮或悬浮全文。
3. **「退回」与「詳情」距离近、均为链接色**：危险操作与普通操作视觉权重一致。建议「退回」用 `danger` 且加二次确认（当前已有确认，但颜色未区分）。

### 6.4 管理层 / 交付负责人

1. **看板 8 个 KPI 挤一行**（已修 4 列）：此前 `1.7 h`、`0.3 天` 会换行，`需求駁回率` 折 3 行，扫视效率极低。
2. **效能评分卡数值被裁切**（已修）：`214.8` 只露出半个数字，是最伤可信度的一类缺陷。
3. **「導出週報」在窄屏被裁掉**（已修）：最高频的汇报动作反而点不到。
4. **周报口径自相矛盾**：「已上線 1」与「部門產出已交付合計 4」并存，需要业务方确认口径（本期 vs 累计），否则汇报时无法自圆其说。

### 6.5 通用

- **RDM 全模块文案仍为硬编码繁体**，未走 i18n；切英文后本模块仍是中文（历史欠债，本次未动以免与"高效开发模式"冲突）。
- **空态文案两套风格**（「暫無任務數據」vs「無此資料」），本次修了 2 处，其余建议统一。
- **表格关键列默认在屏外**是 RDM 列表的通病（列多 + 侧栏 + 视图栏）。根本解法是列配置默认只开 6–7 列，其余默认隐藏。
