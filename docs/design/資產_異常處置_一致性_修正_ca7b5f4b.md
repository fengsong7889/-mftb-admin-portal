# 資產異常處置一致性修正方案

## 範圍與前提
- 本方案待使用者確認後才實施；目前僅完成程式碼分析，未核實線上部署版本或資料庫實際記錄。
- 保留各異常菜單的直接登記入口，不強制所有操作繞行普通歸還。
- 不新增報廢審批流程；報廢維持登記即生效。
- 採用「送修代表實物已交接、維修完成後回庫閒置」口徑。直接送修須補充接收部門、接收位置及交接確認；不支援本輪範圍外的原使用人原地維修模式。
- 賠付登記、定責、免賠、收款及退款均不得直接變更資產持有關係或實物狀態。
- 不將直接報失、直接報廢或直接送修偽裝成普通歸還；由來源關聯及異常終止事件保留完整鏈條。真正透過歸還驗收辦理的記錄仍保留歸還單。

## 已核實的修正依據
- `EamLossServiceImpl.create` 只關閉有效領用，沒有處理有效借用；領用寫入 `loss_closed`，但前端缺少對應標籤。
- `EamReturnServiceImpl.register` 在損壞歸還時將來源記錄置為 `returned`，未解除資產持有關係，也未建立賠付記錄，與頁面提示不符。
- `EamScrapServiceImpl.create` 與 `EamRepairServiceImpl.create/finish` 主要修改資產狀態，未同步結束來源領用／借用。
- `EamReturnServiceImpl.dispose` 的閒置分支使用 `updateById` 清空持有人，受預設非空更新策略影響；且處置時就將歸還單結案，未等待維修或賠付完成。
- 直接賠付使用當前台帳持有人作快照，未可靠追溯已解除持有的歸還／遺失來源。
- 遺失登記與歸還／調撥鎖順序不同；報廢、維修缺少鎖內狀態校驗及完整防重。

## 統一狀態規則
| 操作 | 資產結果 | 來源領用／借用 | 歸還及責任記錄 |
|---|---|---|---|
| 直接報失 | `lost`，清持有人與活躍領用 | 有效來源轉 `loss_closed` | 建遺失單、來源終止事件；不建普通歸還單 |
| 正常歸還 | `idle`，清持有人與活躍領用 | `returned`，關聯歸還單 | 歸還單 `completed` |
| 損壞歸還 | 新增 `pending_disposal`，清持有人與活躍領用 | `returned`，關聯歸還單 | 歸還單待處置；自動建 `pending` 待定責單，不預設員工有責 |
| 歸還標註遺失 | `lost`，清持有人與活躍領用 | 保留現有 `returned` 語義及歸還單關聯 | 自動建遺失單與待定責單，明確標註未收回實物 |
| 直接報廢 | `scrapped`，清持有人與活躍領用 | 有效來源轉 `scrap_closed` | 建即時生效報廢單與終止事件；不自動認定賠償責任 |
| 直接送修並確認交接 | `in_repair`，清持有人與活躍領用 | 有效來源轉 `repair_closed` | 建維修單、交接快照與終止事件；責任另行登記 |
| 歸還處置送修 | `in_repair`，保持無員工持有 | 來源已 `returned`，不重複終止 | 維修單關聯歸還单，未修完前不結案 |
| 完成維修 | `idle`，持有人及活躍領用均為空 | 不恢復舊來源 | 維修單 `done`，再次使用必須新領用／借用 |
| 找回驗收正常 | `idle`，無員工持有 | 不恢復舊來源 | 遺失單 `recovered`，依賠付情況觸發復核 |
| 找回驗收損壞 | `in_repair`，無員工持有 | 不恢復舊來源 | 同事務建立維修單，不僅修改資產狀態 |
| 遺失核銷 | `written_off`，無員工持有 | 不恢復舊來源 | 遺失及關聯歸還同步；與實物報廢明確區分 |

- 解除持有時顯式清空 `current_holder_id`、`user_name`、`active_claim_id` 及當前 `usage_date`；歷史日期與責任人留在来源單據及事件快照。
- 不把 `department` 一律清空：有實物交接時更新為經校驗的接收部門；遺失時保留資產管理歸屬，原使用部門另存快照。
- `holdType` 不作有效借用的唯一依據；有效來源以鎖內查得的領用／借用及持有人一致性為準，避免現有借用登記未寫該欄位導致歸還被拒。
- 同一資產存在多條有效來源、來源與持有人不符時拒絕操作並要求核對，不猜測應關閉哪一條。

## 後端共同持有關係服務
- 新增 `EamAssetLifecycleService`，集中實作來源解析、鎖定、狀態轉移、持有人顯式清空及終止事件；內部寫入方法要求加入呼叫方事務。
- 所有涉及本方案的流程採用相同鎖順序：先查來源識別資訊，依固定順序鎖來源領用／借用，再鎖資產，再鎖關聯歸還／異常單；取得鎖後重新核對關聯及狀態。
- 同步接入既有歸還、調撥、簽署及取消入口，禁止 `loss_closed`／`scrap_closed`／`repair_closed` 被取消或重新簽署復活；保留原簽名證據。
- 沿用資產 `holdVersion` 的資料庫端遞增表達式；新增入口以版本條件更新並檢查影響行數，不使用舊物件覆蓋整筆台帳。
- 直接報廢只接受 `idle`／`in_use`／`pending_disposal`；維修中的資產報廢須由該維修單的報廢處置入口原子關閉維修後執行。遺失、已核銷等狀態不得用直接報廢覆蓋。
- 直接維修只接受 `idle`／`in_use`／`pending_disposal`，同一資產最多一條有效 `repairing` 記錄；已報廢、遺失、已核銷一律拒絕。
- 維修完成須鎖定並確認本維修仍擁有資產處置權；歷史多條維修需核對，不能完成其中一條就釋放整件資產。
- 報廢刪除與維修刪除沿用現有可操作範圍，但釋放資產前必須核對後續事件及版本；有後續業務時拒絕。符合恢復條件時回 `idle` 並顯式清空相關欄位，不復活舊領用。

## 來源追溯及資料結構
- 領用與借用增加 `closed_at`、`close_type`、`close_biz_id`、`close_reason`，其中 `close_type` 為 `loss`／`scrap`／`repair`，來源終態分別使用 `loss_closed`／`scrap_closed`／`repair_closed`。
- 新增 `biz_eam_asset_state_event` 保存資產 ID、業務類型／ID、來源類型／ID、前後資產狀態、前後持有人與部門快照、操作人、業務日期及記錄時間。
- 直接入口增加 `requestKey`，在事件上以操作人與請求鍵建立唯一約束；保存請求摘要，同鍵同參回傳原結果，同鍵異參拒絕。
- 報廢、維修單保存原持有人及來源快照，詳情可直接追溯到原領用／借用；不依賴目前資產表推導歷史責任人。
- 關聯賠付時驗證歸還單／遺失單存在且屬於相同資產；原持有人優先取事件來源快照，其次歸還／遺失快照，僅無來源的直接登記使用當前台帳快照。
- 有來源的同一異常事件僅保留一張有效賠付單，重複申請回傳既有單號；無來源的直接賠付按请求鍵防重，不限制同一資產歷史上不同事件的賠付。
- 本輪不刪除歷史業務記錄。所有新增欄位與表按 MySQL 8 規範檢查存在性後建立，透過新的 `applyOnce` 版本註冊；序號使用實施時的下一可用值。

## 歸還結案與責任流程
- 由後端統一計算異常歸還是否結案：實物處置完成，且相關責任流程已完成、無待復核／待退款時，才為 `exception_closed`。
- `apply_repair` 僅表示已轉维修，維修單仍 `repairing` 時保持 `exception_pending`。
- 損壞／遺失歸還自動建立待定責單；不需賠償透過有原因的免賠操作結束，不把金額初始為零解讀成已免賠。
- 賠付及維修的後續操作，在同一事務內重新計算關聯歸還狀態；直接遺失單沒有歸還來源時不補造歸還資料。
- 找回後已付款的遺失賠付也需復核，由復核金額決定是否退款；不再因 `paid` 而直接跳過。
- 退款後以應賠額與淨收款重新計算狀態，避免只根據「是否退到零」判斷；復核至零且無淨收款時為免賠結清。
- 關聯建立或同步失敗拋出例外回滾，修正「主單成功但子單失敗」的誤導錯誤文案；不以 catch 紀錄日誌代替一致性保證。

## 前端與資料口徑
- 領用／借用增加「異常終止」查詢與歷史展示，區分遺失、報廢及送修，保留來源單號與責任快照；不把這些記錄放入普通已歸還頁籤。
- 台帳、員工資產數量、交接候選使用同一有效持有判斷：來源仍有效、資產狀態及持有人一致。異常資料顯示核對提示，不靠隱藏姓名掩蓋。
- 新增 `pending_disposal` 的後端允許值、API 型別、台帳頁籤、徽標及多語言文案；不可領用、借用或調撥。
- 更新歸還表單提示，使其準確反映自動建立待定責單及實物待處置流程；維修詳情跳轉使用 `repairId` 而非 `assetId`。
- `returnPreview.ts` 保持演示用途，不參與真實業務判斷；測試與正式 API 契約明確分離。
- 新增／修改表單遵循 `form-page-style.md`、獨立頁面、繁體中文及統一二次確認規範；員工显示姓名與工號。

## 歷史資料與錯誤索引的獨立處理
- 先進行只讀核對：非在用資產仍有持有人、來源已歸還但台帳仍佔用、遺失借用未結束、閒置資產掛著活躍領用、重複維修及賠付關聯錯配。
- 根據明確來源證據產生修復候選及前後值清單，歧義資料只標記，不自動更改；資料修復需使用者另行確認，不包含在程式發布的啟動遷移內。
- 現有 `uk_asset_open(asset_id,status)` 不能表達「同資產只有一張未結遺失單」，且阻擋同資產多次以相同終態結束。
- 先只讀核實實際索引與重複資料，產出獨立索引變更腳本草案：以有效未結記錄的資產 ID 作可空生成欄位及唯一索引，已結案記錄生成 NULL。替換舊索引涉及既有結構調整，單獨取得確認後執行；不重用舊遷移中的刪除重複記錄做法。
- 在索引調整完成前，所有遺失寫入仍必須在同一資產行鎖內校驗開單唯一性；多次遺失的資料庫限制列為已知剩餘阻塞，不宣稱完全解決。

## 驗收測試
- 覆蓋來源為領用、借用、無持有人三類，分別測試直接報失、直接報廢、直接送修及歸還異常路徑。
- 驗證所有終止路徑的資料庫實際 NULL 值；不能僅驗證 Java 物件 setNull 後的記憶體值。
- 驗證維修完成後可重新領用／借用，且舊來源不能再次歸還、取消或補簽復活。
- 驗證待處置不結案、維修未完成不結案、待定責不結案、付款／免賠／復核／退款後的最終結案。
- 驗證故障注入下單據、來源狀態、持有關係、事件及關聯回寫全部回滾。
- 在隔離 MySQL 8 測試庫做雙事務測試：報失對歸還／調撥、報廢對送修、重複維修、重複賠付及重複完成操作。
- 索引變更獨立驗證同資產多次遺失再找回、不同未結狀態互斥及歷史記錄完整保留。
- 前端執行 `npm run typecheck`、`npm run lint` 及相關 Vitest 測試；後端執行 `mvn compile -q`、`mvn test -B`。
- 本次分析階段不啟動服務、不操作資料庫、不提交或部署程式。
