## 二、目标与非目标

### 目标
1. 用户可在顶栏一键切换 **淺色 / 深色 / 跟隨系統**，偏好持久化，刷新与跨子系统（eam/hr/rdm）一致。
2. 首屏无白闪（FOUC），4 个入口行为一致。
3. 壳层（侧边栏 / 顶栏 / 内容区 / 搜索区 / 操作区 / 表格 / 表单 / 弹窗 / 统计卡）在深色下完整可用、层次清晰。
4. 存量色值按批次收敛到语义令牌，未令牌化数量由 baseline 门禁钉住**只降不升**。
5. 深色下正文对比度 ≥ 4.5:1、大字/图标/边框 ≥ 3:1（WCAG AA）。

### 非目标（本次不做）
- 不做多品牌换肤（主题色仍固定品牌橙 `#E8720C`，不开放用户自定义主色）。
- 不做高对比度模式（仅 light/dark 两档；如需 `high-contrast` 令牌层已预留扩展位）。
- 不做后端用户偏好存储（多端同步留待后续，接口设计见 §十三）。
- 不改 `@media` 响应式断点策略（仍靠 Flex/Grid 自适应，仅新增 `prefers-color-scheme` 与 `print` 两类媒体查询）。

## 三、总体架构

```
                     ┌─────────────────────────────────────────┐
   首屏（React 前）   │ vite 插件 transformIndexHtml 注入内联脚本 │ → <html data-theme="dark|light">
                     └─────────────────────────────────────────┘
                                        │
   状态层            ThemeProvider (packages/ui/src/theme)  ── preference: 'light'|'dark'|'system'
                                        │                    └─ localStorage['app_theme']
                                        │                    └─ matchMedia('(prefers-color-scheme: dark)')
                     ┌──────────────────┴──────────────────┐
   呈现层            │                                     │
        CSS 令牌层 theme.css                      antd 令牌层 themeTokens.ts
        :root { --text-1:#262626 }                { light:{...}, dark:{...} }
        html[data-theme=dark]{ --text-1:#E8E8E8 }          │
                     │                            ConfigProvider theme={{ cssVar:true,
                     │                              algorithm: dark?darkAlgorithm:defaultAlgorithm,
                     │                              token: TOKENS[theme], components: COMPONENTS[theme] }}
                     └──────────┬───────────────────────────┘
                                │ 双源一致性由 themeTokens.test.ts 钉住
   入口层            ThemeControls.tsx（HeaderBar `.header-right` + PortalTopBar 双处复用，
                     照 PortalLocaleControls 的既有模式）
   事件层            THEME_CHANGED_EVENT（照 TRANSLATION_BUNDLE_EVENT 惯例）
                     → 供 charts / leaflet 等非 CSS 渲染面重绘
```

## 四、令牌体系定版

### 4.1 分层原则

| 层 | 命名 | 谁可用 | 说明 |
|---|---|---|---|
| 原始色阶 primitive | `--gray-1..13` / `--orange-1..10` | **仅 theme.css 内部** | 与 antd 色阶对齐，业务代码禁止直接引用 |
| 语义 semantic | `--surface-*` / `--text-*` / `--border-*` / `--brand*` / `--success*` / `--info*` / `--warning*` / `--danger*` / `--purple*` / `--shadow-*` | 业务代码**只用这层** | 一个语义 = 一个用途，不表达具体颜色 |
| 组件 component | `--sidebar-bg` / `--sidebar-item-*` / `--stat-card-*` | 组件自有 CSS | 仅在壳层组件需要与语义层不同的取值时使用 |

**硬约束**：业务代码（CSS 与 JSX）只允许引用语义层与组件层；出现 `var(--gray-7)` 一律判违规（门禁扫描）。

##### 补充阶令牌（2026-11-05 新增，为了拆掉两个反复出现的「半对」）

这三个不是新语义，而是 antd 调色板上**真实存在、与现有令牌差 1~15 个单位的邻阶**。
为何不直接收敛到现有令牌：收敛会改变浅色观感，而「浅色侧逐像素不变」是本方案 §15.2 第 5 条定下的硬约束
（当时正是为了不接 **1 个单位**的偏差，才把 `#FFF7ED` 从 `--brand-soft` 踢回人工清单）。

| 令牌 | 浅色值 | 深色值 | 存量为何不能并给现有令牌 | 实测对比度 |
|---|---|---|---|---|
| `--danger-callout` | `#FFF2F0` | `rgba(255,77,79,0.16)` | antd v4 error-1，与 `--danger-soft`(#FFF1F0) 差 1 个单位 | 浅色 `danger` 上 **2.99**（存量债务，只守不变差）；深色 `#FF7875` on 合成底 #432627 = **5.30** ✓ |
| `--warning-deep` | `#D46B08` | `#FFA940` | antd orange-7 前景；原列 REVIEW_REQUIRED（建议收敛到 `#FA8C16`），但全站 46 处均作前景、语义单一，收敛会连带改掉 46 处浅色观感 | 浅色 on `--warning-soft` = **3.34**（低于正文 AA，属存量债务，单测按 3.3 卡下限）；深色 #FFA940 on 合成底 #42301E = **6.58** ✓ |
| `--info-hover-tint` | `#F0F5FF` | `rgba(24,144,255,0.16)` | antd geekblue-1；与 `--info-soft`(#E6F7FF) 差 8~15 个单位，一个是淡蓝一个是青蓝，不是同一阶 | 浅色 `--text-2` 上 **6.41** ✓；深色合成到侧栏底 #262626 得 #243749，`--text-2` 上 **5.64** ✓ |

三条都已进 `COLOR_TO_TOKEN`（前两条进 bg 段、`warning-deep` 只进 fg 段），所以后续批次会自动成对。
`--warning-deep` **不进 bg/border 段**，避免把同色值的背景用法误映射成文字令牌。
单测侧已补「合成对比度」一组断言（rgba 要先合成到卡片底再算，`contrastRatio` 不处理 alpha），
并把「深色必须 rgba」的后缀从 `-soft` 拓宽到 `-soft|-tint|-callout`——
否则新令牌会静默逃过这条规则（只靠命名后缀识别叠加型底色本身就是个近似）。

##### 语义色描边阶令牌（2026-11-05 第二轮：`danger/warning/success/info/purple-border`）

这批不是「另一阶邻色」，而是一族新语义：**描边位**。存量里大量淡彩实色出现在
`border: '1px solid #FFD591'` / `borderColor: '#FFCCC7'` 这类位置上，它们既不能并给同族的
`*-soft`（那是背景），也不能并给中性 `border-*`（那是灰度）。

| 令牌 | 浅色值 | 深色值 | 取值依据（只统计 border 段属性位） | 实测可见性（浅 / 深最差） |
|---|---|---|---|---|
| `--danger-border` | `#FFCCC7` | `rgba(255,120,117,0.32)` | 描边位 35 处 > `#FFA39E` 10 处 | 1.4272 / 1.7514 |
| `--warning-border` | `#FFD591` | `rgba(250,160,61,0.32)` | 描边位 63 处 > `#FFE7BA` 29 处 > `#FFD8A8` 4 处 | 1.3835 / 1.9546 |
| `--success-border` | `#B7EB8F` | `rgba(106,190,57,0.32)` | 描边位 32 处 > `#D9F7BE` 18 处 | 1.3731 / 1.8651 |
| `--info-border` | `#91D5FF` | `rgba(64,169,255,0.32)` | 描边位 14 处 > `#ADC6FF` 7 处 | 1.5951 / 1.7843 |
| `--purple-border` | `#D3ADF7` | `rgba(163,113,231,0.32)` | 描边位 17 处 > `#E8D5F5` 4 处 | 1.8935 / 1.5833 |

四条必须记住的口径：

1. **深色统一用「该族深色主色 + 32% alpha」**，与存量 `brand-border` 一致，不逐族拍脑袋。
2. **可见数字是回归守卫，不是 WCAG 达标声明**。描边本身就是 antd 预设的 1.2~1.9 细线，
   拿 3.0/4.5 卡它是假命题；断言下限取观测值（浅 ≥ 1.15、深 ≥ 1.55，存量 `brand-border` 1.1930/1.6212 也在范围内）。
3. **按段映射本身就是防误伤守卫**：五个值只进 `COLOR_TO_TOKEN.border`，所以同色值的背景用法
   （实测 `#FFCCC7` 1 处、`#FFD591` 1 处 bg）不会被换——仓内 `brand-border`（也有 2 处 bg）已是先例。
   所以「该色值全站存在多种角色」不自动否决描边令牌，**只要它只进描边段**。
4. **少数档不收敛也不建第二个令牌**（收敛会动浅色）：按 border 段属性位统计共 **51 处**
   （`#D9F7BE` 17、`#FFE7BA` 16、`#FFA39E` 6、`#ADC6FF` 5、`#E8D5F5` 4、`#FFD8A8` 3）；
   若按这些色值的**全站用量**则是 68 处（差额是非描边角色，不在本族范围内）。
   geekblue 四件套（`#D6E4FF` 52 处描边 + 前景 `#2F54EB`）已在下面「geekblue 四件套补齐」一节定掉。

后缀规则同步拓宽到 `-soft|-tint|-callout|-border`（不会误伤 `border-1/2/3`/`border-input`，它们不以
`-border` 结尾）。断言还新增一条由变异验证发现的缺口：**rgba 必须是含 alpha 的四元**——
`rgba(64,169,)` 这种写错形态会被合成函数静默当成不透明，颜色全错但不报错。

**两个自己犯的错，都是工具抓出来的（记下来是因为它们都属于“错得很静默”那一类）**：

1. **差点新建 `--warning-callout`（#FFF7E6），而它就是 `--warning-soft` 的浅色值**。
   我在 bg 段里加了个与既有键重复的键——对象字面量不报错，**后者静默覆盖前者**，
   而且两条严格等值断言都照样绿（两个令牌的浅色值都与键相等）。它先被 lint 的
   `no-dupe-keys` 报出，现在多了两条永久守卫：「每段 hex 键必须唯一（读源码文本）」与
   「同值不得映到两个令牌」（查归一后的隐式重复，如 `#fff` 与 `#ffffff`）。教训：**建令牌前先查该色值是否已被既有令牌占居**，
   不能只查“语义对不对”。站内那 66 处 `#FFF7E6` 没被令牌化不是缺令牌，而是它们在未跑目录里或写在渐变串内。
2. **变异 harness 不能并发跑**：本因输出被吞又起了一个，第二个 harness 的 pristine 快照抓到
   第一个的变异中状态，它的“还原”反而把污染固化（`#FFF7E6` 变成 `#FFFBE6`）。“还原后逐字节一致”
   只保证回到快照，**防不住快照本身是脏的**；实际抓出它的是对照组（1 failed）。现在 harness
   加了锁文件与「还原后与备份一致」双校，且不再拿「变异文本是否残留」做判据（那个启发式会误报：
   插入的行与合法原文一字不差）。

这三处都只入必要段（deep 类只进 fg、描边类只进 border），并有断言反向卡住不得漏进背景段。

### 4.3 深色取值五条规则（评审口径，后续新增令牌一律照此推导）

1. **不用纯黑**：底色三阶取 `#141414` / `#1F1F1F` / `#262626`（对齐 antd `darkAlgorithm` 的 `colorBgLayout` / `colorBgContainer` / `colorBgElevated`），避免 OLED 纯黑与灰字之间出现「光晕拖影」。
2. **语义色提亮一档**：`#FF4D4F→#FF7875`(6.43:1)、`#52C41A→#6ABE39`(7.09:1)、`#1890FF→#40A9FF`(6.54:1)、
   `#FA8C16→#FAA03D`(7.98:1)、`#722ED1→#A371E7`(4.77:1)。提亮幅度以「实测 ≥ 4.5:1 on `--surface-2`」为准，不是机械提一档
   （紫色若只提到 antd 的 `#9254DE` 仅 3.57:1，作正文不达标，因此多提半档）。
   品牌橙 `#E8720C` 在深底实测 **5.37:1**（比浅色底的 3.07:1 更好），**保持不变**以守住品牌识别。
3. **soft 底色改用 alpha 混合**，不用浅色实底：浅色下的 `#FFF7E6` 类淡底在深色下会变成刺眼亮块，统一改为 `rgba(语义色, 0.14~0.18)`。
4. **阴影失效 → 描边补偿**：深色下 `rgba(0,0,0,x)` 阴影几乎不可见，卡片层次靠 `--card-outline` 的 1px 描边建立。所有使用 `--shadow-*` 的卡片在深色下**必须**同时应用 `--card-outline`（门禁抽查，见 §8.2）。
5. **对比度门槛**：正文 ≥ 4.5:1，大字（≥18px/14px bold）、图标 ≥ 3:1。每个新令牌入表前必须实测比值并登记到 §4.5 矩阵；
   **估算值不得入表**（本方案初稿有 4 处估算偏差被实测推翻，见 §4.5 说明）。

### 4.4 双源一致性（CSS 令牌 ↔ antd token）

**为什么不能只留一份**：antd v5 的 `token` 会经 `derivative` 算法派生出 `colorPrimaryHover` 等值，
传 `'var(--brand)'` 字符串会让内部颜色解析失败、派生色全错。因此 **antd 侧必须传真实色值**，与 CSS 变量形成双源。

**防漂移措施**：
1. `themeTokens.ts` 导出 `TOKENS = { light: {...}, dark: {...} }` 与 `COMPONENTS = { light: {...}, dark: {...} }`；
2. `themeTokens.test.ts` 读取 `theme.css` 文本，用正则抽出 `:root` 与 `html[data-theme='dark']` 两个块的键值对，
   断言：①两块 key 集合完全一致（漏定义会让深色 fallback 到浅色值）；②与 `TOKENS` 中同语义项的值逐一相等；
3. `ConfigProvider` 开启 `cssVar: true`（antd ^5.22 支持），让 antd 自身样式也走 CSS 变量，切换时无需重算全量样式，
   同时使 antd 内部派生色与我们的令牌在同一变量体系下可被 DevTools 检视。

`COMPONENTS` 深色取值（对齐现行 `themeConfig.components`）：

| 组件 | 浅色（现状） | 深色 |
|---|---|---|
| `Menu.itemBg` / `subMenuItemBg` | `#1E1E1E` | `#1A1A1A` |
| `Menu.itemColor` | `#B0B0B0` | `#A6A6A6` |
| `Menu.itemHoverBg` | `#2A2A2A` | `#2E2E2E` |
| `Menu.itemSelectedBg` | `#E8720C` | `#E8720C` |
| `Menu.itemActiveBg` | `#333333` | `#383838` |
| `Table.headerBg` / `headerColor` | `#FAFAFA` / `#333333` | `#262626` / `#E8E8E8` |
| `Table.rowHoverBg` | `#FFF7ED` | `rgba(232,114,12,0.12)` |

> 侧边栏在浅色主题下本就是深色（`#1E1E1E`），因此深色主题的侧边栏只需比内容区**更深一档**（`#1A1A1A`），
> 保持「侧边栏 < 内容区 < 浮层」的明度递增关系，不改变现有视觉语言。

### 4.6 `--on-brand` 定版依据：橙底上到底用黑字还是白字

> 这是原 §十三 第 1 条的决议记录。结论：**深色主题取 `#141414`（黑字）**，浅色维持 `#FFFFFF`。

#### 4.6.1 关键认知：决定因素是底色相对亮度，不是主题

调研主流设计系统的深色主题主按钮（对比度由 `contrastRatio()` 本地实测）：

| 系统 | 深色主按钮底 | 白字 | 黑字(`#141414`) | 实际用 | 备注 |
|---|---|---|---|---|---|
| Ant Design dark | `#1668dc` 蓝 | **5.19** ✅ | 3.55 | 白字 | 蓝系亮度低，白字天然成立 |
| GitHub Primer dark | `#238636` 绿 | **4.63** ✅ | 3.98 | 白字 | 同上 |
| Stripe dark | `#635bff` 紫 | **4.70** ✅ | 3.92 | 白字 | 同上 |
| **本项目** | `#E8720C` 橙 | 3.07 ❌ | **6.00** ✅ | — | 橙系亮度高，与上述三类不同族 |
| Amazon | `#FF9900` 橙黄 | 2.14 ❌ | **8.60** ✅ | **黑字** | 外部实测 9.8:1（达 AAA）vs 2.1:1 |

**“深色模式一律白字”是个伪命题**：它只在蓝/绿/紫主色上成立（亮度 0.14~0.20）。
橙色亮度 0.29，属另一个物理族。Amazon 用黑字不是风格选择，是被物理逼的。

#### 4.6.2 最硬的证据：antd 官方 darkAlgorithm 自己在橙黄系上翻车

`node -e "theme.getDesignToken({algorithm: theme.darkAlgorithm})"` 实测各底色上的**白字**对比度：

| antd 深色 token | 底色 | 白字对比 | 判定 |
|---|---|---|---|
| `colorBgSpotlight`（Tooltip 底） | `#424242` | **10.05** ✅ | 必须白字，不能动 |
| `colorPrimary` | `#1668dc` | 5.19 ✅ | |
| `colorError` | `#dc4446` | 4.24 ⚠️ | 差一点 |
| `colorPrimaryHover` | `#3c89e8` | **3.54** ❌ | antd 自己就不达标 |
| `colorSuccess` | `#49aa19` | **2.98** ❌ | 同上 |
| `colorWarning` | `#d89614` | **2.53** ❌ | 橙黄系，重灾区 |

所以**不能拿“antd 深色就是白字”当质量依据**——它在自家 `colorWarning` 上只有 2.53，
与我们的橙是同一个受害场景。（参考口径：Material 3 在深色主题下 `primary = tone 80`（浅）、`onPrimary = tone 20`（深），
即“浅底配深字”；MUI 的实现是当对比度低于阈值时自动切换到备用文字色。）

#### 4.6.3 重要约束：不得改全局 `colorTextLightSolid`

初稿曾考虑直接改该 token 以保证一致性，实测否定：

```
grep -rl colorTextLightSolid node_modules/antd/es → 20 个组件
button, radio, switch, tag, menu, tooltip, dropdown, steps, date-picker,
avatar, tree, layout, spin, back-top, tour, image, …
```

`colorTextLightSolid` 的语义是「**浅底之上的反色文字**」，不是「品牌橙底上的文字」。
把它整体改黑会连带把 Tooltip 文字也改黑——而 Tooltip 底是 `#424242`，黑字只有 **2.1:1**，
等于把一个 10.05 的满分场景改成品不及格。

→ 正确做法：用**语义令牌 `--on-brand`** 只承担“品牌色实底上的前景”，其余不动。

#### 4.6.4 为何是重命名而不是新增令牌

原 `--text-inverse`（浅 `#FFFFFF` / 深 `#141414`）与提议的 `--on-brand` **浅深两值完全相同**。
直接新增会造出两个全同值令牌，而“同值多语义”正是本方案否决 `#333333` 自动映射的理由（§5.2）。
因此**重命名**而非新增，并顺带修了两个语义不准：

- “inverse” 容易被读成“深色主题反色”，而它真实含义是“品牌底上的前景”；
- “text-” 前缀只暗示文字，但 Checkbox 勾号、Radio 内圆点是**图标**，同样需要随它转色。

同时新增单测断言（Phase 0 已落地）：除 `INTENTIONAL_VALUE_DUPLICATES` 白名单外，
不得存在浅深两值全同的两个令牌——把这次踩的坑直接机验化。
> 该断言同时登记了一对现有重复：`info` 与 `text-brand` 浅深全同（标题蓝与语义 info 色），
> 映射到任一侧渲染结果一致，因此保留两个名字但已写明理由。

#### 4.6.5 Phase 1 覆写清单（底色为品牌橙的全部位置）

| 位置 | 覆写点 | 容易漏的 |
|---|---|---|
| Button primary | `components.Button.primaryColor = '#141414'`（仅深色） | — |
| Menu 选中项 | `components.Menu.itemSelectedColor`（现 `#FFFFFF`） | 文字与**图标**一起转 |
| Switch 选中态 | 选中文字（`啟用`）随 `--on-brand` | 滑柄圆点是 `#fff` 实底，**保持不动** |
| Checkbox / Radio 选中 | 勾号与内圆点颜色 | 这是**图标不是文字**，最容易漏 |
| Tag solid 形态（品牌橙） | 文字 + 图标 | 需先清点是否有橙色 solid Tag |
| 自绘统计卡「品牌/已用」块 | §B.7 用 `#FFF7E6` 淡底深字，**不受影响** | — |

**不动清单**：Tooltip（`#424242` 底）、Modal 深色遮罩、Spin/Loading、Layout Header 反色区、Steps 已完成态（若底非橙）。

#### 4.6.6 遗留议题（不在本方案范围）

方案 C——两个主题都用黑字（对齐 Amazon / Hacker News）在无障碍上最优（6.00 跨主题一致），
但它改动的是**浅色全站主按钮的现有观感**（品牌资产），应由产品单独拍板，不得夹带在深色改造里。
建议深色上线稳定后，拿着真实使用数据再评估。

## 六、特殊渲染面适配

### 6.1 登录页（保持品牌固定样式）
- 完全排除在令牌化之外（§5.4）。
- `theme.css` 中显式声明：`html[data-theme='dark'] .login-page { color-scheme: dark; }`，
  只让浏览器原生控件（滚动条、`input` 光标、`select`）跟随深色，页面视觉不变。
- 深色下登录页与后续页面的过渡：登录成功后进入门户/系统时才应用主题，避免「登录页暗 → 内容区暗」的层次感丢失问题。

### 6.2 门户插画（scene 色板不变）
- 16 个 `data-scene` 色值不动；卡片底、描边、标题、简介文字改用 `--surface-2` / `--border-2` / `--text-1` / `--text-3`。
- **深色下的新约束**（需在 §A.1.1 补一条）：浅色下「禁止近黑实心块 L<20%」是为了避免脏块；
  深色下问题反转为「近黑块贴在 `#1F1F1F` 卡底上不可见」。因此深色下插画容器必须满足：
  `--surface-3` 底 或 1px `--border-2` 描边，二者至少其一，保证插画与卡片底有可辨边界。
- `prefers-reduced-motion` 降级三条（离屏暂停 / `visibilitychange` / 全静态）不受主题影响，不得删。

### 6.3 `@ant-design/charts`（G2 内核）
- 用 `useTheme()` 取当前主题，传 `theme: isDark ? 'classicDark' : 'classic'`（G2 5.x 内置主题名）。

### 6.4 React Flow（`@xyflow/react@12`）

### 6.5 leaflet 地图（不换瓦片源）
- 深色下用 CSS filter 降亮：

  ```css
  html[data-theme='dark'] .leaflet-tile-pane { filter: brightness(0.72) contrast(1.08) saturate(0.85); }
  ```
- ⚠️ **已知坑**：filter 若加在 `.leaflet-container` 上会把 marker / popup 一起压暗。
  必须**只作用于 `.leaflet-tile-pane`**，并对 `.leaflet-marker-pane` 做反向补偿：

### 6.6 `html-to-image` 导出锁浅色
新增 `packages/ui/src/utils/exportWithLightTheme.ts`：

```ts
/**
 * 导出图片时强制按浅色渲染：交付物会进邮件、PPT 与打印件，深色底在其中普遍不可读。
 * 因此临时把 data-theme 切到 light，等两帧确保 CSS 与 antd cssVar 都已生效后再截图，finally 恢复。
 */
export async function exportNodeWithLightTheme<T>(
  node: HTMLElement,
  render: (n: HTMLElement) => Promise<T>,
): Promise<T> {
  const root = document.documentElement
  const prev = root.dataset.theme
  root.dataset.theme = 'light'
  await new Promise((r) => requestAnimationFrame(() => requestAnimationFrame(r)))
  try {
    return await render(node)
  } finally {
    root.dataset.theme = prev ?? 'light'
    await new Promise((r) => requestAnimationFrame(r))
  }
}
```

- 必须**双 `requestAnimationFrame`**：单次只保证样式重算入队，antd `cssVar` 模式下的变量替换需要再一帧才落到组件。
- 所有 `toPng` / `toJpeg` / `toSvg` 调用点统一改走该工具（现有调用点需在 Phase 3 全量清点）。
- 导出期间禁止用户切换主题：`ThemeControls` 订阅一个 `exporting` 状态置灰（或简单地在导出 toast 期间禁用）。

## 七、无障碍

| 项 | 要求 |
|---|---|
| 对比度 | 正文 ≥ 4.5:1；大字/图标/边框 ≥ 3:1（WCAG 2.1 AA）。每个令牌入表前实测并记录 |

### 8.2 新增门禁 `check:theme-tokens`（`scripts/check-theme-tokens.mjs`）

四条断言，任一失败即阻断：
1. **令牌完整性**：`theme.css` 的 `:root` 与 `[data-theme='dark']` key 集合一致（漏定义 → 深色下静默回落浅色值，是最难发现的缺陷）。
2. **双源一致**：`theme.css` 与 `themeTokens.ts` 值一致（与 8.1 的 ② 同源，门禁里再跑一次以防测试被跳过）。
3. **baseline 只降不升**：当前未令牌化裸色值数 ≤ `scripts/theme-token-baseline.json` 记录值（照 `check:i18n` / `check:boundary` 的既有 baseline 惯例）。

## 十一、回滚方案

| 层 | 回滚动作 | 影响 |
|---|---|---|
| 入口 | `VITE_THEME_SWITCH_ENABLED=false` 重新构建部署 | 用户看不到切换按钮，`data-theme` 恒 light，**无需回滚代码** |
| 偏好 | 用户侧 `localStorage.removeItem('app_theme')`；或代码侧忽略该 key | 回到跟随系统/浅色 |
| 深色定义 | 删除 `theme.css` 中 `html[data-theme='dark'] {...}` 整块 | 全站立刻回浅色，令牌消费方（已替换的 `var(--*)`）因 `:root` 值 = 现状色值而**视觉零变化** |
| 代码 | 每个 Phase 独立 PR，`git revert` 单个 merge commit | codemod 提交是纯机械替换，revert 无副作用 |
| 数据库 | 无 | 本方案不涉后端，无迁移、无数据回滚 |
| 配置 | `vite.config.ts` 插件为纯增量，移除即回原状 | 4 个 `index.html` 从未被手工修改，无需清理 |

**关键安全属性**：因为 `:root` 的浅色令牌值与现状裸色值**完全相同**，档 A/B/C 的替换在浅色主题下是**视觉恒等变换**。
这意味着「令牌化」与「深色上线」两件事彻底解耦——前者可以随时合并、随时 revert，后者只由一个 flag 控制。

### 18.4 三个必须记住的坑（本阶段实际踩到）

1. **基线树耦合**：`--snapshot` 存的是**当前所在树**的计数，CI 跑的是**本 PR 提交树**。若先在有改动 A 的分支上 snapshot、
   再基于未含 A 的 main 建分支，计数会回升而判红（#12 实踩：`inlineHex 7962→7968（+6）`，+6 精确等于依赖 PR 的改动量）。
   修复是**先合被依赖的 PR、再 merge main 重取 snapshot**，而不是放宽基线。多 PR 碰同一份基线文件时有合并顺序依赖，需写进 PR 描述。
   **第五批补：同一坑的第二种形态是「工作区挂着别人的未提交改动」**——它也会让 `--snapshot` 存进不属于本批的计数。
   判据很简单：跑批前先 `node scripts/check-theme-tokens.mjs`，若在**未改任何文件**时就判红，那就是工作区脏，
   此时必须改去 `git worktree` 的干净检出里跑（命令见 §18.3）。绝不为了“让门禁变绿”而在脏树上 snapshot。
2. **退出码不进管道**：`cmd 2>&1 | grep …; echo $?` 取到的是 `grep` 的码——本阶段因此写过一次「门禁=0」而实际输出里有 `ERROR`。
   正确写法：`cmd > /tmp/out.txt 2>&1; echo $?` 再单独读文件。
3. **不得凭一行片段断定「没有内联 style」**：`TrafficBalancePanel.tsx` 的 `style={{...}}` 写在 `aria-label` 的**下一行**，
   只看一行导致误判「不需迁断言」。改断言前必须读完整元素。

### 18.5 codemod 的两条安全边界（不得为了“多改一点”而拆掉）

- **只动真实 `style={{…}}` 区段**（含跳行，由轻量状态机识别）。数据对象里的 `{ color: '#1890FF' }` 常被喂给
  ECharts / SVG / canvas，它们**不解析 CSS 变量**，刷成 `var()` 会静默毁掉配色且无报错。
  加上该限制后 Recommend 从预估 925 降到 816，减少的 109 处正是这类不该动的数据对象。
- **不自动处理 JSX 属性形式**（`fill={…}`、模板字符串里的 SVG）：插画里的白色对勾、饱和色上的中心白点都是
  已定版的保留决策，自动刷成令牌色会让它们在底上消失。此类靠人工逐处看背板。
