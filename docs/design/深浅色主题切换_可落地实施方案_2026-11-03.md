## 二、目标与非目标

### 目标
1. 用户可在顶栏一键切换 **淺色 / 深色 / 跟隨系統**，偏好持久化，刷新与跨子系统（eam/hr/rdm）一致。
2. 首屏无白闪（FOUC），4 个入口行为一致。
3. 壳层（侧边栏 / 顶栏 / 内容区 / 搜索区 / 操作区 / 表格 / 表单 / 弹窗 / 统计卡）在深色下完整可用、层次清晰。
4. 存量色值按批次收敛到语义令牌，未令牌化数量由 baseline 门禁钉住**只降不升**。
5. 深色下正文对比度 ≥ 4.5:1、大字/图标/边框 ≥ 3:1（WCAG AA）。

### 非目标（本次不做）
- 不做多品牌换肤（主题色仍固定品牌橙 `#E8720C`，不开放用户自定义主色）。
- 不做高对比度模式（仅 light/dark 两档；如需 `high-contrast` 令牌层已预留扩展位）。
- 不做后端用户偏好存储（多端同步留待后续，接口设计见 §十三）。
- 不改 `@media` 响应式断点策略（仍靠 Flex/Grid 自适应，仅新增 `prefers-color-scheme` 与 `print` 两类媒体查询）。

## 三、总体架构

```
                     ┌─────────────────────────────────────────┐
   首屏（React 前）   │ vite 插件 transformIndexHtml 注入内联脚本 │ → <html data-theme="dark|light">
                     └─────────────────────────────────────────┘
                                        │
   状态层            ThemeProvider (packages/ui/src/theme)  ── preference: 'light'|'dark'|'system'
                                        │                    └─ localStorage['app_theme']
                                        │                    └─ matchMedia('(prefers-color-scheme: dark)')
                     ┌──────────────────┴──────────────────┐
   呈现层            │                                     │
        CSS 令牌层 theme.css                      antd 令牌层 themeTokens.ts
        :root { --text-1:#262626 }                { light:{...}, dark:{...} }
        html[data-theme=dark]{ --text-1:#E8E8E8 }          │
                     │                            ConfigProvider theme={{ cssVar:true,
                     │                              algorithm: dark?darkAlgorithm:defaultAlgorithm,
                     │                              token: TOKENS[theme], components: COMPONENTS[theme] }}
                     └──────────┬───────────────────────────┘
                                │ 双源一致性由 themeTokens.test.ts 钉住
   入口层            ThemeControls.tsx（HeaderBar `.header-right` + PortalTopBar 双处复用，
                     照 PortalLocaleControls 的既有模式）
   事件层            THEME_CHANGED_EVENT（照 TRANSLATION_BUNDLE_EVENT 惯例）
                     → 供 charts / leaflet 等非 CSS 渲染面重绘
```

## 四、令牌体系定版

### 4.1 分层原则

| 层 | 命名 | 谁可用 | 说明 |
|---|---|---|---|
| 原始色阶 primitive | `--gray-1..13` / `--orange-1..10` | **仅 theme.css 内部** | 与 antd 色阶对齐，业务代码禁止直接引用 |
| 语义 semantic | `--surface-*` / `--text-*` / `--border-*` / `--brand*` / `--success*` / `--info*` / `--warning*` / `--danger*` / `--purple*` / `--shadow-*` | 业务代码**只用这层** | 一个语义 = 一个用途，不表达具体颜色 |
| 组件 component | `--sidebar-bg` / `--sidebar-item-*` / `--stat-card-*` | 组件自有 CSS | 仅在壳层组件需要与语义层不同的取值时使用 |

**硬约束**：业务代码（CSS 与 JSX）只允许引用语义层与组件层；出现 `var(--gray-7)` 一律判违规（门禁扫描）。

##### 补充阶令牌（2026-11-05 新增，为了拆掉两个反复出现的「半对」）

这三个不是新语义，而是 antd 调色板上**真实存在、与现有令牌差 1~15 个单位的邻阶**。
为何不直接收敛到现有令牌：收敛会改变浅色观感，而「浅色侧逐像素不变」是本方案 §15.2 第 5 条定下的硬约束
（当时正是为了不接 **1 个单位**的偏差，才把 `#FFF7ED` 从 `--brand-soft` 踢回人工清单）。

| 令牌 | 浅色值 | 深色值 | 存量为何不能并给现有令牌 | 实测对比度 |
|---|---|---|---|---|
| `--danger-callout` | `#FFF2F0` | `rgba(255,77,79,0.16)` | antd v4 error-1，与 `--danger-soft`(#FFF1F0) 差 1 个单位 | 浅色 `danger` 上 **2.99**（存量债务，只守不变差）；深色 `#FF7875` on 合成底 #432627 = **5.30** ✓ |
| `--warning-deep` | `#D46B08` | `#FFA940` | antd orange-7 前景；原列 REVIEW_REQUIRED（建议收敛到 `#FA8C16`），但全站 46 处均作前景、语义单一，收敛会连带改掉 46 处浅色观感 | 浅色 on `--warning-soft` = **3.34**（低于正文 AA，属存量债务，单测按 3.3 卡下限）；深色 #FFA940 on 合成底 #42301E = **6.58** ✓ |
| `--info-hover-tint` | `#F0F5FF` | `rgba(24,144,255,0.16)` | antd geekblue-1；与 `--info-soft`(#E6F7FF) 差 8~15 个单位，一个是淡蓝一个是青蓝，不是同一阶 | 浅色 `--text-2` 上 **6.41** ✓；深色合成到侧栏底 #262626 得 #243749，`--text-2` 上 **5.64** ✓ |

三条都已进 `COLOR_TO_TOKEN`（前两条进 bg 段、`warning-deep` 只进 fg 段），所以后续批次会自动成对。
`--warning-deep` **不进 bg/border 段**，避免把同色值的背景用法误映射成文字令牌。
单测侧已补「合成对比度」一组断言（rgba 要先合成到卡片底再算，`contrastRatio` 不处理 alpha），
并把「深色必须 rgba」的后缀从 `-soft` 拓宽到 `-soft|-tint|-callout`——
否则新令牌会静默逃过这条规则（只靠命名后缀识别叠加型底色本身就是个近似）。

##### 语义色描边阶令牌（2026-11-05 第二轮：`danger/warning/success/info/purple-border`）

这批不是「另一阶邻色」，而是一族新语义：**描边位**。存量里大量淡彩实色出现在
`border: '1px solid #FFD591'` / `borderColor: '#FFCCC7'` 这类位置上，它们既不能并给同族的
`*-soft`（那是背景），也不能并给中性 `border-*`（那是灰度）。

|---|---|---|---|---|
| `--danger-border` | `#FFCCC7` | `rgba(255,120,117,0.32)` | 14 处（另一档 `#FFA39E` 8 处） | 1.4272 / 1.7514 |
| `--warning-border` | `#FFD591` | `rgba(250,160,61,0.32)` | 18 处（`#FFE7BA` 19 处、`#FFD8A8` 3 处） | 1.3835 / 1.9546 |
| `--success-border` | `#B7EB8F` | `rgba(106,190,57,0.32)` | 14 处（`#D9F7BE` 18 处） | 1.3731 / 1.8651 |
| `--info-border` | `#91D5FF` | `rgba(64,169,255,0.32)` | 7 处（`#ADC6FF` 5 处） | 1.5951 / 1.7843 |
| `--purple-border` | `#D3ADF7` | `rgba(163,113,231,0.32)` | 4 处（`#E8D5F5` 4 处，打平） | 1.8935 / 1.5833 |

⚠ **本表原写的「描边位 63/35/32/17/14 处」排序是错的**：当时用的测量脚本逐行匹属性名，
同一行上多个属性会重复命中同一个 hex（例如一个块里 `background`/`border`/`padding` 均开头匹配）。
第九批用两种独立方法重测：按 occurrence + 最近前导属性归类得上面括号里的数字；只匹
`solid|dashed #X` 形态得 FFD591 12 / FFE7BA 15。**结论上的影响**：danger / info 两族的 canonical 仍是主流档，
但 warning 与 success 两档实际近乎等量（purple 打平）——所以下面「少数档」这个说法不成立，
**两档都应当各有一个令牌**，而不是把其中一档当待定项。

五条必须记住的口径：

1. **深色统一用「该族深色主色 + 32% alpha」**，与存量 `brand-border` 一致，不逐族拍脑袋。
2. **可见数字是回归守卫，不是 WCAG 达标声明**。描边本身就是 antd 预设的 1.2~1.9 细线，
   拿 3.0/4.5 卡它是假命题；断言下限取观测值（浅 ≥ 1.15、深 ≥ 1.55，存量 `brand-border` 1.1930/1.6212 也在范围内）。
3. **按段映射本身就是防误伤守卫**：五个值只进 `COLOR_TO_TOKEN.border`，所以同色值的背景用法
   （实测 `#FFCCC7` 1 处、`#FFD591` 1 处 bg）不会被换——仓内 `brand-border`（也有 2 处 bg）已是先例。
   所以「该色值全站存在多种角色」不自动否决描边令牌，**只要它只进描边段**。
4. **第二档描边必须建令牌，不该叫“少数档”**（本节开头那段排序已按第九批重测修正）：
   `#FFE7BA` 19、`#D9F7BE` 18、`#FFA39E` 8、`#ADC6FF` 5、`#E8D5F5` 4、`#FFD8A8` 3，合计 57 处描边位。
   它们与 canonical 同角色但亮度不同，**收敛会改浅色观感**（需产品拍板），而建令牌不改观感且能同时修好深色；
   第九批已实测到这个待定项在**阻塞批次**（一次跑出 6 处新半对，只能先成对回退加锁）。
   命名建议跟现有成对约定走：`--{hue}-soft-border`（它就是“软底卡片的描边”，与 `brand-border` 配 `brand-soft` 同构）。
5. **中性描边 `#E8E8E8` 是最大的单项剩余债**：全站 **188 处**（描边位 83、背景位 92），
   比本族任何一档都大一个量级。它同时当描边和底色用，所以**必须两个令牌**（各自只进一个段，
   按段映射不会串位）；原 REVIEW 条目只说了“接近 --border-2 但不等值”，没意识到量级。
   下一轮建描边令牌时应一并定掉。

后缀规则同步拓宽到 `-soft|-tint|-callout|-border`（不会误伤 `border-1/2/3`/`border-input`，它们不以
`-border` 结尾）。断言还新增一条由变异验证发现的缺口：**rgba 必须是含 alpha 的四元**——
`rgba(64,169,)` 这种写错形态会被合成函数静默当成不透明，颜色全错但不报错。

### 4.3 深色取值五条规则（评审口径，后续新增令牌一律照此推导）

1. **不用纯黑**：底色三阶取 `#141414` / `#1F1F1F` / `#262626`（对齐 antd `darkAlgorithm` 的 `colorBgLayout` / `colorBgContainer` / `colorBgElevated`），避免 OLED 纯黑与灰字之间出现「光晕拖影」。
2. **语义色提亮一档**：`#FF4D4F→#FF7875`(6.43:1)、`#52C41A→#6ABE39`(7.09:1)、`#1890FF→#40A9FF`(6.54:1)、
   `#FA8C16→#FAA03D`(7.98:1)、`#722ED1→#A371E7`(4.77:1)。提亮幅度以「实测 ≥ 4.5:1 on `--surface-2`」为准，不是机械提一档
   （紫色若只提到 antd 的 `#9254DE` 仅 3.57:1，作正文不达标，因此多提半档）。
   品牌橙 `#E8720C` 在深底实测 **5.37:1**（比浅色底的 3.07:1 更好），**保持不变**以守住品牌识别。
3. **soft 底色改用 alpha 混合**，不用浅色实底：浅色下的 `#FFF7E6` 类淡底在深色下会变成刺眼亮块，统一改为 `rgba(语义色, 0.14~0.18)`。
4. **阴影失效 → 描边补偿**：深色下 `rgba(0,0,0,x)` 阴影几乎不可见，卡片层次靠 `--card-outline` 的 1px 描边建立。所有使用 `--shadow-*` 的卡片在深色下**必须**同时应用 `--card-outline`（门禁抽查，见 §8.2）。
5. **对比度门槛**：正文 ≥ 4.5:1，大字（≥18px/14px bold）、图标 ≥ 3:1。每个新令牌入表前必须实测比值并登记到 §4.5 矩阵；
   **估算值不得入表**（本方案初稿有 4 处估算偏差被实测推翻，见 §4.5 说明）。

### 4.4 双源一致性（CSS 令牌 ↔ antd token）

**为什么不能只留一份**：antd v5 的 `token` 会经 `derivative` 算法派生出 `colorPrimaryHover` 等值，
传 `'var(--brand)'` 字符串会让内部颜色解析失败、派生色全错。因此 **antd 侧必须传真实色值**，与 CSS 变量形成双源。

**防漂移措施**：
1. `themeTokens.ts` 导出 `TOKENS = { light: {...}, dark: {...} }` 与 `COMPONENTS = { light: {...}, dark: {...} }`；
2. `themeTokens.test.ts` 读取 `theme.css` 文本，用正则抽出 `:root` 与 `html[data-theme='dark']` 两个块的键值对，
   断言：①两块 key 集合完全一致（漏定义会让深色 fallback 到浅色值）；②与 `TOKENS` 中同语义项的值逐一相等；
3. `ConfigProvider` 开启 `cssVar: true`（antd ^5.22 支持），让 antd 自身样式也走 CSS 变量，切换时无需重算全量样式，
   同时使 antd 内部派生色与我们的令牌在同一变量体系下可被 DevTools 检视。

> 若不在此登记，后续 review 会把既有债务误判为本次改造引入的回归。债务 ②~⑤ 一律标注「独立议题」，不得夹带进主题 PR。
>
> **初稿偏差复盘**：本方案初稿有 4 处对比度为估算值，实测后全部推翻——`--text-3` 估 5.1 实为 4.90（且 s3 上仅 4.50）、
> `--brand` 估 4.6 实为 5.37、`--text-4` 深色估「够用」实为 2.35、`--purple` 估「提一档够」实为 3.57。
> 结论：**颜色对比度一律实测，禁止估算入表**，该要求已写入 §4.3 规则 5 与 §8.1 测试断言。

### 4.6 `--on-brand` 定版依据：橙底上到底用黑字还是白字

> 这是原 §十三 第 1 条的决议记录。结论：**深色主题取 `#141414`（黑字）**，浅色维持 `#FFFFFF`。

#### 4.6.1 关键认知：决定因素是底色相对亮度，不是主题

调研主流设计系统的深色主题主按钮（对比度由 `contrastRatio()` 本地实测）：

| 系统 | 深色主按钮底 | 白字 | 黑字(`#141414`) | 实际用 | 备注 |
|---|---|---|---|---|---|
| Ant Design dark | `#1668dc` 蓝 | **5.19** ✅ | 3.55 | 白字 | 蓝系亮度低，白字天然成立 |
| GitHub Primer dark | `#238636` 绿 | **4.63** ✅ | 3.98 | 白字 | 同上 |
| Stripe dark | `#635bff` 紫 | **4.70** ✅ | 3.92 | 白字 | 同上 |
| **本项目** | `#E8720C` 橙 | 3.07 ❌ | **6.00** ✅ | — | 橙系亮度高，与上述三类不同族 |
| Amazon | `#FF9900` 橙黄 | 2.14 ❌ | **8.60** ✅ | **黑字** | 外部实测 9.8:1（达 AAA）vs 2.1:1 |

**“深色模式一律白字”是个伪命题**：它只在蓝/绿/紫主色上成立（亮度 0.14~0.20）。
橙色亮度 0.29，属另一个物理族。Amazon 用黑字不是风格选择，是被物理逼的。

#### 4.6.2 最硬的证据：antd 官方 darkAlgorithm 自己在橙黄系上翻车

`node -e "theme.getDesignToken({algorithm: theme.darkAlgorithm})"` 实测各底色上的**白字**对比度：

| antd 深色 token | 底色 | 白字对比 | 判定 |
|---|---|---|---|
| `colorBgSpotlight`（Tooltip 底） | `#424242` | **10.05** ✅ | 必须白字，不能动 |
| `colorPrimary` | `#1668dc` | 5.19 ✅ | |
| `colorError` | `#dc4446` | 4.24 ⚠️ | 差一点 |
| `colorPrimaryHover` | `#3c89e8` | **3.54** ❌ | antd 自己就不达标 |
| `colorSuccess` | `#49aa19` | **2.98** ❌ | 同上 |
| `colorWarning` | `#d89614` | **2.53** ❌ | 橙黄系，重灾区 |

所以**不能拿“antd 深色就是白字”当质量依据**——它在自家 `colorWarning` 上只有 2.53，
与我们的橙是同一个受害场景。（参考口径：Material 3 在深色主题下 `primary = tone 80`（浅）、`onPrimary = tone 20`（深），
即“浅底配深字”；MUI 的实现是当对比度低于阈值时自动切换到备用文字色。）

#### 4.6.3 重要约束：不得改全局 `colorTextLightSolid`

初稿曾考虑直接改该 token 以保证一致性，实测否定：

```
grep -rl colorTextLightSolid node_modules/antd/es → 20 个组件
button, radio, switch, tag, menu, tooltip, dropdown, steps, date-picker,
avatar, tree, layout, spin, back-top, tour, image, …
```

`colorTextLightSolid` 的语义是「**浅底之上的反色文字**」，不是「品牌橙底上的文字」。
把它整体改黑会连带把 Tooltip 文字也改黑——而 Tooltip 底是 `#424242`，黑字只有 **2.1:1**，
等于把一个 10.05 的满分场景改成品不及格。

→ 正确做法：用**语义令牌 `--on-brand`** 只承担“品牌色实底上的前景”，其余不动。

#### 4.6.4 为何是重命名而不是新增令牌

原 `--text-inverse`（浅 `#FFFFFF` / 深 `#141414`）与提议的 `--on-brand` **浅深两值完全相同**。
直接新增会造出两个全同值令牌，而“同值多语义”正是本方案否决 `#333333` 自动映射的理由（§5.2）。
因此**重命名**而非新增，并顺带修了两个语义不准：

- “inverse” 容易被读成“深色主题反色”，而它真实含义是“品牌底上的前景”；
- “text-” 前缀只暗示文字，但 Checkbox 勾号、Radio 内圆点是**图标**，同样需要随它转色。

同时新增单测断言（Phase 0 已落地）：除 `INTENTIONAL_VALUE_DUPLICATES` 白名单外，
不得存在浅深两值全同的两个令牌——把这次踩的坑直接机验化。
> 该断言同时登记了一对现有重复：`info` 与 `text-brand` 浅深全同（标题蓝与语义 info 色），
> 映射到任一侧渲染结果一致，因此保留两个名字但已写明理由。

#### 4.6.5 Phase 1 覆写清单（底色为品牌橙的全部位置）

| 位置 | 覆写点 | 容易漏的 |
|---|---|---|
| Button primary | `components.Button.primaryColor = '#141414'`（仅深色） | — |
| Menu 选中项 | `components.Menu.itemSelectedColor`（现 `#FFFFFF`） | 文字与**图标**一起转 |
| Switch 选中态 | 选中文字（`啟用`）随 `--on-brand` | 滑柄圆点是 `#fff` 实底，**保持不动** |
| Checkbox / Radio 选中 | 勾号与内圆点颜色 | 这是**图标不是文字**，最容易漏 |
| Tag solid 形态（品牌橙） | 文字 + 图标 | 需先清点是否有橙色 solid Tag |
| 自绘统计卡「品牌/已用」块 | §B.7 用 `#FFF7E6` 淡底深字，**不受影响** | — |

**不动清单**：Tooltip（`#424242` 底）、Modal 深色遮罩、Spin/Loading、Layout Header 反色区、Steps 已完成态（若底非橙）。

**落地记录（本 PR）**：上表中能靠组件 token 解决的两行（Button primary / Menu 选中项）早已在
`themeTokens.ts` 里完成；剩下的 Switch / Checkbox / Radio 三处直此批才落地，因为**它们根本没有
组件级 token 可用**。取色来源是读 antd 5.29.3 源码查实的，不是推测：

| 控件 | antd 真源 | 实际取色 | 覆写点 |
|---|---|---|---|
| Checkbox 勾号 | `checkbox/style/index.js:97` | `border: lineWidthBold solid token.colorWhite` | `border-color: var(--on-brand)` |
| Radio 内圆点 | `radio/style/index.js:433` | `radioColor: wireframe ? colorPrimary : colorWhite` | `background-color: var(--on-brand)` |
| Switch 选中文字 | `switch/style/index.js:183` | `color: token.colorTextLightSolid` | `color: var(--on-brand)` |

三条全部限定 `html[data-theme='dark']`，**浅色侧零变化**；写在 `components.css` 而非 `theme.css`
（后者是 `generate-theme-css.mjs` 的产出，手改会被门禁拦下）。

> **本批当时多用了 `!important`，理由写错了，廿一轮已实测改正**：#43 当时按「antd CSS-in-JS
> 会在根类上附加 hashId，特异性对拼不稳」这条**未验证的传统说法**加了 `!important`；
> 实测 antd 5 的 hashId 包在 `:where()` 里而 `:where()` 特异性**恒为 0**，
> 三条规则实测 201 / 301 / 300 vs 我们 302 / 302 / 401，**不靠 `!important` 也能赢**。
> `!important` 仍然保留（防“选择器被写短一级”这类静默漂移，见 §21.2 的变异实验），
> 但**不再拿错理由为它辩护**；正确理由已写回 `components.css` 注释。

为什么不能改种子 token `colorWhite` 一劳永逸：它被全站大量组件共用（Tooltip 文字、Modal 关闭钮等），
翻转它属于「为了三处而改坏一批」，影响面失控。

上表「Tag solid 形态」一行已清点为**不适用**：全仓无一处给 `Tag` 的 `color` 传品牌橙实色
（`git grep "<Tag[^>]*color=" ` 匹 `#E8720C`/`#F59432`/`#FA8C16` 命中 0），所以没有需要跟着转色的橙色 solid Tag。

防漂移：`themeTokens.test.ts` 新增一个 describe（8 例），除「三条存在且取 `var(--on-brand)`」外，
还钉住「浅色不得出现这三条覆写」与「不动清单（滑柄白圆点 / 半选方块）不得被顺手加进来」两条反向守卫。
4 组变异验证均被抓到（改裸值 / 去深色限定 / 加滑柄 / 删整条），对照组 27/27 全绿。

> 注：jsdom 不加载外部样式表、也不对 `var()` 求值，所以这批断言只能钉「规则存在与取值」这一层；
> **它们不能证明选择器在浏览器里真的赢了特异性**——那条证据只能来自 §8.5 的浏览器计算值实测。


#### 4.6.6 遗留议题（不在本方案范围）

方案 C——两个主题都用黑字（对齐 Amazon / Hacker News）在无障碍上最优（6.00 跨主题一致），

## 六、特殊渲染面适配

### 6.1 登录页（保持品牌固定样式）
- 完全排除在令牌化之外（§5.4）。
- `theme.css` 中显式声明：`html[data-theme='dark'] .login-page { color-scheme: dark; }`，
  只让浏览器原生控件（滚动条、`input` 光标、`select`）跟随深色，页面视觉不变。
- 深色下登录页与后续页面的过渡：登录成功后进入门户/系统时才应用主题，避免「登录页暗 → 内容区暗」的层次感丢失问题。

### 6.2 门户插画（scene 色板不变）
- 16 个 `data-scene` 色值不动；卡片底、描边、标题、简介文字改用 `--surface-2` / `--border-2` / `--text-1` / `--text-3`。
- **深色下的新约束**（需在 §A.1.1 补一条）：浅色下「禁止近黑实心块 L<20%」是为了避免脏块；
  深色下问题反转为「近黑块贴在 `#1F1F1F` 卡底上不可见」。因此深色下插画容器必须满足：
  `--surface-3` 底 或 1px `--border-2` 描边，二者至少其一，保证插画与卡片底有可辨边界。
- `prefers-reduced-motion` 降级三条（离屏暂停 / `visibilitychange` / 全静态）不受主题影响，不得删。

### 6.3 `@ant-design/charts`（G2 内核）
- 用 `useTheme()` 取当前主题，传 `theme: isDark ? 'classicDark' : 'classic'`（G2 5.x 内置主题名）。
- 图表实例不监听 CSS 变量变化，因此主题切换时必须**强制重建**：外层容器 `key={theme}`。
- 同时订阅 `THEME_CHANGED_EVENT` 处理「非 React 渲染路径」（如在 `useEffect` 里命令式创建图表的场景）。

### 6.4 React Flow（`@xyflow/react@12`）
- v12 已使用 `--xy-*` CSS 变量，天然可主题化。在 `theme.css` 中按主题覆盖：
  ```css
  html[data-theme='dark'] .react-flow {
    --xy-background-color: var(--surface-1);
    --xy-edge-stroke: var(--border-1);
    --xy-node-border-radius: 6px;
    --xy-handle-background-color: var(--brand);
  }
  ```
- `AlgorithmFlow.tsx` 的 5 种自定义节点（terminal/stage/process/decision/system）用档 C codemod 收敛内联色值即可。

### 6.5 leaflet 地图（不换瓦片源）
- 深色下用 CSS filter 降亮：
  ```css
  html[data-theme='dark'] .leaflet-tile-pane { filter: brightness(0.72) contrast(1.08) saturate(0.85); }
  ```
- ⚠️ **已知坑**：filter 若加在 `.leaflet-container` 上会把 marker / popup 一起压暗。
  必须**只作用于 `.leaflet-tile-pane`**，并对 `.leaflet-marker-pane` 做反向补偿：
  ```css
  html[data-theme='dark'] .leaflet-marker-pane { filter: brightness(1.39) saturate(1.18); }
  ```
  （`1/0.72 ≈ 1.39`，抵消父级亮度衰减）。popup / tooltip 走 antd 令牌，自动跟随。
- `.leaflet-container { background: var(--surface-1); }` 避免瓦片加载期露白。

### 6.6 `html-to-image` 导出锁浅色
新增 `packages/ui/src/utils/exportWithLightTheme.ts`：

```ts
/**
 * 导出图片时强制按浅色渲染：交付物会进邮件、PPT 与打印件，深色底在其中普遍不可读。
 * 因此临时把 data-theme 切到 light，等两帧确保 CSS 与 antd cssVar 都已生效后再截图，finally 恢复。
 */
export async function exportNodeWithLightTheme<T>(
  node: HTMLElement,
  render: (n: HTMLElement) => Promise<T>,
): Promise<T> {
  const root = document.documentElement
  const prev = root.dataset.theme
  root.dataset.theme = 'light'
  await new Promise((r) => requestAnimationFrame(() => requestAnimationFrame(r)))
  try {
    return await render(node)
  } finally {
    root.dataset.theme = prev ?? 'light'
    await new Promise((r) => requestAnimationFrame(r))
  }
}
```

- 必须**双 `requestAnimationFrame`**：单次只保证样式重算入队，antd `cssVar` 模式下的变量替换需要再一帧才落到组件。
- 所有 `toPng` / `toJpeg` / `toSvg` 调用点统一改走该工具（现有调用点需在 Phase 3 全量清点）。
- 导出期间禁止用户切换主题：`ThemeControls` 订阅一个 `exporting` 状态置灰（或简单地在导出 toast 期间禁用）。

```css
@media print {

```
即打印恒浅色，与导出锁浅色口径一致。

### 6.9 ThemeControls 交互规格

- 位置：`HeaderBar` 的 `.header-right` 内、`<PortalLocaleControls />` 之后、通知铃铛之前；`PortalTopBar` 同位置。
- 形态：图标按钮 + antd `Dropdown`（三选项，当前项带 `CheckOutlined`），图标随当前**解析后**主题变化：

  使「无记录 = 跟随系统」成为唯一真值口径，避免三态与二态混用。
- 切换后派发 `THEME_CHANGED_EVENT`，并 `message.success`？**不弹 toast**（主题切换是即时可见的，弹提示属噪声）。

### 6.10 FOUC 防闪烁脚本（`scripts/lib/theme-boot-script.mjs` 单一真源）

```js
export const THEME_BOOT_SCRIPT = `(function(){try{
var p=localStorage.getItem('app_theme');
var d=p==='dark'||(p!=='light'&&window.matchMedia('(prefers-color-scheme: dark)').matches);
document.documentElement.dataset.theme=d?'dark':'light';
}catch(e){document.documentElement.dataset.theme='light';}})();`
```

- 通过 `vite.config.ts` 内联插件注入，`transformIndexHtml` 返回 `{ tag:'script', attrs:{}, injectTo:'head-prepend' }`，
  对根 `index.html` 与 3 个 app 的 `index.html` **一次性全覆盖**（`build-apps.mjs` 复用同一 config）。
- `theme.css` 同时提供 `html { background: var(--surface-1); color-scheme: light; }` 与
  `html[data-theme='dark'] { color-scheme: dark; }`，让滚动条、`input`、`select` 等原生控件跟随。
- 门禁校验：`check:theme-tokens` 断言 4 个 `index.html` 构建产物均含该脚本特征串（防止将来新增第 5 个 app 时漏注入）。

## 七、无障碍

| 项 | 要求 |
|---|---|
| 对比度 | 正文 ≥ 4.5:1；大字/图标/边框 ≥ 3:1（WCAG 2.1 AA）。每个令牌入表前实测并记录 |
| `color-scheme` | 必须声明，否则深色下原生控件（滚动条、日期选择器输入区）仍是白底 |
| 焦点环 | antd 默认 focus 环在深色下对比不足，需覆盖为 `--brand` 且宽度不小于 2px |
| 不以颜色为唯一信息载体 | 状态标签已有文字（`啟用`/`停用`），深色下仍成立；`--danger` 类色块必须配文字或图标 |
| `prefers-reduced-motion` | 现有降级保留；主题切换本身不加过渡动画（避免大面积重绘卡顿），仅 `background-color`/`color` 加 `0.2s` |

## 十一、回滚方案

| 层 | 回滚动作 | 影响 |
|---|---|---|
| 入口 | `VITE_THEME_SWITCH_ENABLED=false` 重新构建部署 | 用户看不到切换按钮，`data-theme` 恒 light，**无需回滚代码** |

| 代码 | 每个 Phase 独立 PR，`git revert` 单个 merge commit | codemod 提交是纯机械替换，revert 无副作用 |
| 数据库 | 无 | 本方案不涉后端，无迁移、无数据回滚 |
| 配置 | `vite.config.ts` 插件为纯增量，移除即回原状 | 4 个 `index.html` 从未被手工修改，无需清理 |

**关键安全属性**：因为 `:root` 的浅色令牌值与现状裸色值**完全相同**，档 A/B/C 的替换在浅色主题下是**视觉恒等变换**。
这意味着「令牌化」与「深色上线」两件事彻底解耦——前者可以随时合并、随时 revert，后者只由一个 flag 控制。

### 18.4 五个必须记住的坑（本阶段实际踩到）

1. **基线树耦合**：`--snapshot` 存的是**当前所在树**的计数，CI 跑的是**本 PR 提交树**。若先在有改动 A 的分支上 snapshot、
   再基于未含 A 的 main 建分支，计数会回升而判红（#12 实踩：`inlineHex 7962→7968（+6）`，+6 精确等于依赖 PR 的改动量）。
   修复是**先合被依赖的 PR、再 merge main 重取 snapshot**，而不是放宽基线。多 PR 碰同一份基线文件时有合并顺序依赖，需写进 PR 描述。
   **第五批补：同一坑的第二种形态是「工作区挂着别人的未提交改动」**——它也会让 `--snapshot` 存进不属于本批的计数。
   判据很简单：跑批前先 `node scripts/check-theme-tokens.mjs`，若在**未改任何文件**时就判红，那就是工作区脏，
   此时必须改去 `git worktree` 的干净检出里跑（命令见 §18.3）。绝不为了“让门禁变绿”而在脏树上 snapshot。
2. **退出码不进管道**：`cmd 2>&1 | grep …; echo $?` 取到的是 `grep` 的码——本阶段因此写过一次「门禁=0」而实际输出里有 `ERROR`。
   正确写法：`cmd > /tmp/out.txt 2>&1; echo $?` 再单独读文件。
3. **不得凭一行片段断定「没有内联 style」**：`TrafficBalancePanel.tsx` 的 `style={{...}}` 写在 `aria-label` 的**下一行**，
   只看一行导致误判「不需迁断言」。改断言前必须读完整元素。
4. **自匹配**（第二十节实踩）：用正则 `prop\s*[:=]` 探「基态」时，会匹到 handler 自己的
   `style.borderColor = '#E8720C'` —— 把「已令牌化的基态」误报成裸值，结论变成「零活缺陷」。
   正确写法：只认冒号声明，且从候选窗口里**剔除含 `.style.` 的行**。
5. **只认全写、不认简写**（第二十节实踩，比 4 更危险）：基态常用 `border: '1px dashed var(--border-1)'`
   声明边框色，只查 `borderColor:` 就是「找不到基态」→ 同样误判为裸。
   **两条通用做法**：属性名探测必须同时查它的简写父属性；以及**结论出「零」之前先用夹具做阳性对照**
   （人造一个应该报错的片段，确认工具真的会报错；注意「已修过的真文件」不能当对照，
   因为它根本不进入候选集，“没报错”会被当成“工具正常”）。

### 18.5 codemod 的两条安全边界（不得为了“多改一点”而拆掉）

- **只动真实 `style={{…}}` 区段**（含跳行，由轻量状态机识别）。数据对象里的 `{ color: '#1890FF' }` 常被喂给
  ECharts / SVG / canvas，它们**不解析 CSS 变量**，刷成 `var()` 会静默毁掉配色且无报错。
  加上该限制后 Recommend 从预估 925 降到 816，减少的 109 处正是这类不该动的数据对象。
- **不自动处理 JSX 属性形式**（`fill={…}`、模板字符串里的 SVG）：插画里的白色对勾、饱和色上的中心白点都是
  已定版的保留决策，自动刷成令牌色会让它们在底上消失。此类靠人工逐处看背板。

**C：组件 props 不需要 schema 扩展（推翻我自己上一轮的说法）**

我之前断言「`Tag` 的 `color`+`borderColor` 一对多必须扩 token-map schema」——本轮拿证据核了，**结论是不需要**：

- antd `Tag` 自定义色实际只做一件事：`style={{ backgroundColor: color }}`（`node_modules/antd/lib/tag/index.js`），
  **不派生 borderColor、不做任何色彩运算**（全文 `toRgb|tinycolor|@ant-design/colors` 命中 0），
  只跟预设名做字符串比对。所以 `color="var(--brand)"` 本来就能用；

## 十九、表达式类盲区清理与「品牌/设备资产」排除（2026-11-06）

§17.2 第 3 条登记的是「表达式/变量形式的色值是**双重盲区**」：既不被 codemod 扫到，

### 19.1 存量（三种独立口径，不用单一脚本下结论）

| 口径 | 正则 | 结果 |
|---|---|---|
| A 字符串内 `fill="…"` / `stroke="…"` | `fill=["']#[0-9a-fA-F]{3,8}["']` 等 | fill 68 / stroke 71（**其中 `SystemArtwork.tsx` 占 100 且早已整文件排除**） |

**C 才是真正的大头，也是本方案的终点问题**：这些色值喂给 ECharts / canvas / React Flow
节点数据，**它们不解析 CSS 变量**（§18.5 边界 1 正是为了保护它们）。所以
「`inlineHex` 收敛到 0」不是一个机械批次能到的目标 —— 它需要先定一个
**JS 侧主题调色板机制**（从 theme context 取当前主题→给图表供真实色值），属独立立项。

已实测到同类机制约束的一个实例：`RDM_TASK_TYPE_COLOR`（`contracts/src/constants/rdm.ts:872`，7 个色值）。
它的**消费方全部是 DOM/SVG**（`GanttChart` / `GanttBoard` / `useTaskTypeDict` 的 6 个消费文件
`echarts|getContext|<canvas` 均命中 0），本可直接令牌化；但 `useTaskTypeDict.colorOf` 的真值链是
「**DB 字典 color** → 内置常量 → `#8C8C8C`」—— 任务类型色可由用户在配置页填任意 hex，
所以这一族**天然不能靠 CSS 变量主题化**（令牌只覆盖得到默认值，覆盖不到库里的值）。
→ 归入上面的 JS 调色板立项，本轮不动。

### 21.1 先证实了最重要的安全属性：开关关闭时根本到不了深色

| 步骤 | 实测结果 |
|---|---|
| `localStorage.app_theme='dark'` + 重载（flag 未开） | `data-theme` 仍为 `light`，`--surface-1=#F5F5F5`、`--on-brand=#FFFFFF` |
| 同一份页面、仅把 flag 以**进程变量**注入 | `data-theme=dark`，`--surface-1=#141414`、`--on-brand=#141414` |

这不是“开关遮住了按钮”，而是 `theme-boot-script.mjs` 与 React 侧「开关关闭恒浅色」**刻意同源**：
若脚本按系统偏好先写了深色、React 再改回浅色，深色 OS 用户每次刷新都会闪一下。本轮把这段注释里的
设计意图**跑成了数据**，开关关闭 = 线上零视觉影响，至此有浏览器级证据。

### 21.2 特异性问题不再靠“应该能赢”：实测数字入表

方案 §4.6.5 当时诚实写了「jsdom 不能证明选择器真的赢了特异性」，并把它推给 §8.5 人工核对。
本轮把它做成了 **CI 机验**（`onBrandSpecificity.test.tsx`，13 例），因为登录页并不包含这三类控件，
而人工截图只能回答“看上去对”，回答不了“为什么对”：

| 控件 | antd 注入的实际规则 | 特异性 | 我们的规则 | 特异性 | 结论 |
|---|---|---|---|---|---|
| Checkbox 勾号 | `:where(.css-dev-only-do-not-override-…).ant-checkbox .ant-checkbox-inner:after` | **201** | `html[data-theme='dark'] .ant-checkbox-checked .ant-checkbox-inner::after` | **302** | 严格胜出 |
| Radio 内圆点 | `:where(…).ant-radio-wrapper .ant-radio-checked .ant-radio-inner::after` | **301** | `html[data-theme='dark'] .ant-radio-checked .ant-radio-inner::after` | **302** | 险胜（+1） |
| Switch 选中文字 | `:where(…).ant-switch .ant-switch-inner .ant-switch-inner-unchecked/-checked` | **300** | `html[data-theme='dark'] .ant-switch .ant-switch-inner .ant-switch-inner-checked` | **401** | 严格胜出 |

三条必须记下来的实测事实（都是本轮踩过才查到的）：

1. **antd 5 的 hashId 包在 `:where()` 里，而 `:where()` 特异性恒为 0**
   —— “CSS-in-JS 会加 hashId 因而特异性不稳”这句常见说法在 antd 5 上**不成立**，
   权重只由真类名贡献。#43 的 PR 描述里那句话是未验证的传统说法，本轮把它改正了。
2. **Checkbox 用单冒号 `:after`，Radio 用 `::after`**；两者都属伪元素列。只按 `::after` 写匹配
   会漏掉 checkbox，只按 `:after` 归一会漏掉 radio —— 所以两侧都要规范化。
3. **Checkbox 的白色写在基态**（`.ant-checkbox .ant-checkbox-inner:after`，不在 `-checked` 作用域），
   并且用 `border` **简写**声明 —— 简写同样设定 border-color，必须当竞品计入。

变异验证 3 组全部被抓到（降权到与 antd 相等 201、删整条、给未选中态也加覆写），
其中“降权到 201”那条报出的就是本次要防的真实事故：

```
AssertionError: 我们 201 必须严格大于 antd 最大 201
  我们: [data-theme='dark'] .ant-checkbox-inner::after
  antd: :where(.css-dev-only-do-not-override-mncuj7).ant-checkbox .ant-checkbox-inner:after
```

→ 也就是说：如果把选择器写短一级（去掉 `.ant-checkbox-checked`），**它会与 antd 打平**，
而同特异性下比的是源码顺序 —— 那是一种“今天赢、重构就输”的静默失效。这就是把守卫入 CI 的理由。
工具本身另有 7 条手算对照表钉住（探针初版把 `:after` 当伪类算，虚高了 100，靠这张表才暴露）。

### 21.3 §8.5 第 1 项：“登录页不变”基本成立，但画布这一层确实漏了（已修）

先拿到一个**推翻自己初步读法**的结果：单看 `.login-title-v2` 的计算色，浅色 `rgb(0,0,0)` / 深色
`rgb(255,255,255)` 看着像“登录页跟着主题变了”。但那是个**不可见的继承容器**（`.login-title-v2 h2`
自己写的是 `color: #fff`）。改成对「登录页 23 个**可见**文字元素」做同一调用内的 light/dark 差分：

```
{ n: 23, changedCount: 0, changed: [] }
```

→ 文字层 0 处变化，“登录页不变”在文字与玻璃面板上成立。但同一轮量到真正的缺口：

| 测量项 | 浅 | 深 | 判定 |
|---|---|---|---|
| `html` 计算背景（FOUC 画布） | `rgb(255,255,255)` | `rgb(31,31,31)` | ❌ 会跟随主题 |
| `.login-page-video` 背景 | `rgba(0,0,0,0)` | `rgba(0,0,0,0)` | 透明，不盖画布 |
| `.login-video` 背景 | `rgba(0,0,0,0)` | `rgba(0,0,0,0)` | 同上（颜色由视频本体提供） |

所以**视频加载前 / 未铺满的边缘 / 视频加载失败的回退场景会露出深色画布**——虽然平时看不见，
但它确实违反已拍板的“登录页不参与主题切换”。修复（`components.css`）：

```css
html:has(.login-page-video) { background: white; }
```

三个决定都有理由：用 `white` 而不是 `var(--surface-2)`（本条目的就是**不随主题变**）；
不写 `#FFFFFF`（不给 `cssHex` 棘轮添一笔，实测确实不变）；挂 `:has()` 而不是直接给
`.login-page-video` 加背景（后者会新增一层绘制，而画布本身才是问题根源）。

修后实测：

| 验证 | 结果 |
|---|---|
| 登录页两主题画布 | 均为 `rgb(255,255,255)`，`canvasNowStable=true` ✅ |
| 不外溢到非登录页 | 临时摘掉 `.login-page-video` 后画布立即回到 `rgb(31,31,31)`，`scopedCorrectly=true` ✅ |
| 浅色侧零变化 | 原本就是白画布，无差异 ✅ |

并已把这两条变成永久断言（同一测试文件的 `登录页不受主题接管（画布层也要钉住）`），
不留在“我看过一次”的口头结论里。

### 21.4 §8.5 清单现状：1 项已过，其余 11 项被凭据政策正当拦住

已验：第 1 项（登录页）。未验的 11 项全部需要**已登录会话**，而本仓自己的政策是
（`ENVIRONMENT-REFERENCE.md` §1.5）：“密码值只写在本地 `backend/.env.local` 与交付记录里，
**不得回显到本文件或任何入库文件**”，且已明确废除“Mock 登录账号”（前端自授 admin 会话等于绕过鉴权）。
把口令或 token 写进工具调用/会话记录就是一次回显，所以**本轮不是做不到，而是不该做**：

| 可执行的补验步骤（用户本人约 2 分钟） | 要看的点 |
|---|---|
| 1. `VITE_THEME_SWITCH_ENABLED=true npm run dev` | 顶栏主题入口出现 |
| 2. 用本地管理员账号登录并切深色 | 逐项对照 §8.5 第 2–12 项 |
| 3. 重点三项：门户卡片墙（scene 插画不变）、统计卡淡底、`Modal.confirm` 暖橙面板 | 这三处历史上有过“深卡配白边/白底亮字”类缺陷 |

### 21.5 本轮另外两条流程级发现

1. **沙箱会部分失败 `git checkout`**：在 workspace 外的工作树里，`git checkout` 能推进 HEAD/index，
   但**写文件会被拒**（Operation not permitted），结果是磁盘停在旧内容而 HEAD 已前进——
   `git status` 就会把那批文件报成“本地修改”。本轮实踩一次，后果是：**差点把它们当改动提交**，
   等于在一个新 PR 里默默 revert 上一批。
   做法改为：只按显式路径 `git add`，永远不用 `-A`/`-u`；并用 `git diff --stat` 看差方向的符号
   （本例是 `85 insertions / 199 deletions`，正好是上一批的**反向**，才识别出磁盘陈旧）。
   同理：`cp` / `perl -i` / `rm` / `git checkout -- <file>` 在 workspace 外均不可靠，
   改文件一律走就地编辑，删文件走专用工具。
2. **变异 harness 要区分“断言无牙齿”与“变异未生效”**：本轮四个 `perl -i` 变异全没落盘，
   harness 先把它们报成了“断言无牙齿”——幸好它同屏输出了 `WARN 变异未生效`，否则我会去改一个
   本来完全正常的测试。今后 harness 必须把“变异已落盘”的校验放在“测试失败与否”之前，
   两者不能合并成一个结论。
