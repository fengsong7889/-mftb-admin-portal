## 一、结论与本次确认

**推荐且已确认：先拆工程，不立即拆 Sealos 后端服务。**

采用“单源码仓库 + 前端多应用构建 + 后端 Maven 模块化单体 + 一个后端部署单元”。优先改造产研交付（RDM）、资产（EAM）、人事（HR）；其余系统先保留兼容工程，不以菜单数量机械决定服务数量。

- 目标：减少开发和发版的重复编译、缩小日常验证范围，尽量维持正常业务下约 **1元/天** 的应用运行成本。
- 后端业务模块可分别编译和测试，但首期仍装配为一个 Spring Boot JAR、一个镜像；Sealos 保持现有一个 Deployment。一个 Deployment 不等于永远只有一个副本。
- **明确限制：后端仍整体发布、整体重启，共享进程故障范围；不能把这一阶段称为后端独立部署完成。**
- 前端应用各有入口、类型检查、测试、构建产物与版本；不要求每个应用单独购买 Nginx 容器。
- 不拆源码仓库、不拆数据库、不更换框架、不引入微前端运行时、消息队列、服务网格或分布式事务。
- 本期优先完成三个大业务域的工程隔离。小系统仍在兼容工程时，明确标记“未独立”，不宣称全系统拆分完成。
- 后续是否独立部署 RDM，只作为测量后的独立决策，不是本方案的默认必做阶段。

**门禁策略已确认（不再重开）：保留提交/推送/CI 的全量门禁。** 拆分只缩小日常验证范围，不缩小最终验证范围；CI 可以按系统分片并行，但所有分片合起来必须覆盖全部已登记测试，任一分片缺失或失败即不通过。因此“拆分后只跑单系统”仅适用于日常开发档位，不适用于最终门禁，详见 §5.3。

**当前仅交付设计文档，不代表任何工程改造已经完成。** 不修改业务代码、数据库、Sealos 配额、HPA、域名或发布状态。

## 二、Sealos 成本测算

### 2.1 已知事实与不足

用户截图显示：

- 区域：HangzhouH；应用：mftb-admin-backend。
- 每实例配置：1核 CPU、1GB 内存。
- 弹性伸缩：CPU 目标70%，实例数1～3。
- 控制台估价：CPU 0.66～1.98元/天，内存0.33～0.99元/天，合计0.99～2.97元/天。
- 所选账期总额7.508843；未提供精确起止时刻与逐时副本数，不能将其直接当成固定日费。按7～8天粗算约0.94～1.07元/天，与用户描述基本一致。

截图不包含 JVM 实际内存峰值、CPU 限流、启动峰值、数据库连接数和完整项目成本，不能据此认定512MB足够，也不能断言过去发生过几次扩容。

### 2.2 计算方法

[Sealos 官网计价标准](https://sealos.run/docs/billing)给出的杭州参考单价：

- CPU：0.027671元/核·小时，折合 **0.664104元/核·天**。
- 内存：0.013956元/GiB·小时，折合 **0.334944元/GiB·天**。

以下按该参考价、每实例全天运行计算；实际账户结算以控制台和账单为准。官网参考价与截图两位小数估价存在小幅差异。

`日计算费用 = Σ[每实例CPU核数 × 0.664104 + 内存GiB × 0.334944] × 对应运行天数占比`

副本数变化时分时段累加；另加新增网关、静态托管、卷、出网、迁移/临时实例等费用。

**按分配资源和运行时间估算，不按代码量或CPU实际利用率乘折扣。** 只减少编译时间、但不改变运行配置，不会自动降低 Sealos 账单。

### 2.3 方案比较

以下配置仅用于算账，不代表已验证的生产容量；月费用按30天估算，不含额外服务。

| 路线 | 配置假设 | 计算费/天 | 计算费/30天 | 判断 |
|---|---|---:|---:|---|
| 现状 / 模块化后合并运行 | 1个1核+1GiB实例 | 约1.00元 | 约29.97元 | 本期基线；工程拆分不新增常驻成本 |
| 合并运行后评估降CPU | 1个0.5核+1GiB实例 | 约0.67元 | 约20.01元 | 有省钱空间，但必须验证限流、启动和HPA行为 |
| 两个小后端 | 各0.5核+0.5GiB | 约1.00元 | 约29.97元 | 只是数学上持平；两个JVM能否稳定未知，无新增网关及扩容预算 |
| 主后端+RDM | 0.5核+1GiB，加0.5核+0.5GiB | 约1.17元 | 约35.00元 | 尚未计网关、扩容等，已高于目标 |
| 主后端+HR+EAM+RDM | 各0.5核+0.5GiB，共4个 | 约2.00元 | 约59.94元 | 低配算例也明显超预算，不采用 |
| 16个极小后端 | 各0.1核+0.5GiB | 约3.74元 | 约112.26元 | 不代表可用容量；仍明显超预算，不采用 |

若16个后端均沿用现有1核+1GiB规格，仅计算费就约15.98元/天。

原方案还规划每系统一个 Nginx。即便假设平台允许每个静态容器0.1核+128MiB，也约0.108元/天；17个约1.84元/天，尚未计后端。**因此取消“一个门户系统配一个前端容器”的默认设计。**

### 2.4 成本结论与控制方式

1. 当前规模下，**合并运行通常更省常驻资源和维护费用**。功能菜单多不等于需要独立进程；拆进程会重复 JVM、线程池、连接池和监控开销。
2. 两个服务如果能装进原来的总配额，价格可以接近不变，但不是因为拆分本身更便宜。单个JVM可能更容易共享内存余量。
3. 保持现有配置时，目标是“不增加正常运行底座费用”，不是承诺任何一天不超过1元。当前HPA本身允许约3倍计算费。
4. 滚动发布期间旧新实例短暂共存也收费。新增一个现有规格实例运行10分钟，参考额外费用约0.007元；不能为省这部分费用取消就绪检查或先停旧实例。
5. 降CPU只作为最后的容量优化实验：先保留1GiB内存，验证后再决定是否采用0.5核。若触发更频繁的HPA扩容，日总价可能反而上升。
6. 预算范围纳入本次新增的所有应用计算/静态托管/网关费用；原有外部数据库、存储、模型和通知费用单列为“不因本次改造而新增”，不能把截图当成全项目总成本。
7. 不使用试用金、暂停必要任务、关闭日志/安全校验或关闭HPA等方式制造省钱结论。构建耗时、CI分钟数和Sealos运行费用分开统计。

## 三、对旧方案的审查与调整

| 旧方案问题或不足 | 本次修订 | 依据与验收 |
|---|---|---|
| 将独立工程与16套独立服务绑定 | 工程边界与运行边界分离，首期一个后端部署单元 | 成本表；部署清单不得新增业务后端实例 |
| 从广告试点，一开始涉及财务和商户交易 | 优先RDM工程隔离，再EAM、HR；广告与财务写链保留现状 | 广告退款在本地事务内调用财务写入，不能顺手改HTTP |
| 忽略可先获得的流水线收益 | 最先消除已证实的重复安装、检查和编译 | 后端测试产物与镜像内JAR摘要一致，Docker不再编译源码 |
| OA回调容易被统一改成异步 | 首期仅抽接口和本地适配器，保留每条流程的事务、异常和顺序语义 | OA授权、请假、产研的失败处理目前不同，逐路径回归 |
| 默认抽独立IAM并在线调用鉴权 | IAM仍在同一进程，不新增所有请求依赖的网络鉴权点 | 登录、撤权、强制下线、资源归属行为不变 |
| 同时改迁移为独立Job | 首期维持现有启动迁移、锁、自愈、审计和就绪门禁 | catalog、versionKey、初始化器和契约资源迁移后完整且仅注册一次 |
| 前端公共层仍可能引用业务页面 | 拆纯权限/导航契约和按域组件，禁止公共包反向引用应用源码 | 现有AuthContext、MenuTabs依赖Permission/types；日报预览引用RDM页面 |
| 只移动目录仍可能编译全仓 | 明确TS项目边界、Maven依赖方向、测试支持隔离 | 独立模块日志不得出现无关业务实现源码编译 |
| 增量构建容易被误解成减少最终测试 | 维持提交/推送/CI全量门禁；测试范围、编译范围、发布范围分别输出 | 不缓存旧测试通过结果冒充本次验证 |
| 版本文件与缓存存在串写风险 | 构建元数据写入各自产物，不回写共享源码；缓存严格校验输入 | 并行构建后版本不串台，源工作区无生成污染 |
| 全面迁移才算有收益，投入不可控 | 每阶段单独验收；先记录收益，不以完成16系统迁移作为前提 | 阶段失败停止扩展，禁止带病继续搬代码 |

本次采用 evolution-planner、risk-quality-reviewer、deployment-topology-analyzer 的分析方法，只读核查方案、代码和构建配置；未进行生产容量测试，不声称线上稳定性已经验证。

### 4.2 前端托管与发布

**本期不增加Sealos前端容器，也不切换现有生产托管。**

- 独立构建产物按应用保存；现有单站托管期间，由站点装配步骤组合目标应用的新产物与其它应用已验证的旧产物。
- 初次建立基线必须全量构建。以后引用的旧产物须有来源SHA、输入摘要、公共包/契约版本及文件校验；缺失或失配则重建/阻断，不能随意下载一个“最新版本”。
- 发布清单串行更新，基于最新已发布清单替换目标应用，防止两个发布互相覆盖。
- 在现有GitHub Pages模式下，整站上传/发布仍可能存在；**减少无关应用重新编译，不等于Pages具备按目录原子独立部署。** 单应用回滚通过重新装配发布清单完成。
- 保留当前/上一兼容版本的哈希资源，验证旧浏览器标签页在更新后不出现chunk 404；HTML、版本信息与内容哈希资源使用不同缓存策略。
- 如后续迁移托管，只评估一个共享静态站点/网关承载多应用目录，不采用17个Nginx。迁移费用、GitHub Pages适用范围、域名和缓存能力另行批准；不将现有托管描述为已完成合规评估。

### 4.3 后端模块化单体

建议目录职责：

| 目录 | 职责 |
|---|---|
| `backend/libraries/` | 最小技术底座、安全与测试基础设施 |
| `backend/contracts/<domain>/` | 按提供方划分的接口与最小DTO，不含业务Entity/Mapper |
| `backend/modules/rdm/`、`eam/`、`hr/` | 各域生产代码、资源和测试 |
| `backend/modules/legacy/` | 尚未抽取的业务，不包装成已隔离服务 |
| `backend/bootstrap/` | 唯一启动和装配入口、跨域本地适配器，生成完整应用 |

依赖原则：

1. 私有业务实现之间不直接互相依赖，只依赖对方的契约；双向业务协作通过契约和装配层本地适配器断开编译环。
2. 公共技术包不能装下全体Entity、Mapper、DTO或业务规则；现有`SecurityTestBase`拆成纯安全设施与各域Mock。
3. 保留Java 17/Maven/Spring Boot；优先保持既有包名、API、序列化与MyBatis映射语义，避免同时进行大范围命名重构。
4. 首期继续同一数据源与事务管理器、进程内调用；保持`@Transactional`代理、传播行为、异常处理及提交后通知时序。禁止为拆模块改成远程调用或统一异步。
5. 数据库不搬表、不换业务所有者、不引入逐模块连接池。表和字段的归属先用于工程约束与审查，不虚称同一个数据库账号已具备模块级物理隔离。
6. 初始化器、Mapper XML、定时任务、AOP和迁移资源纳入唯一注册清单。Bootstrap扫描不得让同一类/任务重复加载，也不得漏掉迁移与权限切面。
7. 后端模块JAR可分别产出，但完整镜像仍包含全部业务。禁止在运行容器中热替换个别JAR或共享可写依赖目录。

## 五、构建与验证提速的具体实现方向

### 5.1 先消除重复工作

已核实：后端workflow执行`mvn test`、`mvn package -DskipTests`后，Dockerfile再次从源码`mvn package`；其中Docker是新的编译环境，前面的JAR未被复用。

修订为：

- 后端以一次完整Maven生命周期完成编译、全部测试、打包和必要校验，迁移资源检查针对该JAR执行。
- 测试通过的JAR作为本次workflow制品上传；镜像job只消费同一运行、同一SHA、摘要匹配的JAR，运行镜像构建阶段不含Maven。
- 保留现有版本记录功能。`.git`目前用于运行时读取提交历史，不在提速切片中未经替代验证就移除。
- 前端尽量在同一runner完成一次依赖安装、一次完整类型检查、各门禁、测试与构建。CI后续打包必须依赖该次成功检查；本地`build:strict`入口保留。
- 私有前端变化不产生新的后端镜像；纯后端变化不必重新发布相同前端产物，但最终质量门禁仍按现行规则执行。

### 5.2 模块隔离后的日常任务

保留现有`check:affected`、`test:affected`，增加按应用/模块的构建入口与机器可读解释结果。

- 日常只选择目标模块、必要契约及其编译前置依赖；本地运行后端仍启动完整单体。
- 影响分析区分测试、编译、装配、发布四种范围。修改共享契约必须扩大消费者验证，不能为了显示“只编一个模块”漏掉真实依赖。
- Java选择以Maven模块依赖和明确的契约/业务链登记为准，不再用两跳类名共现作为可靠隔离依据。
- Git读取或解析失败、删除/重命名、未知归属、业务改动没有测试覆盖时，保守扩大范围或阻断，不显示为“无影响”。
- 新目录与`.qoder/rules/edit-verification.md`、门禁脚本同步适配，保持原安全分类；移动文件不能成为绕过L2的手段。
- 缓存键覆盖源码/资源、依赖锁与POM、编译参数、JDK/Node及插件版本、上游契约；失配即重建。禁止直接复用未经校验的IDE生成class。

**收益边界：** 本期首先保证“同一发布流水线不重复编译相同后端”和“日常目标模块不编译无关业务实现”。最终门禁仍执行全部测试；冷CI、首次拆分、公共依赖变更时，仍可能需要全量编译一次。不能承诺每次提交都完全不检查其他系统，也不预先承诺固定加速倍数。

### 5.3 日常 / 提交 / CI 三档行为对照（回应“是否只跑单系统前端”）

| 动作 | 现状 | 拆分后（P2 完成） | 依据 |
|---|---|---|---|
| 类型检查 | `tsc --noEmit` 扫整个 `src`（`tsconfig.json` 的 `include: ["src"]`） | 日常只检查目标应用 + 其依赖的共享包；其它应用源码不在其编译图内 | `tsconfig.json`、§4.1 独立 tsconfig |
| 前端单测 | 全量 vitest | 日常只跑该应用测试集合 | `scripts/affected-tests.mjs` 现有影响域机制 |
| 前端打包 | 全站一次 `vite build` | 只构建该应用产物，其它应用复用已验证产物（§4.2 装配清单） | `package.json` 的 `build`/`build:strict` |
| Lint | `eslint src` 全目录 | 日常只对变更文件；收尾/CI 全量 | `package.json` 的 `lint` |
| **提交/推送前 L2、CI** | 全量 | **仍为全量**，按系统分片并行执行，分片合集必须覆盖全部已登记测试 | `.qoder/rules/edit-verification.md` L2 档 |

**三个必须知道的例外（否则会被误认为“拆了没效果”）：**

1. 命中共享层仍强制全量，规则不变：`src/components/**`、`src/constants/**`、`src/contexts/**`、`src/hooks/**`、`src/i18n/**`、`src/utils/**`、`src/styles/**`、`src/App.tsx`、`src/main.tsx`、`src/test/**`、`src/pages/_shared/**` 及前端工程配置文件。该分类已内置在 `scripts/affected-tests.mjs` 的 `GLOBAL_FE`。
2. §4.1 列出的三处反向依赖未解环前，登录、菜单、权限、日报预览相关改动会把 RDM/Permission 拉进编译图并升档全量；解环是 P2 的验收前置，不是可选优化。
3. 天生跨系统的轻量门禁（`check:menu`、`check:i18n`）在语言包按域拆分前仍按全仓执行；它们不是当前耗时主要来源，但不得为显示“只跑单系统”而跳过。

**结论表述口径：** 对外只能说“日常开发只验证目标系统，最终门禁仍全量分片并行”，禁止表述为“CI 不再全量”或“改一个系统不需要回归其它系统”。

## 六、稳定性与业务回归门槛

| 保护对象 | 必须验证的路径 |
|---|---|
| 会话与权限 | 登录→门户→目标系统；撤权、强制下线、停用、越权、旧链接、跨标签退出；后端继续裁决资源归属 |
| RDM | 提交/准入审批→认领分配→任务→提测/验收→交付；需求变更、日报与已有通知链接 |
| EAM | 采购审批→订单→入库→领用/归还；借用、调拨等关联记录与权限；不生成重复库存动作 |
| HR/考勤 | 员工资料及人员选择；入转调离；请假批准后考勤重算；隐私字段和账号授权边界不放宽 |
| OA授权 | 审批通过→权限/额度实际兑现；失败回滚与现行实现一致，不能只看页面显示成功 |
| 广告/财务 | 扣费、退款、并发重复提交和账本一致性；仍保留本地事务链，不因工程移动改变结果 |
| 迁移与任务 | 升级前后versionKey、catalog、资源与契约完整；同一任务单一执行；迁移失败不就绪、旧版本保留 |
| 前端版本 | 单应用更新、全站装配、旧页签加载、深链接、语言切换、回滚后资源完整 |

每个领域先建立特征回归，再移动代码；不同时调整业务规则和工程边界。发现现有缺陷须区分“基线问题”与“本次回归”，不能通过修改断言、吞异常或减小测试范围收口。

- 模块单测可以隔离Mock；关键事务、锁、迁移与约束使用隔离MySQL 8验证，不能只依赖H2或Mock。
- 全量测试有清单和结果汇总；分片缺失、未执行或失败均不能通过。
- 本地重型前后端测试默认串行；CI分片使用隔离runner和数据库，避免把资源争用误判为业务错误。
- 真实链路验收包含浏览器→API→数据库事实→刷新回显；外部通知、计费使用测试端点或禁发模式，不触达真实收件人。
- 发布保留就绪/存活检查、优雅退出和请求排空；新实例就绪后再切流，滚动窗口防定时任务、通知与写动作重复。
- 单副本运行无法保证进程故障零中断；本方案追求不降低现有稳定性，不作高可用或零故障承诺。

**验收：** 全量门禁通过；Docker镜像无源码编译；镜像JAR与测试制品摘要一致；前端没有重复类型检查；输出前后耗时差值。若变慢，先定位，不继续扩大改造。

### P2：前端独立工程，按RDM→EAM→HR逐个完成

- 第一子切片先解 §4.1 列出的三处反向依赖（纯权限/导航契约包、日报预览组件、EmployeeSelect），否则后续“只跑单系统”不成立。
- 建立workspaces、公共小包、导航/权限契约和兼容入口；依次隔离每个大系统。
- 首个RDM切片验收完成后才开始EAM，随后HR；考勤与HR的业务归属单独登记，不按文件前缀硬合并。
- 应用发布采用可追溯站点清单装配，不新增Sealos静态服务。

**每域验收：** 私有页面构建不拉入无关应用源码、不启动Maven；关联页面/权限/深链/多语言正常；其它应用产物摘要不变；全站装配与回滚测试通过。

### P3：后端模块化，仍合并运行

- 先拆契约与安全测试支持，再按RDM→EAM→HR移动完整领域切片；跨域依赖改为本地接口适配，保留事务。
- 聚合启动入口仍生成完整应用；其它系统保留legacy，不复制出第二套长期分叉业务实现。
- 每域独立编译后必须再次验证完整应用装配、启动与跨域关键流程。

**每域验收：** 该域独立编译不包含其它业务实现/测试；允许必要契约和技术库；全量测试完整；无重复Bean/Mapper/任务、迁移遗漏或权限变化；后端仍只有一个部署单元。

### P4：容量与最终收益验收

- 汇总改造前后冷/热任务耗时、编译源码范围、测试用例数、产物尺寸、启动耗时、CPU/内存与成本。

- 若成本与稳定性通过，输出节省金额；否则维持原1核+1GiB和现有HPA，不以节省几角钱牺牲业务。
- 本期在P4结束，不自动进入后端多服务拆分。

## 八、最终验收与后续分服务准入

### 8.1 本期完成标准

1. 已隔离三大业务域的私有前端/后端日常构建不编译无关业务实现，依赖范围有可解释清单。
2. 一个后端发布周期只生成一次经过测试的JAR，镜像消费同一制品；测试数和安全门禁没有减少。
3. 全量冷构建与完整应用启动通过，避免只在开发机热缓存下成立。
4. 各切片关键业务与权限回归零新增失败；回滚演练通过，不产生重复财务、库存、授权或通知事实。
5. 同一环境和输入集至少3次测量，分别报告中位耗时及波动；结果必须表明实际改善，否则不标记提速完成，不预填百分比。
6. 同负载下关键接口p95和启动就绪时间相对基线不劣化超过10%；超过则阻断相应切片/容量调整并调查。LLM等外部耗时单列，不用于掩盖内部回归。
7. 正常业务7日平均成本目标≤1元/天；迁移期临时测试成本、滚动发布和异常扩容单列。若实际超目标，解释分项并保留安全配置，不自动关闭服务。
8. 三域之外未隔离的范围、已有缺陷和未知生产数据明确列出。

### 8.2 后续仅在满足条件后评估“主后端+RDM”

同时具备以下证据才另行提案：

- 去重和模块化后，发布等待/整体重启仍是可测量的主要痛点。
- RDM资源与变更频率数据支持独立运行，且能够明确其认证、员工主数据、OA回调、编号、通知和AI调用边界。
- 全部跨进程写路径已有契约、超时/重试/幂等、持久化失败恢复和回滚设计；不以同库假装跨进程仍有原本的本地事务。
- 单独核算两个JVM、数据库连接池、必要网关、HPA及滚动窗口，验证有资源余量；512MB是否足够必须实测。
- 若总成本超过目标，明确申请预算调整或继续合并运行；不能默认增加实例。

不预设再拆HR/EAM、不建设独立IAM集群；它们需要新的业务收益和成本证据。

## 九、变更影响、安全与回滚

- **前端影响：** 工程入口、构建/发布清单、共享契约和资源打包；页面设计和业务语义不变。
- **后端影响：** Maven模块、测试支持、装配和镜像制品链；部署单元、现有API及进程内事务不变。
- **数据库影响：** 首期不改变业务表结构和数据、不拆连接账号；保留迁移/自愈/锁/审计/备份。必要的新数据库改动另列纵向切片批准。
- **安全边界：** 前端校验仍仅负责UX；鉴权、资源归属、金额、状态由后端裁决。内部模块接口不能放宽HR改账号权限，公开分享接口不能因路由归组转为任意开放。
- **代码回滚：** 每个切片独立可撤回，保护用户其它改动；兼容入口保留到该切片验收通过，不在同一轮提前删除恢复路径。
- **产物回滚：** 保留上一已验证完整后端镜像及前端站点清单；按摘要回切，不重新从未知源码构建“旧版本”。
- **数据回滚：** 不删表/删字段；如出现独立业务数据变更，必须先验证旧程序兼容，不能只回滚镜像。
- **配置回滚：** 保存原资源/HPA/路由配置；降配或托管切换失败恢复原值。生产变更、云资源创建和实际发布始终另行授权。

### C.22 HR 域切片的实测阻碍（本批尝试后回退，结论入库）

尝试按同一四步法拆 HR（Hr*/Hcm*/Employee*/Position*/Contract* = 177 类）时，编译立刻暴露
**三组未在 C7 基线里体现的耦合**（因为它们是「改名后仍在同一包内」的横向依赖）：

| 耦合 | 证据 | 处置难点 |
|---|---|---|
| HR 自身强依赖 `Emp*` 主数据 | HR 代码引用 `EmpPositionRecord` **112 次**、`EmpContract` 11 次、两个 Mapper 14 次 | 这些类必须随 HR 一起搬 |
| legacy 反向引用 `Emp*` | `AuthorizationTraceService/Impl`（IAM 授权追踪）、`EmergencyContactService/Impl`（员工紧急联系人）、`SalaryConfigVO/SalaryIncomeVO/SalaryDeductionVO`（薪酬）、`AuthorizationCenterController` | 要么这些也属 HR（如紧急联系人），要么需要 IAM/薪酬侧契约 |
| 组织主数据 `Org*` | `OrgLegalEntity/OrgPosition/OrgJobGrade/OrgJobFamily` + Mapper 被 HR 直接使用 | 属 organization 域，需要只读契约或随主数据下沉 |

本次迁移已全部回退（`git status` 与 HEAD 一致），避免留下半迁移状态。
**结论：HR 不是一个“搬文件”的切片，而是需要先做三件事**：
1) 把 `Emp*`（员工主数据）与 HR 一起定义为人事域；
2) 为 IAM 的授权追踪、薪酬的薪资资料做只读契约（与 EAM 的 `EamPurchaseOrderPort` 同法）；
3) 组织主数据（`Org*`）下沉或提供只读投影。
这三件事做完，HR 才能像 RDM/EAM 一样用 `mvn -pl modules/hr -am compile` 验收。

**第二次尝试（按“HR = 员工资料”扩域）同样回退，新增两条硬证据：**

- HR 的 `Hcm*` 控制器直接调用**薪酬服务**：`HcmPayrollRunController` / `HcmPayrollBenefitController` /

  `PayrollBenefitService`、`PayrollEnrollment(VO)` 等薪酬域类型。
  把 HR 搬出去就必须同时决定「薪酬是 HR 的子域，还是独立域」——这不是搬文件，是领域划分决策。
- HR 还依赖**组织主数据**（`OrgLegalEntity/OrgPosition/OrgJobGrade/OrgJobFamily/OrgUnit` + Mapper + `OrgScopeService`）
  与 **OA 待办**（`OaApprovalTaskMapper`，离职待办改派）。前者应下沉为共享主数据，

入口只有 `assets/index-*.js` 一个 —— 这清楚说明**目前仍是单入口单站产物**，
清单只解决「产物归属与摘要可追溯」，不冒充「按应用独立构建」。

**装配规则单测（7 例）**：首次发布全 build；内容未变 reuse；同名不同 sha 必须 rebuild；
消失文件显式 drop；上一版有、本次没有的应用也要出现在计划里（写明 drop 什么）；
清单校验覆盖 sha 非法、重复登记、空应用、空清单。

### C.26 应用路由清单（§4.1 拆分基线）+ 门禁

**为什么这一步先做清单而不是直接搬路由**：App.tsx 有 **447 条 `<Route>`**、360 个 `lazy()`，
其中应用路由 rdm 56 / eam 81 / hr 80 = 217 条，且 3 条被 `<Suspense>` 包裹（公开分享页）。
脚本化搬迁在本机实测中两次产出破损 JSX（多行块终止行判断错、数组元素缺逗号），
这类重构必须逐字保序 + 回归测试，不能靠正则硬搬——所以先把「每个应用到底拥有哪些路由」固化成数据。

| 产物 | 内容 |
|---|---|
| `frontend/apps/<app>/src/routes.inventory.json` | 该应用路由清单：`path` / `module`（相对应用 src）/ `shareWrapped`；按 path 排序 |
| `scripts/gen-app-route-inventory.mjs`（`npm run gen:routes`） | 从 `src/App.tsx` 解析 lazy 与 `<Route>` 块生成清单；只收「组件全部属于该应用」的路由（混用例不猜） |
| `npm run check:routes` | 门禁：清单与 App.tsx 不一致即失败（要求重跑生成器），并接入 `verify` 与 CI |

**当前清单**：rdm **56**（公开页 1）、eam **81**（公开页 2）、hr **80**（公开页 0），共 217 条。
`shareWrapped=true` 的三条是 `/rdm-daily-view`、`/m/asset-tag-view`、`/asset-claim-sign`，
拆分时要按「公开分享路由」单独处理（不能跟着应用私有路由一起走）。

这条门禁的作用：以后任何人往 App.tsx 里加/改这三个应用的路由，必须同步刷新清单，
否则 CI 失败——**拆分基线不会静默腐坏**。
