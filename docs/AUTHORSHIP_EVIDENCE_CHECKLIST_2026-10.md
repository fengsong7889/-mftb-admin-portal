## 一、这份清单解决什么问题

`LICENSE` 第十条第 3 款承诺：「作者真实身份与署名的对应关系，以软件著作权登记证书、
版本控制提交记录及首次公开发表记录共同固定」。但**这三根支柱现在有两根是空的**：

| 支柱 | 现状 | 缺口 |
|------|------|------|
| 版本控制提交记录 | 638 个提交散布着 **12 种不同署名身份**，其中多数提交署名为一个英文占位假名 | 对方可主张「提交记录里的作者不是署名者，也不是你」 |
| 软著登记证书 | **未办理** | 没有任何官方文件把笔名 `fengsong7889` 与自然人本人绑定 |
| 首次公开发表记录 | 已具备（GitHub 仓库创建时间 + GitHub Pages 上线时间） | 需固化成可提交的证据形式 |

结论：**在笔名公开、真名不公开的路线下，第二项（登记）不是"锦上添花"，而是整条证据链的地基。**
本清单把它拆成可执行步骤。

> 🔎 本文档**不记录** git 历史中出现过的具体姓名与邮箱值（那些是本机主机名、内网 IP 派生的
> 邮箱与占位假名，属个人信息）。需要清单时在本机执行第四节命令自行获取。

## 四、步骤 2：`.mailmap` 非破坏性映射（推荐先做这个，而不是重写历史）

`.mailmap` 只改变**显示层**的作者归属，不改写任何 commit，风险为零，可以立即提交入库。

**第一步：在本机列出现有身份（不要把这些值抄进任何入库文件）**

```bash
git log --all --format='%an <%ae>' | sort | uniq -c | sort -rn
```

**第二步：在仓库根目录建 `.mailmap`**，格式为 `正确名字 <正确邮箱> <被映射的旧名字或旧邮箱>`：

```
fengsong7889 <you@yourmail.com> <旧名字1>
fengsong7889 <you@yourmail.com> <旧邮箱2>
fengsong7889 <you@yourmail.com> <旧名字3> <旧邮箱3>
```

每一行把历史里的一个来源身份归一到你选定的署名。**把所有旧身份都覆盖上**，
`git shortlog -sne` 的统计才会收敛成一个人。

**第三步：验证**

```bash
git log --use-mailmap --all --format='%an <%ae>' | sort -u   # 期望只剩 1 行
git shortlog -sne --all                                       # 期望只剩 1 个作者
```

> ⚠️ 不同子命令对 `.mailmap` 的默认套用行为不一致（`git log` 需 `--use-mailmap`，
> `git shortlog`/`git blame` 行为另有差异），**验证时统一带 flag**，别只看一个命令的结果就下结论。
> 网页端是否采用 `.mailmap` 以 GitHub 当前行为为准，需实测确认，不要把本地验证结果当成网页端结论。

## 六、步骤 4：软件著作权登记（核心）

### 6.1 官方依据与入口

- 法规：《计算机软件著作权登记办法》（国家版权局公布），材料要求见第九、十、十一条，
  例外交存见第十二条，封存见第十三条，审查时限见第二十条，不予登记情形见第二十一条，
  补正期限见第二十二条
- 登记机关：**中华人民共和国国家版权局**；受理机构：中国版权保护中心
- 入口：中国版权保护中心官网 [ccopyright.com.cn](https://www.ccopyright.com.cn/) → 注册 → 个人实名认证 → 计算机软件著作权登记

> ⚠️ **费用与时效不要按本文数字做预算**：第三方攻略的口径互相冲突且经常过期。
> 官方办法第二十条明确的是「自**受理日**起 60 日内审查完成」；实名认证审核、加急通道、
> 收费金额等以版权中心官网当期公示为准。

### 6.2 材料清单（个人申请人）

| 类别 | 具体材料 | 要点 |

### 6.3 源程序样本的制备（可直接执行的起点）

```bash
# 1) 选取候选源文件（前端 src + 后端业务模块），按目录顺序连续排列
git ls-files 'src/**/*.ts' 'src/**/*.tsx' 'backend/modules/legacy/src/main/java/**/*.java' \
  | sort > /tmp/soft-files.txt
# 想定制开头/结尾时，改为手工维护这份清单（或用 head/tail 挑定的文件列表拼接）

# 2) 合并为一份文本，去掉空行（实践口径是提交"有效代码行"，最终以版权中心公示要求为准）
xargs grep -hv '^[[:space:]]*$' < /tmp/soft-files.txt > /tmp/soft-src.txt
wc -l /tmp/soft-src.txt

# 3) 按每页 50 行计算，取前 30 页与后 30 页
head -n 1500 /tmp/soft-src.txt > /tmp/soft-front.txt
tail -n 1500 /tmp/soft-src.txt > /tmp/soft-back.txt
```

**实测规模（2026-10-31 在本机跑过，命令可用）**：上述三类文件共 **1358 个**，
去空行后 **约 24.1 万行**，折合 **4800+ 页**。远超过 60 页，所以**必须做前后截取**，
不必纠结“全部提交”。

> 🔵 **排序直接决定材料观感**：命令里的 `sort` 会按路径字母序排。但登记要求
> “必须含软件起始语句”且“最后一页应是程序的结束页”。建议手工定制文件列表顺序：
> - **开头**放真正的入口文件：`backend/bootstrap/.../MftbAdminApplication.java`、`src/main.tsx`、`src/App.tsx`
>   ——这样前 30 页看起来就是一个程序的开头；
> - **结尾**以一个有明确结束语句的文件收束，保证后 30 页的最后一页是程序尾部；
> - 中间内容不敏感（只截 30 页），不必全量拼搭。

> 🔴 「前、后各**连续** 30 页」里的“连续”是硬要求：前 1500 行必须来自文件列表的**开头连续部分**，
> 后 1500 行来自**结尾连续部分**，不能随机抽样拼接。排版（页眉、页码、每页恰好 ≥50 行）
> 需要在 Word/PDF 里再做一遍，命令只负责把原始内容切准。

## 八、步骤 6：历史作者重写（破坏性，最后做，且要算清代价）

只有在完成 1~5 之后、且**与 git 历史凭据清洗合并成一次操作**时才做。单独做一次的收益
低于它的代价。工具用 `git filter-repo`（配合 `--mailmap`），由本人执行。

**必须先确认的 4 个影响面**（缺一不可，都是本项目的真实依赖）：

| 影响 | 具体位置 | 处置 |
|------|---------|------|
| 所有 commit SHA 变化 | 生产库 `sys_version_history.commit_hash`（`VARCHAR(40)`）存的是同步时的 Git SHA | 表中存量记录会指向**不存在的提交**，「版本管理 → 从 Git 同步」页会出现追溯失效，需要评估是否重跑同步或做数据订正 |
| 生产后端镜像内嵌 `.git` | `backend/Dockerfile` 复制 `.git` 目录供读取提交历史 | 重写后必须重新构建镜像，否则容器里还是旧历史 |
| CI/CD | push 到 `main` 触发 `deploy.yml` + `backend-docker.yml` | force push 会连带触发一次生产部署，需安排在可接受部署的时段 |
| 协作者本地仓库 | 全部需要重新 clone | 提前通知，且不要在他人有未推送分支时执行 |

**执行前硬性检查**：

- [ ] 所有已知泄露凭据均已完成作废处置（凭据类变更属于仓库外信息，**不在公开文档里逐项跟踪状态**；
  实况见本地未入库台账 `.qoder/security-followups-2026-10.md`）——未逐项确认前不要清史
- [ ] 已确认无并行分支/未推送工作
- [ ] 已备份一份完整旧仓库（`git clone --mirror`）
- [ ] 已知悉：已存在的 fork 与他人的 clone **无法回收**，清史只是阻止新增发现

执行后：向 GitHub 提交工单请求清理缓存视图，并在 `ENVIRONMENT-REFERENCE.md` §八 的
泄露处置台账里勾掉「git 历史清洗」一项。
